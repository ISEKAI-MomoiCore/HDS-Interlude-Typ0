# 她的显形：生成式 Presence 渲染愿景与可行路径（SV3/SV4 语境）

> 状态：实验性前瞻设计，尚未实现——本文档用于讨论愿景、边界和可行路径，不冻结实施阶段或具体接口
> 适用项目：`HDSI-desktop-typ-0`（桌面壳）+ `koishi-plugin-hds-interlude`（插件）
> 关联文档：`ENVIRONMENT_OBSERVATION_DESIGN.md`（环境观察/单向窥视）、`SV34_AGENCY_CORE_VISION.md`（版本阶梯 SV1–SV4 见其 §0）
> 关联愿景：本文档对应 EO 文档中的“Presence 视图”和角色物品图像化方向；是否完整落地，取决于后续叙事实验、渲染质量和设备条件
>
> 一句话：用 AI 绘图只生成"她"的透明人物帧，按空间锚点与剧本姿态合成的已校准真实场景中，
> 以 0.x 帧/秒的节奏让她在用户的房间里可见。生成归宿主/云端（慢），合成归显示端（快），
> 两者之间的契约可以先在 typ0 固定机位中驱动平面合成，未来再迁移到 AR 设备中的 3D billboard 或其它空间渲染方式。

## 1. 设计命题与定位

环境观察（EO）建立了单向窥视：她经由摄像头感知用户的环境，生活在对应的叙事空间（副本环境）里。EO 遗留了一个缺口——用户看不见她。本系统补上这一半：**把剧本中的她渲染进用户的真实视野**。

定位约束（继承自 EO 与 SV34）：

- 她的存在位置、动作、朝向来自持续写作（ScriptCommit），渲染是**派生状态**——可重建、可删除、可失效，永远不反向驱动她的行为；
- 可见性由她的元主体性决定：何时被看见、以什么角度被看见、是否走出画面，都在剧本中产生；
- 她不改变现实物体；"互动"是叙事性与视觉性的（接触姿态 + 接触阴影），没有物理模拟；
- 单帧生成延迟（秒级）被 0.x 帧/秒的目标节奏吸收——本系统本质即是 AR（把她的存在叠加进用户所在的真实空间），typ0 阶段以"固定摄像头 + 校准 + 平面合成"承载同一套 AR 语义（空间锚定、遮挡、在场）：AR 硬件不是首阶段的前置条件，而是 SV4 把同一契约换成设备原生渲染的升级件。

## 2. 总体架构：按延迟分层

```
┌─ 慢层（秒级，允许离线）──────────────────────────────────────┐
│  剧本状态 ──► 姿态求解(rig spec) ──► 3D 底帧(Blender A–F) ──► AI 后绘制(G) │
│              （确定性计算）          （赛璐璐底+遮罩+线深通道）  （分区重绘：表情/质感）│
└──────────────────────────┬─────────────────────────────────────┘
                           ▼  可迁移契约：锚点 + rig spec + alpha 人物帧
┌─ 快层（<50ms，显示端）────────────────────────────────────────┐
│  合成器：定位叠层 → 遮挡 → 光影配方(§7) → 呈现                     │
│  typ0 阶段 = 宿主合成进摄像头预览；SV4 阶段 = 设备原生渲染(立牌语义)  │
└────────────────────────────────────────────────────────────────┘
```

两层各自独立演进：慢层换模型/换工作流不影响契约；快层换渲染器（2D 合成 → 3D 实时 → AR billboard）不影响慢层。**SV4 迁移 = 只换快层**。

### 2.1 渲染器家族（快层是多方案的）

契约 `(锚点, 姿势, 朝向)` 之下，"把她画出来"有三种实现，共享同一求解层与空间状态层：

| 渲染器 | 姿态控制形式 | 帧率 | 角色一致性 | 依赖 |
|---|---|---|---|---|
| **R2 串行管线（主，已裁定）** | 3D 姿势重定向 → Blender 渲染出底 → **AI 后绘制**补风格化细节与表情 | 叙事节奏（关键帧触发后绘制） | 3D 资产锁几何与配色，AI 只加高频笔触 | Blender sidecar + 绘图模型 |
| R1 纯 AI 生成帧 | 3D 姿势投影为骨架图 → ControlNet | 0.x fps | 参考图/LoRA 维持 | 绘图模型（云/本地）；冷启动用 |
| R2b WebGL 实时 NPR（备选） | 同 R2 前半，three.js toon + 轮廓通道 | 实时 | 同 R2 | 零额外安装；质感上限低 |
| **R3 全实时三渲二（2026-09 扩充，§6.2c）** | 同 R2 前半 + **实时表情**（blendshape/贴图换脸）+ **物理骨骼**（SpringBone），零 AI 依赖 | 连续实时（60fps 级） | 3D 资产锁全部 | MToon/EEVEE + VRM 生态 |

主渲染器是**严格串行**的两段：Blender 渲染器通过骨架完成阶段 A–F（角色资产、赛璐璐着色、描边、动画、灯光、渲染），产出带 alpha 的赛璐璐底帧与区域遮罩；AI 后绘制（阶段 G）在其上补少量风格化细节与面部表情。几何、姿势、构图、遮挡、明暗由 3D 段锁定——AI 段**只做加法**（笔触质感、材质细节、表情重绘），不做结构性改动。伊人制造管线的"3D 出底 + CLIP STUDIO 手工修正表情"结构在此被全自动复刻，且更进一层：表情修正也交给 AI。

R2 仍是 SV4 的原生路径：3D 模型的 z-buffer 与 AR 设备深度图做 z-test 即像素级遮挡，§3 的 L1/L3 遮挡补丁整体退役；赛璐璐色阶直接消费场景光照信息（环境色与主光方向映射为 Blender 灯光）。R1 保留冷启动职责（尚无 3D 资产与 Blender 环境时即可显形）；QQ"她的照片"走 R2 串行管线的离线高清渲染。渲染器策略已由维护者裁定（原 D10），不再作为待决项。

## 3. 分层渲染模型（合成器内部）

合成器把一帧画面理解为固定次序的图层，与溶图社区的"背景不动、只动人物与光影"实践同构：

| 层 | 内容 | 来源 | 更新频率 |
|---|---|---|---|
| L0 | 相机帧（真实房间） | 摄像头/校准快照 | 呈现时 |
| L1 | 静态遮挡层 | 校准多边形（桌沿、显示器边缘等 z 值大于她的物体） | 一次校准 |
| L2 | 她的透明人物帧 | 串行管线：Blender 赛璐璐底帧 + AI 后绘制（§6） | 0.x–1 fps |
| L3 | 动态遮挡层 | 人形分割（用户从她前面经过） | 呈现时 |
| L4 | 光影配方 | 确定性后处理（§7） | 恒定 |

深度规则：L2 按 rig spec 携带的锚点 z 值插入 L1 各多边形之间；L3 恒在她之上。

## 4. 空间状态层：场景校准

固定机位是本方案最大的成本优势：场景几何与光照参考**一次校准、长期复用**。

```ts
interface PresenceCalibration {
  calibrationId: string
  cameraId: string
  canvas: { width: number, height: number }        // 归一化到 0–1 坐标系
  /** 已知空间锚点（她可占据的位置）。z：0(远)–1(近)，与 occluders 比较深度。 */
  anchors: Array<{ id: string, label: string, x: number, y: number, z: number,
    postureSet: string }>                          // 该锚点允许的姿势组（如"桌边坐姿组"
  /** 静态遮挡多边形：z 大于她当前锚点的多边形盖在她上面。 */
  occluders: Array<{ id: string, label: string, z: number,
    polygon: Array<{ x: number, y: number }> }>
  /** 光影配方的采样参考：环境色采样点 + 主光源方向。 */
  colorRefs: {
    ambientSamples: Array<{ x: number, y: number, label: string }>
    keyLight: { from: 'left' | 'right' | 'top' | 'front', tone: 'warm' | 'cool' | 'neutral' }
  }
  /** 接触平面：接触阴影的 y 基准（桌沿高度等）。 */
  contactPlanes: Array<{ id: string, label: string, y: number }>
  calibratedAt: string
}
```

校准的产出方式见决策点 D7（手动标注 UI / 视觉自动推断 / 分阶段）。校准数据是**设备本地数据**：只含归一化坐标与多边形，不含图像。

## 5. 契约核心：rig spec

剧本状态到生成请求之间的全部几何/姿态信息，收敛为一个确定性求解结果。它同时是生成层的控制条件与合成层的定位依据。

```ts
type PostureId = 'sit-writing' | 'sit-looking-at-user' | 'sit-leaning' | 'sit-rest'
  | 'stand' | 'walk-by' | 'crouch' | 'sleep' | string   // 姿势库可扩展

type Facing = 'camera' | 'away' | 'left-profile' | 'right-profile'
  | 'back-left' | 'back-right'

interface RigSpec {
  rigId: string
  anchorId: string
  posture: PostureId
  facing: Facing
  /** 画布定位：锚点 + 姿势基准高度推导的包围盒（归一化坐标）。 */
  bbox: { x: number, y: number, w: number, h: number }
  /** 接触点（接触阴影的位置与类型），由锚点 + 姿势模板推导。 */
  contacts: Array<{ planeId: string, x: number, y: number, kind: 'lean' | 'rest' | 'sit' }>
  /** 生成强度提示（表情/氛围），仅影响提示词，不影响几何。 */
  mood?: string
  /** 深度：取锚点 z。合成层用它与 occluders 排序。 */
  z: number
  /** 生成时刻的相机位姿（AR 阶段来自设备追踪快照；typ0 恒为校准机位）。
   *  求解器据此计算画面透视（她被看见的角度）；贴片朝向由它反向推导
   *  （立牌语义：牌面法线指向该位姿，牌面恒竖直）。 */
  cameraPose?: { x: number, y: number, z: number }
  /** 精细动作轨迹（§5.2）：一段骨骼状态序列（生成优先——M-gen 产出的骨架流
   *  或库剪辑/程序化片段），在姿势包络内叠加；M0 程序化层恒在。
   *  分辨率上限即动作生成服务的输出粒度，Agency Core 流式 tokens 直填此字段。 */
  motionTrack?: Array<{ clipId?: string, procedural?: string, skeleton?: unknown, durationHintMs?: number }>
}
```

求解器是**纯函数**：`(calibration, presenceState) → RigSpec | 'off-screen'`。

**姿势枚举与骨架流的关系（契约闭合）**：`posture` 标签承担菜单/缓存键/道具声明/节拍包络校验；`motionTrack.skeleton` 存在时**覆盖该姿势的默认骨架**（实际姿态以骨架流为准），但 posture 标签仍生效（缓存键、requiredProps 装配、L3 包络都以标签判）。两者是"标签管语义、骨架管形状"的分工，不冲突。presenceState 从 ScriptCommit 的空间痕迹与副本环境状态提取（她的当前位置、活动、朝向描述），提取规则与 EO 的 §7.4 Presence 视图同源。

姿势库（PostureId → 姿势资产）是静态资产表。**姿势以 3D 原生形式定义**（一个人形姿势 = 3D 骨架状态 + 可选过渡动画片段 + 提示词片段 + 接触点模板 + **所需道具声明 requiredProps**，见 §6.6），按渲染器投影：R1 投影为该机位视角下的 OpenPose/DWPose 骨架图，R2/R2b 重定向至角色骨架（串行管线的 3D 段与 AI 段共用同一骨架状态）。剧本活动文本 → 姿势枚举的映射由规则 + 兜底模型分类完成；映射不到时回落到锚点的默认坐姿。R2 的姿势切换遵循**有限动画**语义：保持（hold）为常态、换姿势按一拍二/一拍三节奏出帧、关键动作补少量插值帧——跳帧感是传统动画的作画节奏，按风格处理而非缺陷。

### 5.1 presence 状态来源：剧本 → rig spec 的映射（分层）

剧本文本本身不含位置关系，翻译层由四个来源层级构成，宿主对来源无感知（只认契约）：

| 层 | 机制 | 成本 | 定位 |
|---|---|---|---|
| L1 主模型副输出 | NarrativeDecision 增加可选 `presence` 字段；**空间词汇表注入**（校准锚点 + 姿势库 + 朝向/表情枚举作为菜单进提示词——同贴纸目录/端点选择的"菜单注入 + 受限枚举"先例）。输出落 script entry metadata：**每个剧本节拍携带一个 presence 状态，节拍即关键帧** | 零（随主调用） | 首选；写作时即被空间锚定（"窗边"本来就是合法锚点，不存在事后对不上） |
| L2 presence 侧任务 | 主模型缺席/非法时（小模型常见），一次便宜 JSON 侧任务：读本节拍 + 同一份菜单 → 输出枚举；复用现有侧任务基建（时间导演/压缩同管道），可指定任意 provider。最底层再垫纯词表规则（姿势库触发词表正则） | 每节拍一次小调用 | 兜底 |
| L3 钳制层 | 宿主校验：锚点存在于校准、姿势在库、朝向/表情合法；**连续性检查 + 节拍包络**（§6.5 R1–R3：一帧一拍、朝向 ≤45°/帧、锚点 ≤一步/帧、sit↔stand 经前倾帧、持物连续；超包络插节拍帧或判 cut）；非法值回落上一状态 | 零 | 永远在；使 L1/L2 的错误率无关紧要 |
| L4 Agency Core（未来） | 更高实时性的剧本化创作概念接管 presence 流——**已具体化为 Agency Action Frame 模型（§18–19，SV34 §11–12）**：worldAction 即 rig spec 上游契约 | — | 来源升级，**渲染层零改动**——契约先行是关键 |

presence track 是 script entry metadata 的一等公民（可审计、可重放、可删除、可由任意来源填充）；映射机制选择见决策点 D13。

### 5.2 动作生成层（一等公民，生成优先）

姿势枚举菜单只承担**粗契约**（锚点 + 基础姿势 + 朝向 + 表情）；动作生成服务是独立一等层，**大动作自由生成、细节走预设**：

```
叙事模型（主叙事 / 未来 Agency Core）
  │  动作描述（自然语言——剧本本来就在写）或远期原生交错 motion tokens
  ▼
动作生成服务（NL → 骨架流）
  ├─ 躯干/手臂/腿/颈/头朝向：text-to-motion 自由生成（MotionGPT/MotionLLM 开源权重；MoMask/MLD 级速度）
  ├─ 手部/脚部：预设手型库 + 接触 IK（foot locking）——SMPL 底座无手指，领域标准做法
  ├─ 约束钳制：look-at、桌面接触、锚点包络（L3 职责并入）
  └─ 物理与风格收尾：弹簧骨、Cascadeur 式补间、风格化 retiming（自然主义时序→动漫顿挫，必做）
  ▼
骨架流（motionTrack 的分辨率上限）→ 串行管线（Blender NPR → AI 后绘制）不变
```

**分层职责（优先级已按生成优先重排）**：

| 层 | 内容 | 定位 |
|---|---|---|
| M-gen 生成基座 | text-to-motion 自由生成大动作；**动漫分布微调路径**：MMD VMD 语料（海量动漫风格运动数据）retarget 统一骨架 + motion-to-text 自动标注 → 微调动漫分布模型 | 大动作的唯一来源 |
| M0 程序化永续层 | 呼吸、重心微移、眨眼、look-at 头眼 IK、发梢衣物弹簧骨、笔尖微动 | 环境性动作永不生成（零成本恒在） |
| M2 库与检索（降级） | 预设手型库；生成不可用时的大动作兜底；生成的 few-shot 锚点。复用 HDSI 既有 embedding 基建 | 手脚细节 + 兜底 + 锚点 |
| M5 AI 后绘制修正 | 表情与次级细节（G 阶段既有） | 面部表现力 |

**延迟事实**：MLD 级扩散对短动作片段亚秒、MoMask 级 masked transformer 更快、MotionGPT 类可 token 流式（IRG-MotionLLM 原生交错增量生成）——对 0.8–1 fps 串行管线为降维打击；流式形态即 Agency Core 的正确接口。

**叙事模型集成两步走**：近期 = 剧本自然语言动作描述直接喂生成服务（零改动）；远期 = **叙事模型原生输出交错 text+motion tokens**（IRG-MotionLLM 已证形态）——记为 Agency Core 第一条设计要求：统一流式模型输出文本与动作 token，动作超低延迟由此原生获得而非外挂。

行业参照：Neuro-sama 与 Amica/Utsuwa 生态均为"库 + 程序化 + 触发"（无生成层）——证明 M0/兜底可用；生成基座是本系统的差异化上限。动作策略选择见决策点 D14。

## 6. 人物呈现层

呈现层按渲染器家族分三条实现（§2.1），共享 rig spec 与姿势库。

### 6.0 质感目标：赛璐璐 × 厚涂结合体

目标画风是**赛璐璐骨架上叠厚涂血肉**——插画界真实的"セル塗り+厚塗き"混合画法，技术映射为两段分工：

| 画风要素 | 归属 | 技术实现 |
|---|---|---|
| 轮廓线、亮部/固有色平涂、干净色阶边界 | 3D 段（A–F） | 影法线控制的赛璐璐二分/三分色阶 + Freestyle 变宽描边（平涂由 NPR 管线天然产出，绝对稳定） |
| 暗部/材质/发丝/布料的厚涂笔触、环境色浸染 | AI 后绘制（G） | 低重绘区较高强度 img2img + 厚涂风格 LoRA/提示词；或 Stylized Neural Painting（CVPR 2021）式 stroke-based 笔触层——可微渲染器、笔画厚度可控、支持 impasto/湿画法，是"厚涂"的直接技术对应物 |
| 面部表情细节 | AI 后绘制（G）脸部 pass | §6.3 脸部专项生成 |
| 整体平面化收敛（把 3D 渲染感压平成 2D 画） | AI 后绘制（G）全域 pass | few-step img2img 平面化（见 §6.3 加速与超轻档） |

该分工的要点：**结构稳定性交给 3D（画得对），笔触生命感交给 AI（画得像手画的）**——赛璐璐保证她跨帧永远是"同一个人在同一张画里"，厚涂保证画面不 plastic。

### 6.1 R1：AI 生成帧渲染器

职责单一：给定 rig spec 与角色外观设定，产出一张**透明背景人物帧**。

```
RigSpec ──► 3D 姿势投影骨架(ControlNet 姿态控制) ─┐
角色外观(参考图/角色卡) ────────────────────────┼─► 绘图模型 ─► 抠像 ─► alpha 人物帧
风格预设(画风/线条/上色) ────────────────────────┘
```

- **姿态控制走骨架而非提示词**：朝向与动作由 rig spec 的 3D 姿势投影出的 OpenPose/DWPose 骨架图约束，模型只负责把骨架画好。视角词（side view / from behind 等）作为辅助条件并入提示词。
- **背景处理**：生成时使用纯色/低噪背景，之后经分割抠像（动漫色块边缘对抠像友好）。
- **一致性**（决策点 D1）：同一房间里的同一个人，跨帧不能面目全非。候选方案见 §9。

### 6.2 R2：三渲二 NPR 离线渲染器（伊人制造路线）

**参照基准**：《伊人制造》（《メイクアガール》，安田现象 / Xenotoon，2025 剧场版，全编全 3DCG）——约 7 人核心团队以 Blender 三渲二完成传统动画观感的剧场长片。其公开可查的管线特征：全流程 Blender 为核心；**表情经作画监督在 CLIP STUDIO PAINT 上做 2D 修正描画后再交动画师**（"3D 出底、2D 修脸"的混合结构，是脸部不崩的关键）；剧场级色管理贯穿画面制作；有限动画节奏。管线深度资料见 CGWORLD 2025年2月号（vol.318）制作特集。

**大体渲染流程**（阶段 A–H，含本系统的承接方）：

| 阶段 | 内容 | 承接 |
|---|---|---|
| A 角色资产 | 动漫比例建模 + 绑骨 + **影法线用修正网格**（单独调制的低模/修正网格经法线传递控制阴影边界走向——阴影线该断在哪、怎么拐是"画出来的"而非光照算出来的） | 一次性资产（开放问题 8） |
| B 赛璐璐着色 | 二分/三分色阶，**彩色阴影**（偏环境色的暗部，非黑影）；脸部按视角使用预制表情资产（颜面 pattern，正/侧/仰/俯各备），避免 3D 脸在非正视角崩坏 | Blender 材质 + 姿势库表情位 |
| C 描边 | Freestyle 变宽线（按深度/距离控制线宽）+ 手绘抖动参数；轮廓线是"笔迹"不是几何边缘 | 渲染管线参数（固定配方） |
| D 动画 | 姿势库 3D 状态 + 一拍二/一拍三节奏；关键动作补 2–4 帧插值；冲击帧可用 smear/变形板 | rig spec + 姿势库 |
| E 灯光 | 校准 colorRefs/keyLight 映射为 Blender 主光（方向/色温）+ 环境光；色阶边界由 A 的影法线决定，灯光决定明暗侧 | PresenceCalibration |
| F 渲染 | Blender headless（EEVEE）**多通道输出**：① 赛璐璐底帧（带 alpha）② 区域遮罩通道（脸/发/衣服/物件，由头骨投影与材质 ID 派生）③ **法线通道（必需，双用途：ControlNet 条件 + 显示时实时重光照 §7.1）** ④ 线稿/深度通道（ControlNet）⑤ **参考光照快照**（生成时灯光参数，供 Tier 1 比值计算） | Blender sidecar |
| G AI 后绘制 | 串行第二段（§6.3）：以底帧为 img2img 初值，**分区重绘**——脸部区域高重绘（表情，来自 presenceState 的表情/情绪位）、其余区域低重绘（仅补笔触质感与材质细节，几何/描边/色阶不动）；线稿/深度通道作 ControlNet 锁定构图 | 绘图模型（复用模型中心 image 用途） |
| H 摄影/合成 | §7 配方收尾：色彩迁移（她的色阶向房间环境色微调）、接触阴影、边缘熔接、纸感/网纹与辉光 | 合成器 |

管线要点：**质感三支柱是 A（影法线）、C（描边）、G（AI 后绘制的表情层）**——A/C 属"人工调制"资产，G 属 AI 能力；三者都不依赖实时渲染，这正是离线 Blender 路线能达到传统动画观感、而 WebGL 实时路线难以复刻的原因（R2b 的根本上限所在）。伊人制造用 CLIP STUDIO 手工完成的表情修正层，在本管线中由 G 阶段的 AI 后绘制全自动承担。

```
RigSpec ──► 姿势重定向(角色骨架) ──────────────┐
校准场景(锚点世界坐标 + 赛璐璐灯光) ────────────┼─► Blender headless ─► 赛璐璐帧(alpha)
角色模型 + 赛璐璐着色 + Freestyle 描边 ─────────┘     (EEVEE，秒级/帧)
```

- **模型资产（格式与质感解耦）**：.blend / MMD pmx 导入 / VRM 导入皆可——质感由 NPR 管线接管，与模型来源生态无关。来源路径见开放问题 8。
- **部署形态**：Blender 作为宿主 sidecar（headless/background 模式），与 ComfyUI sidecar 同一管理方式（安装引导、进程生命周期、渲染队列）。EEVEE 单帧秒级，完全覆盖叙事节奏；渲染器不直接吃背景图，输出可复用的干净人物帧。
- **遮挡**：typ0 阶段沿用 §3 的 L1/L3 图层近似（渲染帧作为 L2）；AR 阶段 3D 模型 z-buffer 直接与设备深度图 z-test，L1/L3 退役。

### 6.2b R2b：WebGL 实时 NPR（备选）

three.js 自定义 toon 着色 + 轮廓通道，零额外安装、可实时。**上限证据修正**：GGXrdShading（galloscript，GitHub WebGL 复刻 demo）已证明 Guilty Gear Xrd 级技术（顶点手调法线 = 影法线、ILM illustration map、limited animation 帧步进、后处理）可在 WebGL 复刻——R2b 的质感上限高于此前评估，配合 RealToon 类生产级 toon shader 与 MSDF 墨线可接近主机动画观感。仍保留为备选的根本原因不变：手工调法线/ILM 资产的人工成本与连续动画数据依赖（稀疏姿态流下的廉价感），以及 G 阶段厚涂/表情 AI 修正无法实时化。作为"无 Blender 环境"降级与 AR 阶段设备端兜底。

### 6.2c R3：全实时三渲二渲染路径（2026-09 扩充）

> 与 R2 并行的**连续在场档**，不替代 R2 的离线高清职责；原构想（R1/R2/R2b 及 G 阶段）全部保留，本节只做路径扩充。

**动机（三个收益）**：① 去 AI 后绘制——G 阶段是串行管线的延迟大头（秒级/关键帧），全实时路径的表情与质感由着色器与资产直接产出，降至动画播放级；② 外部物理交互从容——"她坐椅子上，用户推椅子"：她挂在椅子锚点下，椅子位移 = 根运动，物理骨骼自动产生连续的二次运动；AI 重绘路径（每帧秒级 + 物理不连续）几乎做不到；③ 单帧物理效果——发、裙、手臂的惯性摆动是实时管线的免费赠品。

**实时赛璐璐硬阴影/高光的技术组合**（最难的部分已有成熟解法，四件套）：

| 部位 | 技术 | 说明 |
|---|---|---|
| 身体硬阴影 | **影法线编辑**（vertex normal editing） | Xrd 起源：阴影 terminator 由手调法线 + 阈值判定（非阴影贴图），"动画逻辑"的硬阴影；Blender EEVEE 复刻教程成熟（BlendAtlas 系列），与 R2 同栈 |
| 脸部硬阴影 | **SDF 面部阴影** | 原神/崩坏系标准：脸不用法线，SDF 距离场贴图 + 光向阈值比较，完全手绘感的脸影（Rembrandt 形/鼻侧形）；有手绘→SDF 烘焙工作流（ASP/Character shader bake 工具） |
| 明暗色 | **shadow ramp 色阶贴图** | 暗部颜色走 ramp 采样，色阶边界天然硬 |
| 头发高光 | **matcap 天使环** | 视角驱动的高光贴图采样 |

描边：反壳法（inverted hull）或深度/法线边缘检测后处理。

**表情（零 AI）**：VRM Expressions blendshape 预设（joy/angry/sorrow/fun/blink + 口型 A/I/U/E/O）；上限档为 Arc 系贴图换脸（脸部关键帧直接换贴图，最平面化）；辅以 Xrd 的脸朝向摄像机技巧。叙事侧的 `worldAction.expression` 直接映射到 blendshape/贴图索引——R2 里由 G 阶段 AI 重绘完成的环节，在 R3 是查表。

**物理**：VRM SpringBone（VRM 1.0 规范内建：springbone joints + collider groups）驱动发/裙/软体；推椅子机制 = 椅子锚点位移 → 她的根节点跟随 → SpringBone 惯性摆动自动发生；手臂可加简单摆锤约束。UE 侧对应 KawaiiPhysics（MIT 插件）。UniRig（2025，arXiv）代表自动绑骨 + 物理的后续方向。

**引擎落地**：VRM/MToon 是唯一跨引擎 toon 标准——Unity（UniVRM）、Web（`@pixiv/three-vrm` 全量移植 MToon）、Godot（V-Sekai 系移植），与 typ0 Web → AR 原生的多渲染器演进一致；Unity 强化档 = lilToon + SDF 脸 + ramp + matcap（或官方 Toon Shader/RealToon/Poiyomi）；Blender EEVEE = R2 sidecar 同栈实时化。galloscript GGXrdShading（WebGL）已证明 Xrd 级可在浏览器复刻——R2b 的"质感上限低"前提就此推翻。

**与 R2/R2b 的分工**：R2 保留离线高清（QQ 照片、立绘级大画面、厚涂氛围上限）；R3 承载连续在场（走动、被推椅子、眨眼、微表情、物理交互）。两档共存、契约不变——`rig spec` 之外 R3 只新增两个消费端字段（blendshape 索引、物理参数档位），求解层与空间状态层零改动。

**局限（诚实记录）**：厚涂笔触/材质细节/复杂光影氛围仍是 R2+AI 的强项，R3 上限是"主机动画观感"（Xrd 级）而非手绘厚涂；Xrd 级资产需要手调法线/ILM/贴图换脸的精修投入（VRM 生态有大量现成模型与工具链可借力，MToon 级开箱即用但更"3D 感"）；连续插值与 R2 的"有限动画/一拍二"作画节奏需在 R3 内重新设计折中（如常规连续、关键动作抽帧）。

### 6.3 G 阶段：AI 后绘制（串行第二段）

职责：在 3D 底帧之上**只做加法**——补少量风格化细节与面部表情，不改动几何、姿势、构图、描边走向与色阶结构。

```
底帧(赛璐璐+alpha) ──img2img 初值──┐
区域遮罩(脸/发/衣服) ──分区重绘强度──┼─► 绘图模型 ─► 后绘制帧 ─► 回贴 alpha ─► H 摄影合成
线稿/深度通道 ──ControlNet 锁构图──┘
```

- **分区重绘强度**：脸部区域高重绘（0.5–0.7，表情由 presenceState 的表情/情绪位驱动提示词——"3D 脸崩"问题在此终结，预制表情面片降级为 AI 不可用时的兜底）；发/衣服/皮肤低重绘（0.2–0.35，仅加笔触质感、发丝、布料纹样等高频细节）。
- **构图锁定**：底帧自身的线稿/深度通道作 ControlNet 条件——AI 拿到的既是初值又是约束，结构性偏移被双重锁死。
- **alpha 处理**：后绘制在纯色底上进行，完成后按原 alpha 边缘回贴，背景（真实房间）零改动；H 阶段再统一溶图。
- **一致性**：身份与几何由 3D 资产锁定，AI 只加可变的高频风格——跨帧脸不漂、形不崩由架构保证，D1 的角色参考图从"一致性必需"降级为"发肤纹理增强（可选）"。
- **触发与成本**：后绘制仅在**关键帧**触发（表情/姿势/灯光变化时）；hold 帧直接复用最近一次后绘制结果。单帧成本 = 一次分区 img2img，秒级。
- **表情语义来源**：presenceState 增加表情位（mood/expression），由剧本产出——她的表情和她的动作一样属于剧本事实，渲染层只执行。
- **加速器（few-step）**：G 阶段 img2img 用少步蒸馏模型——SDXL Turbo（对抗扩散蒸馏，1–4 步）或 Hyper-SD/Hyper-SDXL（ByteDance，1–8 步）——把单次后绘制从 20–30 步压到 1–8 步，配合本地 ComfyUI sidecar 可达亚秒级，这是 0.8–1 帧/s 上限（D12 裁定依据）的直接支撑；少步模型与厚涂风格 LoRA 的兼容性需实测。
- **脸部 pass 的可见性门控（只有脸部可见才生成）**：脸部高重绘 pass 仅在 `facing` 含正面分量（camera/left-profile/right-profile）**且**区域遮罩通道显示脸部未被遮挡层覆盖时执行——背面（away/back-*）或脸部被前景遮蔽的帧直接跳过脸部重绘，省一次生成。此模式即社区 FaceDetailer/ADetailer 范式（检测→裁剪→专用提示词重绘→回贴）的变体；我们的优势是**脸部 bbox/遮罩由 3D 头骨投影直接给出（F 阶段多通道输出），无需检测器**，且裁剪回贴的缩放锐度问题（bilinear 模糊）可用 3D 已知几何规避。
- **超轻平面化档（AnimeGAN）**：AnimeGAN v2/v3（GAN 单次前向、近实时、浏览器可跑）作为"整体画风平面化"的零成本档——把 3D 底帧快速压平成 2D 画感，无提示词控制、风格固定，适合 hold 帧的廉价刷新或低配设备；有提示词需求的正式档走 few-step img2img。
- **厚涂层（§6.0）**：暗部/材质区域的较高强度重绘 + 厚涂 LoRA；进阶实验档为 Stylized Neural Painting 式 stroke-based 笔触层（笔画序列可缓存复用——同一姿势的笔触参数化跨帧稳定，厚涂感比 diffusion 更"手绘"且完全确定）。

### 6.4 共通语义与端到端延迟预算

- **出画**：求解器返回 `off-screen` 时所有渲染器不产生帧，呈现层显示"她不在视野里"（对齐 EO Presence 视图"超出范围"语义）。她的离开本身来自剧本。
- **QQ 照片动作**：静帧走 R2 串行管线的离线高清渲染（含 AI 后绘制）；3D 资产就绪前以 R1 纯生成兜底。

**串行管线单关键帧延迟预算**（目标 ≤ 1.25s/帧，支撑 0.8 帧/s）：

| 段 | 预算 | 说明 |
|---|---|---|
| presence 提取（L1 随主调用/L3 钳制） | ~0 | 契约层 |
| 3D 段 Blender EEVEE 渲染（含多通道） | 0.2–0.5s | 单帧单 GPU；M0 程序化层在同场景内 |
| G 阶段 few-step 后绘制（1–8 步） | 0.3–0.8s | 脸部 pass + 低重绘全域 pass；本地 sidecar；云路由时 +网络往返 |
| H 摄影合成（§7.1 实时摄影层，每显示帧） | <50ms/帧 | 逐像素 shader（环境光比值 + N·L + 接触阴影缩放）；关键帧时的烘焙部分见 §7.2 |
| 补间帧（运动段） | 0.2–0.5s/帧（批量） | 仅 Blender，不上 AI；8–12 fps 显示（§6.5 两层帧率） |
| 合计（关键帧） | **0.6–1.4s** | hold 帧复用为 0；hold 期间显示上一帧；运动段显示补间层 |

### 6.5 动作连贯性：纯关键帧展示的抽帧编排（已按维护者意向裁定方向）

**方向：只显示关键帧，接受抽帧观感**——连贯性不靠加帧，靠编排可读性。

**感知前提（诚实边界）**：真正的运动感知（apparent motion）需要 ≥5–10 fps——0.8 帧/s 下人眼不可能把相邻帧融合成连续运动。因此连贯性来自**相邻帧对的可补完性**（漫画分镜闭帧理论，McCloud）：相邻帧构成 moment-to-moment / action-to-action 过渡时观众脑内自动补完；跳跃过大只能读作剪辑（cut——合法，动画本就如此）。观感参照系：活的相册 / 纸芝居 / 极低帧定格。

**编排规则（落入求解器与 L3，可实现）**：

| 规则 | 内容 | 实现点 |
|---|---|---|
| R1 一帧一拍 | 每个关键帧只推进**一个可读动作节拍**（头转/手放/重心移）；禁止合并节拍——"起身并走两步"拆为前倾→起身→迈步三帧 | 求解器输出粒度 + L3 校验 |
| R2 动漫时间缩放 | presence 事件间距 ≥ 1.25s/拍——她生活在定格时间（起身 4–6 帧 = 现实 5–8s，优雅的慢）；**大位移不快放，直接 CUT**（桌边→窗边 = 剪辑跳帧） | L3 按节拍包络裁决"节拍序列 or cut" |
| R3 连续性包络（硬规则） | 朝向 ≤45°/帧（一档）；锚点 ≤一步/帧；sit↔stand 必经前倾帧（anticipation 是连续性必需品，非风格加分）；持物不无故消失（杯在手→杯在桌必经"放下"帧或 cut） | L3 钳制 |
| R4 关键帧采样器 | M-gen 骨架流中**选帧**：极值姿势（动作最高/最低点）与接触时刻（手触桌、脚落地瞬间）优先成为关键帧——动画师选关键张的算法化；采样间距强制节拍包络 | 求解器 |
| R5 显示侧微活（可选） | hold 的 1.25s 内贴片做 1–2px 呼吸式微缩放/微摆（显示端 transform，零生成成本）——画面"活"而不加帧 | 合成器 |

姿势库条目的 anticipation（前倾帧）与 follow-through（手悬停帧）设计在 R1/R3 下从美学原则升级为**连续性必需品**。

**帧率演进**：管线提速到 2–4 帧/s（few-step/批量改进）时 apparent motion 开始成立，上述规则无害退化（包络仍防止跳变）；5+ 帧/s 后 R2 的时间缩放自然放松。补间层方案（Blender 未上色中割，运动遮蔽掩护）降级为**可选增强档**，非默认路线（维护者 2026-10-05 裁定：默认纯关键帧）。策略选项保留见 D16。

### 6.6 物件交互：她的道具（笔记本、笔、杯子……）

**答案架构 = 脸部方案的第三次复用：3D 给结构，AI 给外观，参考图给身份。** 四层：

| 层 | 机制 | 说明 |
|---|---|---|
| 几何层：socket 挂接代理 | 每个物件有**代理模型**（素几何体即可：圆柱=杯、扁盒=笔记本）挂到骨骼挂点（socket，游戏引擎标准做法；VRChat avatar 道具 toggle / MMD .vac 附件同款生态）。姿势库条目声明 `requiredProps`（写字姿势 ⇒ 笔+笔记本），L3 钳制层校验装配。代理随 A–F 渲染进底帧——**接触、握持、遮挡、深度全部由 3D 保证**，跨帧绝对稳定（杯子不会每帧变形） | 3D 段 |
| 外观层：物件区域精绘 | F 阶段材质 ID 通道把每个物件输出为独立区域遮罩（同脸/发/衣服机制）；G 阶段按物件区域做**参考图驱动的重绘**——AnyDoor/Paint-by-Example/OmniGen 类对象级参考插入模型（零样本：物件参考图 → 插入画面且保持身份细节）。代理给"在哪、多大、被什么挡"，AI 给"长什么样" | G 阶段 |
| 身份层：物件注册表 + 一次性设计 | 副本环境物品表（EO 设计中她的物件本就是叙事事实）：`{objectId, label, proxyAsset, referenceImage, sockets, stateVariants（笔记本开/合、杯满/空）}`。**设计一次性生成并锁定**：新物件经剧本诞生（"她买了只新杯子"）→ R1 按叙事描述生成物件设定图 → 锁定为 canonical 参考图 → 此后所有帧用它精绘（身份跨帧稳定）。用户可自定义初始物件（EO 开放问题 3 的延伸） | 叙事 + 一次性生成 |
| 语义层：姿势声明 | 动作描述中的物件动词（写字/喝水/合上笔记本）经 L1/L2 映射到姿势+道具组合，L3 校验"姿势需要笔+本 → 装配代理"；物件状态变化（翻页、放下杯子）= 叙事事件 → 代理变体切换或新关键帧 | L1–L3 |

边界：软体交互（液体倾倒、纸张翻飞）首版不做——用姿势库帧级表现替代（拿杯倾斜的姿势代替液体模拟）；AnyDoor 类模型对小物件（杯/笔尺寸）效果最佳，正合场景。策略选择见决策点 D15。

## 7. 光影与溶图配方（L4）：生成时烘焙 + 显示时实时重光照

**动机（"关灯发光"问题）**：若光照烤进生成帧的像素，环境光变化（关灯/开灯/天色）时帧不变——她会在暗房间里"发光"。解法是把**内容更新（0.8 fps，贵）与光照适应（显示帧率，便宜）分离**：帧在参考光照下烘焙，显示时按实时环境光重光照。这也是传统动画撮影的本体结构——赛璐璐片不带环境光，光是摄影台的滤镜层。

### 7.1 实时摄影层（每显示帧，快层，~免费的逐像素 shader 运算）

技术路线为 **2D 精灵法线动态光照**（Unity Light2D / Godot 2.5D 标准；社区有完整工具生态）——且本系统相对游戏开发者的决定性优势：**法线通道从 3D 渲染直接输出，真实且免费**（游戏需手绘/算法生成精灵法线）。

1. **环境光比值适应**：从 L0 实时采样环境亮度/色温（校准 ambientSamples 点位在当前相机帧上的采样值）→ 计算与参考光照（生成时快照）的比值 → 乘到绘制帧。关灯=比值下降=她同步变暗，即时且平滑——光强/色温变化（最常见情形）纯乘法完美处理；
2. **方向光 N·L ramp**：法线通道 + 当前主光方向（校准 keyLight，方向基本恒定）做柔和的方向性明暗；色阶边界来自影法线几何，不随光强变化；
3. **接触阴影**：位置/形状生成时定（几何性），**强度随环境光比值缩放**（显示时）；
4. **边缘熔接**：羽化 + 颗粒匹配，恒定项；
5. **接触平面反光**（可选）：桌面亮斑随环境光缩放。

### 7.2 关键帧烘焙层（0.8 fps，慢层）

- G 阶段的**参考光照 = 生成时刻的实时环境光采样**（不是校准时的旧值）——绘制帧天然与生成瞬间一致，Tier 1 只需覆盖其后的漂移；
- **剧变档（Tier 3，可选，即原 D3 高阶档）**：光照差超出乘法合理范围时（全黑场景需暗部反光色彩），IC-Light 在关键帧节奏对绘制帧重打光。

配方分层的成本结论：实时层为逐像素 shader 运算（GPU 微秒级/帧，或固定机位分辨率下 CPU 亦可承受）——"溶图实时化"不构成算力问题。

## 8. 帧循环、触发权与呈现

### 8.1 帧循环

- 事件源：ScriptCommit 新场景/活动变化、校准变更、用户打开 Presence 面、可见性事件（不可见→可见，见 §8.4）；（定时心跳作为兜底，见 D8）。立牌语义下用户视角变化不触发重生成——新朝向随下一次叙事关键帧自然发生；
- 前置门控：当前可见性状态为"不可见"时串行管线整体跳过（§8.4——不可见时段零渲染成本）；
- 节流：最小重生成间隔（建议默认 60s）+ 每日生成预算（成本护栏）+ 去重（presenceState 未变化不重生成）；
- 生命周期：人物帧为临时资产（缓存 TTL + 数量上限），保留策略对齐 EO 的 L1/L2 边界（§10）。

### 8.2 触发权（决策点 D6）

呈现行为遵守元主体性：生成请求由剧本侧（她的活动/意图）驱动为主；用户请求可见性时以"用户看向 Presence 面板/发出请求"为叙事事件进入剧本，由她决定回应与否。候选强度分级见 §9。

### 8.3 呈现场所（决策点 D5）

- **Presence 面板**（typ0）：摄像头预览 + 合成帧的主场所，即 EO §7.4 的实现；
- **QQ 照片动作**（变体）：她以 `character-platform-action` 发送"她拍下的瞬间"（合成帧经 CQ:image file:// 本地路径投递——与贴纸投递同一通路），触发权完全在她；
- **独立悬浮窗**：低频桌面伴随形态（不需要摄像头持续预览，用校准快照做背景）。

### 8.4 可见性判定与渲染门控

**原则：可见性只门控绘制，永不门控存在。** 她的行为、位置与剧本推进不依赖用户是否看见她——观察者效应为零（单向窥视原则的延续）。可见性判定因此纯属快层（渲染侧）关注点。

**三态状态机**（对齐 EO Presence 视图的"可见 / 超出范围 / 暂时未知"）：

| 状态 | 判定 | 渲染行为 |
|---|---|---|
| 可见 | 锚点在视锥内 **且** 视线射线未被场景几何遮挡 | 正常渲染（billboard 贴片，深度遮挡逐帧裁剪） |
| 不可见 | 视锥外，或视线被墙/地板/家具遮挡 | **不绘制**——她继续存在与生活，串行管线整体跳过（零渲染成本）；Presence 面板显示"超出范围" |
| 暂时未知 | 场景几何缺失（AR 重建空洞/未扫描区域） | AR 阶段保守**渲染**：贴片交给设备逐帧深度遮挡裁剪，让真实几何决定可见性（宁可画了被裁，不可错杀）；typ0 阶段按超出范围处理 |

**判定实现分阶段**：

- **typ0（固定机位）**：可见性 = 锚点在校准画布内 + 未被 L1 静态遮挡多边形完全遮蔽。她的活动空间本就以摄像头覆盖范围为界（EO 设计），"她在厨房"这类画外位置以"超出范围"状态存在——判定退化为廉价 2D 检查。
- **AR / SV4**：设备场景网格（ARKit scene geometry / Quest 空间扫描）+ 相机位姿 → 视锥判定 + **射线遮挡判定**（从相机到她锚点 raycast 场景网格）。此计算在设备侧高频进行（快层）；宿主只接收低频**可见性事件**（可见↔不可见↔未知 + 当前视角上下文），作为串行管线的关键帧生成门控之一。

**用户场景的几何消解**（无需特判，几何自动给出答案）：

- *她下楼了，用户在楼上看*：视线射线过楼梯井栏杆 → 可见（部分可见由设备深度遮挡像素级裁剪，栏杆自然挡住她半身）；射线被地板挡住 → 不可见。两种结果都对——用户探头看向楼梯井时几何自己会切换状态。
- *隔得很近但不在一个房间*：射线被墙挡住 → 不可见，无绘制参考也无需参考。"她就在隔壁"的临场感由叙事承载：剧本知道她的位置，用户能问她——渲染层不越权。

**关键帧朝向：固定贴片（立牌语义，已裁定方向）**：人物帧不是永远正对用户的追踪贴片，而是一块**在生成时刻朝向当时观察者位置摆好的竖直牌子**。画面透视（她以什么角度被看见）在生成时由当时的相机位姿求出并画进帧里；牌子本身立在 3D 空间固定不动。两帧之间用户的走动 = 绕着一块真实立牌走——视角变化不触发任何重渲染；下一次叙事关键帧自然朝向用户此刻的位置。此模型将成本控制与用户行为完全解耦（只随叙事节奏走），且每一帧画的都是"生成那一刻观察者真实看到的她"——帧与观察历史绑定，比库存视角更叙事正确。渲染延迟期间（管线 2–10s）用户走动按立牌语义直接接受（牌子朝向发出请求时的位置，下一帧自然纠正）。牌面恒为竖直：透视活在画里，牌子只是画布。从背面观看的行为见决策点 D12。typ0 固定机位阶段此语义自动退化为现状（相机固定 = 牌子永远朝向校准机位）。

**防闪烁滞后**：可见性切换加宽限期（1–2s 或头部角速度感知的动态宽限）——用户快速转头时贴片不闪烁；宽限期后状态切换生效。她的消失不渐隐（直接切走），符合作画切换的干脆感。

## 12. 可行路径（非冻结式）

本节只描述从叙事状态到空间显形的依赖关系，不构成版本计划、PR 排期或接口冻结。此前讨论过的 PR、T1–T6 等编号可以作为历史工作笔记保留，但不应被理解为必须按顺序交付的工程承诺；§9 决策点与 §17 缺口清单中残留的 PR 编号引用（如"PR-2R 前需协议草图"）一律按此历史笔记理解，指依赖顺序而非交付排期。

### 12.1 叙事与状态路径

首先需要能够回答“她为什么在这里、正在做什么、这个状态还能持续多久”。可行的方向包括：

- 从 ScriptCommit、Scene、Arc、Agency、Urge 和当前潜流中读取 Presence 所需的状态；
- 将位置、朝向、姿态、可见性、持物和活动意图作为可重建的派生表达；
- 为在场状态保留来源、有效期和失效条件，方便切面、断线、重启和回放；
- 允许一个状态只停留在潜流或候选事件中，不要求所有视觉表现都成为长期剧本事实。

### 12.2 空间与合成路径

空间部分可以从最小的固定机位开始：

- 手动校准摄像头、锚点、遮挡区域和光照参考；
- 使用有限姿态与有限动作库验证空间存在、接触阴影、遮挡和出画；
- 再逐步增加自动校准、动态遮挡、环境色采样和更多机位；
- 最后将同一套锚点、姿态、可见性和事件语义迁移到 3D billboard 或 AR 原生渲染。

### 12.3 生成与渲染路径

人物生成不必一开始就追求连续高帧率。一个可行的组合是：

- 确定性渲染负责几何、姿势、构图、遮挡和光影结构；
- AI 后绘制负责表情、笔触、材质和局部风格化细节；
- 关键帧由叙事事件或在场状态变化触发；
- 稳定状态由本地重放、hold 帧和轻量动作补间维持；
- 当绘图、Blender、摄像头或网络不可用时，退化为静态帧、简单占位、文字描述或暂不可见。

### 12.4 HNSU Agency Core 的接入路径

Presence 可以先作为 HNSU Agency Core 的输出端，消费已有的在场事件；之后再让观察窗口和用户在场行为成为 Agency Core 的实时上下文。其基本方向是：

```text
共享叙事状态 / 环境观察
          ↓
HNSU Agency Core 的短时判断与事件编排
          ↓
Presence / Voice / Motion / IM 输出
          ↓
可选的候选经验回流 HDSI Narrative Core
```

回流的目的，是让主叙事有机会理解“她刚刚经历了什么”，而不是让一个动作或一帧画面直接改写长期剧本。

### 12.5 从 typ0 到 AR 的迁移思路

typ0 的固定摄像头和平面合成、桌面在场视图、视频预览和未来的 AR billboard 可以共享同一套高层契约：

```text
角色叙事状态 → 在场事件 → 锚点 / 姿态 / 可见性 → 具体渲染器
```

这样，未来更换显示设备时，迁移的是快层和校准方式，而不是重新发明角色的行为逻辑。最终是否采用 Blender、WebGL、设备原生渲染或混合方式，可以由实际质量、延迟和成本决定。

## 15. 潜流（Undercurrent，原概念名 Agency Core）概念与联动

> 定名已裁定（2026-10-05）：**潜流 / Undercurrent**；产品化名称 **HNS-Undercurrent（HNSU，Hyperrealistic Narrative System）**——系统整体（原 typ0 壳，更名承袭"零号"血统）的及时性子模式；对话子模式为 HDSI。双子结构与面切换（Surface Handoff）设计详见 `SV34_AGENCY_CORE_VISION.md` §0。

### 15.1 概念

主叙事（ScriptCommit）以粗节拍书写她的故事——分钟级的事件、对话、剧情。**潜流是事件之间持续存在的微叙事流**：秒级/亚秒级的存在细节——微动作、视线、表情、位置漂移、意图前兆。一句话分工：**主叙事写"她做了什么"，潜流写"她正在怎样地存在"。**

架构上它是**双层写作节奏**的下半层：不是第二个叙事模型重写故事，而是存在流的生成器——不产生剧情，只产生节拍之间的生命感。

### 15.2 四条约束的架构回应

| 约束 | 回应 |
|---|---|
| 叙事化 | 潜流输出是微型写作（token 流），与主叙事同源（写作而非模拟）——只是粒度与频率不同 |
| 高度及时性 / 频繁更新 | token 流式：接口要求 #1（统一模型交错输出 text+motion tokens，IRG-MotionLLM 形态）；意图先行：接口要求 #2（意图 token 先于行动 token，给渲染层前瞻窗口） |
| 低成本 | ① 微叙事≠文学性——1–8B 本地小模型可胜任；② **默认零账本写入**（输出为临时流，无 DB 写、无压缩成本）——接口要求 #3：提升（promotion）是唯一持久化路径；③ 事件驱动 + 低频心跳，闲时只有 M0 程序化层 |

### 15.3 与既有系统的关系

- **urge 系统是它的前身**：urge 回答"何时主动联系"，潜流回答"事件之间如何持续存在"——同一元主体性谱系的扩展；
- **ScriptCommit 仍是唯一持久真相**：潜流是派生/临时层；主叙事提交时可引用潜流时刻提升为剧本事实（promotion），也可忽略；
- **和解规则：主叙事永远赢**——冲突时潜流重放/丢弃（渲染是派生层，和解廉价）；
- **双向但单向写入**：潜流 → 主叙事的上下文摘要（提交前主模型可读近期潜流摘要，使粗节拍与身体已做的事对齐）；主叙事 → 潜流的重置/锚定。

### 15.4 与呈现系统的联动（§5.1 L4 的具体化）

motionTrack 高频直填（微动作/骨架流）、表情位、微位置漂移、意图事件（预渲染前瞻窗口）。潜流节拍输出天然满足 §6.5 节拍包络（R1–R3）——它生来就是一拍一输出的。

在动作帧模型（§18–19）下，潜流呈双层形态（详 SV34 §13.3C）：已播出的动作帧序列是它的**演出层表达**，低频剧作准备层整理的注记是它的**势能层沉淀**——后者与 HDSI 已灰度验证的 Narrative Attractor（长线指导）架构同构，两模式可复用同一套"指导生成与注入"基建。

### 15.5 可行演进方向

- **纯文本潜流**：以微动作描述、短时意图或状态提示作为起点，再由求解器映射为节拍帧，小模型即可参与；
- **motion tokens 或其它结构化事件**：在实时性和模型能力允许时，让文本、动作、表情和空间意图以更紧密的方式共同表达。

两种形式可以长期并存，由不同设备、模型能力和成本档位选择；它们不是固定的版本定义。

### 15.6 命名（已裁定）

**潜流 / Undercurrent**（2026-10-05）。理由记录：主叙事事件是浪，它是水下持续存在的流——名字自带"事件之间的存在"语义，与"幕间 Interlude"气质同源；中英双语顺口，工程语境 "undercurrent stream" 自然。产品化名称 HNS-Undercurrent（HNSU）。typ0 壳后续更名为系统整体名（承袭伊人制造"零号"血统）。

### 15.7 双子模式与面切换（Surface Handoff）

系统整体下辖两个可切换子模式：**HDSI**（对话面：主叙事 + 消息投递）与 **HNSU**（在场面：同一主叙事 + 潜流 + 呈现层）。无缝切换的架构根基是**一个账本两个面**——持久叙事真相（ScriptCommit 账本）唯一共享，切换只做三件事：账本零迁移、派生状态重建（本设计的校准/presence/渲染缓存皆为派生层，秒级重建）、叙事衔接（潜流从当前状态起流，她知道手机上聊过一切，因为同一本账）。在外面时她在家的存在仍由主叙事自动推进（HNSU 停的只是渲染不是存在）；回家戴上 AR，看到的就是她此刻正在做的事。完整设计与场景见 `SV34_AGENCY_CORE_VISION.md` §0/§0.1。

## 16. HNSU Agency Core、Presence 与叙事回流

### 16.0 职责关系（权威定义见 SV34 §0.2，本节为技术实现细化）

Presence 是 HNSU 在场面的显形系统，Agency Core 是 HNSU 在场模式中的实时行为与事件编排层，两者都不取代 HDSI 的 Narrative Core。**职责层级的权威定义见 `SV34_AGENCY_CORE_VISION.md` §0.2**（HDSI Narrative Core ↔ HNSU Agency Core → Presence / Voice / Motion / IM Event，含事件回流方向与"长期事实回归共享账本"的边界规则）；本节不重复维护层级图，只细化 Presence 侧的技术要求。

Agency Core 可以让角色在 HNSU 中抬头、停顿、转向、等待、继续手里的事，或者对当前环境作出短暂回应。Presence 负责把这些状态变成空间中的视觉表现；它不应因为自己完成了一次渲染，就自动创造新的角色事实。

这意味着 Presence 事件最好能够保留“为什么出现”的来源关系，例如关联到当前的 ScriptCommit、潜流片段、观察窗口或 HNSU Agency Event，并拥有合适的有效时间。这里的来源、有效期和可回放性是为了支持调试、切面、断线和重建，不是为了把渲染器变成另一套知识库。

### 16.1 在场状态的可逆性与叙事回流

Presence 的短时状态可以有不同的命运：

- 只在当前窗口中存在，过期后自然消失；
- 作为潜流的一部分被继续维持，但仍然属于派生状态；
- 被 HNSU Agency Core 组合成一个候选事件，等待主叙事理解；
- 经 HDSI Narrative Core 重新写作后，成为可持续的剧本事实；
- 与当前叙事冲突时被重置、替换或丢弃。

因此，合理的回流方向是：

```text
ScriptCommit / 当前叙事状态 → Agency Core → Presence
观察 / 在场经验 → 候选事件或上下文 → HDSI Narrative Core（可选）
```

而不是：

```text
Presence 画面 → 自动改写角色性格或长期剧本
```

这使得“她现在看起来正在做什么”和“她以后会记得自己做过什么”可以保持联系，但不必被强行视为同一件事。

### 16.2 非冻结式的可行路径

Presence 的发展可以沿着以下几条相互配合的方向推进：

1. **先验证在场语义，再提高画面质量**：先用静态帧、有限姿态和简单光影确认用户能否理解她的空间存在，再逐渐引入 Blender、后绘制和更复杂的材质；
2. **先使用可重放的状态，再追求实时生成**：动作、停顿、视线和姿态可以先由本地状态机或短动作片段表达，模型负责较低频的选择与改写；
3. **先固定叙事来源，再扩展观察来源**：渲染系统首先消费 ScriptCommit、Scene、Arc 和当前潜流，之后再把环境观察和 HNSU Agency Event 接入同一个来源链；
4. **先保证降级仍然成立**：模型、Blender、摄像头或网络不可用时，系统仍应能回到文字、静态 Presence、低频动作或“暂不可见”的叙事状态；
5. **最后再将同一契约迁移到 AR**：typ0 的二维合成、桌面在场和 AR billboard 不必拥有不同的角色逻辑，它们只需要共享锚点、姿态、可见性和事件来源语义。

这些方向描述的是从叙事存在到空间显形的可行路径，不预设最终的渲染器、帧率、模型供应商或具体版本。

## 18. 最新技术实现澄清：Presence 作为 Agency Action Frame 的显形层（2026-10-05）

本节不删除前文任何渲染路线、决策点、历史设计或开放问题，仅补充 HNSU 在场系统与最新 Agency Core 模型之间的技术边界。

### 18.1 Presence 不产生行为，只显现动作帧

在 HNSU 的最新模型中，Presence 不是独立的行为决策器，也不是把一个抽象意图继续拆解成若干低级动作的代理层。它接收一次 Agency Core 调用生成的 **Agency Action Frame（在场动作帧）**，并负责将这一个动作帧呈现为：

- 姿态、视线、表情和活动状态；
- 语音、文字、音画同步和动作时长；
- 光影、遮挡、合成、空间锚定与设备适配；
- 失败降级、播放状态回报和动作完成标记。

渲染器可以为了设备能力进行插值、补帧和技术性过渡，但这些不是新的叙事行为。任何会改变角色意图、目标或剧情方向的动作，都必须来自新的 Agency Core 调用。

### 18.2 一次 Agency Core 调用直接对应一次动作帧

HNSU 的基本呈现链路是：

```text
用户视角观察
    ↓
Agency Core（快速叙事模型）
    ↓
极短剧本片段 + 一个 Agency Action Frame
    ↓
Presence / Voice / World Action 呈现
    ↓
动作后用户视角捕获
```

这里不再预设“Agency Scenelet → 若干低级动作 → 执行器”的必要层级。一次调用可以描述一个完整而短促的在场节拍，例如“停下手上的事、抬头、看向用户并说一句话”，呈现层将其作为一个动作帧处理。动作内部是否包含渲染所需的姿态插值、骨骼过渡或音频播放片段，属于演出实现，不构成新的叙事决策。

### 18.3 动作帧的建议记录

为了让呈现可回放、可中断、可恢复，Presence 记录动作帧的来源与生命周期信息；**字段定义以 §19.3 为本文档权威版**（含 `posture`（与 rig spec 的 PostureId 同族，不用 pose）、`spatialAnchor` 与 `failed` 状态）。这些字段仍是技术实现建议，不冻结接口。

`worldAction` 是叙事片段的结构化演出投影，而不是一个可以脱离 `narrative` 独立运行的行动计划。`status` 用于记录呈现事实，供下一次叙事理解上一帧发生了什么；它不应被误解为 Presence 可以自行推进剧情。

### 18.4 用户视角是呈现之后的叙事材料

在 AR 路径中，每次动作帧呈现后，可以捕获一张用户视角图片，并与结构化场景数据、动作状态和前一帧引用一同交给下一次 Agency Core。图片中允许包含 bot 自身的 Presence：模型被明确告知这是用户的视角，画面中的 bot 是叙事主体自身的上一帧显形。

因此 Presence 的闭环不是“渲染结果必须被模型隔离”，而是：

```text
Agency Action Frame
    ↓
用户看到的 Presence
    ↓
动作后用户视角图片
    ↓
下一次叙事续写
```

这使得动作的姿态、视线、距离、遮挡和光照可以在下一帧继续影响剧本，并帮助角色行为保持连贯。

### 18.5 与现有渲染路线的兼容性

本模型不否定现有 R1、R2、R2b、G、L4 等路线。无论使用生成帧、三渲二、WebGL NPR 或 AI 后绘制，渲染器都可以作为同一个动作帧的不同显形实现：

- Agency Core 决定这一帧叙事上发生什么；
- Presence 选择在当前设备上如何显示；
- 渲染器可以根据能力做降级，但不能把降级扩写成新的剧情；
- 动作结束后的用户视角再进入下一次 Agency Core，而不是由渲染器自己生成下一帧行为。

### 18.6 不冻结的技术验证方向

1. 先在现有 typ0 固定机位中把一帧动作完整呈现出来，验证动作帧来源、状态回报和用户视角回流；
2. 用多种渲染器播放同一个动作帧，验证叙事语义与视觉风格解耦；
3. 测试中断、动作失败、设备不可用时，是否能把真实呈现结果交给下一次 Agency Core，而不是伪造“动作已完成”；
4. 在 AR 场景中用动作后单帧捕获代替持续视频作为默认闭环，再按需要增加可选的短窗口观察；
5. 保留现有渲染路线作为实验空间，不把本节建议提前固化成最终协议或版本阶段。

本节补充的是职责关系与实现方向，不替换前文的设计路线。

## 19. 概念一致性补充：Presence 显现的是一帧剧本动作（技术路径，不删改前文）

> 本节只补充 Agency Core、动作帧、用户视角回传之间的职责关系，不删除前文的渲染器家族、慢快分层、空间锚定、遮挡、光影、R1/R2/R2b 或 AR 迁移路线。前文提出的多种实现仍可作为实验分支。

### 19.1 不把 Agency Scenelet 拆成叙事上的低级动作链

Presence 的上游最小契约可以统一称为 `Agency Action Frame`。一次 Agency Core 调用放出一帧动作，渲染层可以在这一帧内部执行骨骼插值、口型同步、音频播放和视觉过渡，但这些是同一帧的演出实现，不是新的剧情决策。

```text
Agency Narrative Core
        ↓
极短剧本片段 + Agency Action Frame
        ↓
Presence / Voice / World Action
        ↓
动作后用户视角捕获
```

因此，Presence 不需要依赖“一个 Scenelet 再拆成若干低级动作”的固定结构。若历史章节使用 `Agency Scenelet` 一词，可以把它理解为叙事描述或实验性容器；在当前技术路径中，真正交给呈现层的最小可执行叙事单位是一帧动作。

### 19.2 渲染层是 Narrative Realization Layer，不是剧情控制器

Presence 层应负责把已有动作帧可靠地显现为人物帧、姿态、表情、视线、声音、光影、遮挡和设备事件。它可以进行确定性校验、能力协商和降级，例如将不支持的空间效果改为二维合成，或在设备不可用时报告失败；但它不能自行决定角色为什么停下、为什么靠近、为什么说话，也不能在动作帧结束后自动生成下一帧剧情。

```text
narrative       = 动作发生的剧本原因与即时描写
worldAction     = 剧本动作的结构化投影
renderer        = 对这一帧进行可靠显现
```

如果需要在代码中设置接口边界，建议使用 `Narrative Realization Layer`、`World Action Projection Layer` 或 `Frame Renderer` 等名称，避免 `Intent Executor` 让人误解为叙事外置。

### 19.3 一帧动作的结构化呈现契约

以下结构是技术路径示意，不冻结最终接口：

```ts
type AgencyActionFrame = {
  frameId: string
  previousFrameId?: string
  narrative: {
    perspective: 'narrator'
    text: string
    continuity?: string
  }
  worldAction: {
    activity?: string
    posture?: string
    gaze?: string
    expression?: string
    voice?: string
    spatialAnchor?: string
  }
  durationMs?: number
  viewCaptureAfter?: boolean
  status?: 'generated' | 'presented' | 'captured' | 'closed' | 'interrupted' | 'failed'
}
```

`worldAction` 不是另一条自主行动链，而是为设备、渲染器和观察回传提供稳定字段。`status` 记录真实呈现事实，让下一次 Agency Core 知道上一帧是否完成；它不能被渲染器用来自动推进不存在于剧本中的后续行为。

**与潜流（§15）的衔接**：动作帧流即潜流的离散化表达——Agency Core 逐帧输出的极短剧本就是"事件之间持续存在"的具体形态，§15 的接口要求 #1（交错 text+motion tokens）在此具体化为 narrative+worldAction 的成对输出。**worldAction 是 rig spec 的上游契约**：HNSU 模式下，presence 求解器的输入从 §5.1 的 L1/L2 presence 映射切换为 `AgencyActionFrame.worldAction`（activity/posture/gaze/expression → PostureId/Facing/mood；spatialAnchor → anchorId），motionTrack 消费其动作序列；§5.1 的 L1–L3 分层保留给 HDSI 模式（无 Agency Core 时）作为来源层。

### 19.4 Presence 可以进入用户视角并参与连续性

在 AR 或固定机位合成中，动作后用户视角可以包含 bot 的 Presence。模型收到图片时应被告知：这是用户的相机视角，图片中的 bot 是上一帧动作的显形，Agency Core 以叙事者身份理解这一关系。

因此不必强制拆分“没有 bot 的 raw image”和“合成后的 composited image”，也不应为了规避假想中的反馈污染而移除 bot。Presence 的位置、姿态、视线、遮挡和光照正是下一帧动作保持连贯的重要视觉材料。`viewSemantics` 可作为辅助元数据，但只表达视角语义，不限制模型使用画面。

### 19.5 动作后用户视角是 Presence 的下一步输入

Presence 的闭环可以表达为：

```text
Agency Action Frame
        ↓
Presence / Voice / World Action 呈现
        ↓
用户看到的动作后视角
        ↓
图片 + 结构化场景数据 + 呈现状态
        ↓
下一次 Agency Narrative Core
```

持续视频、短窗口、关键帧和视频模型仍可按需作为增强材料，但 HNSU 的最小闭环只要求动作后用户视角的单帧捕获。这使渲染技术可以独立演进，同时保留角色“活在用户可见视角中”的剧本拟真。

### 19.6 对现有渲染路线的兼容方式

R1、R2、R2b、AI 后绘制、WebGL NPR、AR billboard 等路线都可以实现同一个 `Agency Action Frame`。它们之间的差异只在“这一帧如何被显现”，而不在“下一帧剧情由谁决定”：

- 慢层可以根据动作帧生成或更新角色图像、姿态和材质细节；
- 快层可以进行定位、遮挡、光影、合成和设备适配；
- 如果显现失败，呈现层回报事实，下一次叙事决定如何解释；
- 渲染器不应因为插值或降级而创造额外剧情。

本节与前文的所有视觉、灯光、空间锚定和设备迁移设计并列存在，只是为上游叙事与下游显现划清职责。

## 20. Agency Core 低延迟路径对 Presence 呈现的补充

> 本节仅补充与 Agency Core 低延迟结构相配套的呈现侧思路，不删除前文任何渲染器、空间锚定、光影、遮挡、慢层 / 快层或 AR 迁移设计。Agency Core 的具体路径比较见 `SV34_AGENCY_CORE_VISION.md` 的相关新增章节。

### 20.1 呈现侧不再引入逐帧模型往返

收到一个 `Agency Action Frame` 后，Presence 层应尽可能直接进行字段校验、资源选择、能力适配和呈现，不再默认追加一个“动作解释模型”或“动作审核模型”。这有助于保持：

```text
一次 Agency Core 调用
        ↓
一个动作帧
        ↓
一次确定性显现
```

渲染资源预热、角色资产索引、设备能力读取和可复用的视觉资源准备，可以在动作帧生成之前进行；但它们不应创造新的叙事动作。若动作帧无法完整呈现，Presence 层记录真实的降级、失败或中断状态，交给下一次 Agency Core 解释。

### 20.2 低延迟优化的边界

Presence 侧可优化资源加载、图像合成、姿态插值、语音播放准备、遮挡计算和设备通信，但不能通过“为了流畅而自动补动作”的方式掩盖 Agency Core 没有生成的剧情。动画内部的插值不等于多次 Agency 调用，也不需要额外的叙事模型审批。

因此，Agency Core 的低延迟与 Presence 的低延迟应分别测量：前者关注观察材料就绪到动作帧可用，后者关注动作帧可用到第一帧显现及完整呈现。两者都应记录实际失败和中断，而不是只记录最终画面是否出现。
