## 0. 概念命名、愿景坐标与系统结构（2026-10-05 记录）

**概念定名：潜流（Undercurrent）**——本文以下正文的"Agency Core"即此概念的历史名称。

**愿景坐标（SV ladder）**：

| SV | 内容 | 对应 |
|---|---|---|
| SV1 | HDSI 0.x.x 内核（历史） | 0.x 发布线 |
| SV2 | HDSI 1.x.x 内核（**当前**） | 1.0.1-rc 线 |
| SV3 | **HDSI 整体稳定性、功能附加、架构拓展性 + HNSU 初步实现** | typ0 固定机位、Presence 与潜流的早期探索 |
| SV4 | **HNSU 的构建、验证与稳定** | AR / billboard 迁移、面切换和更丰富的在场事件探索 |

SV3/SV4 在本文中是帮助讨论成熟度和能力范围的愿景坐标，而不是发布承诺、硬件代称或必须按顺序执行的工程阶段。§2 的演进路径只表达能力之间的依赖关系，不代表固定排期。

**系统命名结构**：

```
系统整体（原 typ0 桌面壳，更名承袭——"typ0"之 0 源自伊人制造"零号"血统）
├─ 子模式 A：HDS-Interlude（HDSI）——专注对话系统（消息面）
└─ 子模式 B：HNS-Undercurrent（HNSU，Hyperrealistic Narrative System）——专注及时性（在场面，潜流的原生表达）
```

两个子模式可切换使用；**剧本化同源**——见 §0.1。

### 0.1 面切换（Surface Handoff）：一个账本，两个面

HDSI 与 HNSU 不是两个系统，是**同一个持久叙事真相之上的两个表达面**：

| 层 | HDSI 面（对话面） | HNSU 面（在场面） |
|---|---|---|
| 持久叙事真相（共享，唯一） | ScriptCommit 剧本账本 + 角色/关系/事实/世界状态 | 同一个（零迁移、零同步——根本没有两个系统） |
| 表达层 | 主叙事 + 消息投递（debounce/延迟/主动联系——现有全部） | 同一个主叙事 + 潜流（微叙事流）+ 呈现层（presence 渲染管线） |
| 节奏 | 对话节拍（分钟级） | 存在节拍（秒级微叙事 + 关键帧呈现） |

**切换三件事**：

1. **账本零迁移**——同库同源，这就是"剧本化同源"的实现方式；
2. **派生状态重建**——校准加载、presence 求解、渲染缓存预热，全部是派生层（可重建，见呈现设计的数据生命周期与状态回流章节）；
3. **叙事衔接**——主叙事在切换点照常提交；潜流从当前状态起流；她"知道"手机上聊过什么，因为同一本账。

**体验语义**：切换不是"传送她"，是"改变你能看见她的方式"。用户在外面用手机时，她在家里的存在仍由主叙事自动推进书写（HNSU 停止的只是渲染，不是存在）；回家戴上 AR，看到的就是她此刻正在做的事。

**场景**：出门 → 手机 HDSI 聊天（消息面）｜回家 → AR 设备 HNSU 启动 → 场景校准 → 她出现在锚点，位置/活动/持物与账本连续，视线由潜流接管。

**开放点**：双面并发（在场时收到 QQ 消息）需要面仲裁规则（哪面"活"、她以何方式回应——出声/事后消息），随 HNSU 首个可用形态后议。

### 0.2 HDSI 与 HNSU 的职责分工

这里的“两个面”不仅是两个输出界面，也对应两种不同的运行节奏，但不对应两套长期叙事核心：

- **HDSI 面继续使用当前的 Narrative Core**。它负责回合式主叙事、剧本提交、关系与长期事实演化、消息投递，以及现有的 Agency / Urge 等叙事能力；
- **HNSU 面在进入在场模式时启用 Agency Core**。Agency Core 面向 HNSU 的实时性，负责将共享剧本、当前观察、潜流和在场约束转化为语音、动作、姿态、Presence 与即时事件；
- Agency Core 不是 HDSI 的替代品，也不是第二本独立剧本。它可以在 HNSU 内部进行连续的感知、微决策和事件编排，但长期剧情事实、关系变化和不可逆的角色弧线仍然回到共享的叙事账本中；
- 当 HNSU 关闭或切回 HDSI 时，Agency Core 停止的是实时在场运行，不是角色的叙事存在。HDSI 仍然依据同一本账本继续主叙事；
- HNSU 产生的即时经验、候选事件或行为痕迹，可以作为后续 HDSI Narrative Core 的上下文材料。它们是否被写入长期剧本，应由主叙事重新理解，而不是由渲染或实时事件自动决定。

因此，理想的关系不是“两个模型争夺谁来扮演她”，而是：

```text
HDSI Narrative Core：负责她的长期叙事与剧本真相
        ↑                         ↓
  事件回流 / 叙事解释       HNSU Agency Core：负责在场时的连续表达
                                  ↓
                    Presence / Voice / Motion / IM Event
```

这一段是愿景层面的职责分工，不冻结具体进程、模型数量或协议形态。未来可以有不同的本地模型、远程模型或混合运行方式，只要保持叙事真相与在场表达的边界即可。

## 1. 一句话愿景

**当用户进入 HNSU 在场模式时，Agency Core 接管实时表达：角色以连续叙事流的方式在用户身边存在，通过 IM 协议控制语音、动作与行为；当用户回到 HDSI 时，当前 Narrative Core 继续负责对话与长期剧本。**

## 2. 从当前到愿景的演进路径

```
当前 HDSI（文字异步）
    ↓ 环境窥视（单向感知：她看得到你）
    ↓ 实时感知（双向视频流：她实时看到你）
    ↓ Agency Core（连续叙事流：她持续存在并反应）
    ↓ AR 具身（她在你的视野里，用 IM 协议控制语音/动作）
```

每一步都是前一步的自然延伸，不是断裂式跳变。

| 阶段 | 感知 | 叙事模式 | 交互 | 硬件 |
|---|---|---|---|---|
| 当前 | 无（文字输入） | 回合制（advance + debounce） | 聊天软件文字 | PC/手机 |
| 环境窥视 | 单向（摄像头快照） | 回合制 + 环境注入 | 聊天软件文字 | PC 摄像头 |
| 实时感知 | 双向（视频流） | 准实时（缩短 advance 间隔） | 语音 + 文字 | PC 摄像头 + 麦克风 |
| Agency Core | 实时（持续视频/音频流） | **连续叙事流** | IM 协议控制 | AR 设备 |
| AR 具身 | 实时 + 空间感知 | 连续叙事流 | 语音 + 动作 + 空间存在 | Vision Pro / Orion |

## 3. Agency Core 是什么

### 3.1 与当前回合制的区别

当前 HDSI 的叙事引擎是**回合制**的：
- 用户发消息 → debounce → 生成一个叙事回合 → 投递 → 等待下一次触发
- 自动推进定时器 → advance → 生成生活片段 → 循环
- 每个回合是独立的叙事单元，有时间边界和明确起止

Agency Core 是**HNSU 内部的连续在场运行层**：
- 没有明确的"回合"边界——角色在 HNSU 中持续存在、持续感知、持续反应；
- 叙事输入来自共享的 Narrative Core 与当前 HNSU 上下文，输出是连续的在场事件，而不是另起一套长期剧本；
- 感知输入可以是持续的视频、音频和空间数据，也可以先从低频的观察窗口开始；
- 输出是多模态的（语音、文字、姿态、动作指令、Presence 事件），不局限于纯文本；
- HNSU 可以产生短时的微叙事和行为候选，但它们是否成为长期事实，仍需回到 HDSI Narrative Core 的叙事流程中理解和提交。

这里的“连续”主要描述 HNSU 的在场节奏，不意味着每一帧都需要调用模型，也不意味着模型输出的每一个瞬时动作都要进入 ScriptCommit。连续感可以由已确认的状态、有限动作库、事件前瞻、重放和本地渲染共同产生。

### 3.2 技术含义

```
当前回合制引擎                     Agency Core 连续流引擎
┌─────────────────┐              ┌─────────────────┐
│ 等待触发          │              │ 持续感知输入       │
│   ↓              │              │   ↓ (视频/音频/空间) │
│ 收集上下文        │              │ 滚动上下文窗口     │
│   ↓              │              │   ↓               │
│ 调用模型（完整回合）│             │ 流式生成（token级） │
│   ↓              │              │   ↓               │
│ 解析/校验/落库    │              │ 实时分发到输出通道  │
│   ↓              │              │   ↓               │
│ 投递消息          │              │ 语音/动作/文字     │
└─────────────────┘              └─────────────────┘
```

**已具备的基础设施**（可复用）：
- ScriptCommit 叙事账本 → 演变为流式事件追加
- Scene/Arc 压缩 → 演变为滚动上下文管理
- Agency/Urge → 演变为实时行为仲裁
- 桥接协议 → 演变为 IM 协议控制通道
- 端点注册表 → 演变为多设备路由

**需要新建的**：
- 流式叙事生成模式（token 级 streaming，不是完整回合）
- 多模态输出分发器（语音/动作/文字并行）
- 实时感知管道（视频/音频流 → 特征提取 → 滚动上下文）
- IM 协议控制通道（外部系统通过协议控制 bot 行为）

## 4. IM 协议控制

当前 HDSI 的输出是"角色决定说什么" → 生成文本 → 投递到聊天软件。

在 Agency Core 中，输出变为**结构化的行为指令流**，通过 IM 协议分发给渲染/执行层：

```json
{
  "type": "agency-core-stream",
  "timestamp": "2026-10-03T14:32:05.123Z",
  "participant": "user-qq-12345",
  "stream": {
    "speech": {
      "text": "你今天看起来累了呢",
      "voice": "warm-concerned",
      "pace": "slow",
      "interruptible": true
    },
    "action": {
      "expression": "worried",
      "gesture": "tilt-head",
      "gaze": "at-user"
    },
    "narrative": {
      "internal": "她注意到用户揉了揉眼睛，肩膀也垮着。想提醒休息但又怕唠叨。",
      "scene-note": "用户在客厅沙发上，光线昏暗，电视开着"
    }
  }
}
```

这就像 Neuro-chan 的控制协议——但叙事决策由 HDSI 的 Agency/Urge 系统驱动，不是简单的 prompt → response。

### 4.1 控制协议层次

```
Layer 1: 叙事决策（HDSI 核心）
  "她现在想说什么、做什么、注意什么"
    ↓
Layer 2: IM 协议封装
  "结构化的 speech + action + narrative 流"
    ↓
Layer 3: 渲染执行（AR 端）
  "语音合成 → 播放 / 3D 模型 → 动作 / 文字 → 显示"
```

HDSI 核心**不关心**渲染层怎么实现——Vision Pro 的 spatial computing、VRChat 的 3D avatar、还是简单的语音+字幕。它只通过 IM 协议输出决策流。

## 5. 与 Neuro-chan (VRChat) 的区别

| | Neuro-chan | HDSI Agency Core |
|---|---|---|
| 叙事引擎 | 简单 prompt → response | ScriptCommit + Scene/Arc + Agency/Urge |
| 记忆 | 短期对话缓冲 | 持久剧本 + 关系状态 + 长期事实 |
| 主体性 | 被动响应为主 | 独立生活推进 + 主动联系 + 行动容量管理 |
| 感知 | VRChat 内的虚拟环境 | 用户真实环境（AR 摄像头 + 空间感知） |
| 存在形态 | 虚拟世界中的 avatar | AR 叠加在现实上的陪伴者 |
| 叙事深度 | 娱乐互动 | 持续性人物弧线 + 长期关系演化 |

**核心差异**：Neuro-chan 是一个"能对话的 3D 模型"，HDSI Agency Core 是一个"有完整叙事生活的存在，通过 AR 获得视觉表达"。

## 6. 环境窥视作为铺垫

`ENVIRONMENT_OBSERVATION_DESIGN.md` 的设计在这个愿景中的位置：

| 环境窥视（现在） | Agency Core（未来） |
|---|---|
| 每次 advance 拍一张快照 | 持续视频流 + 空间感知 |
| vision 模型生成结构化描述 | 实时特征提取管道 |
| 注入回合制叙事 payload | 滚动注入连续流上下文 |
| 她可以选择提及或不提 | 她实时反应（延迟 < 1s） |
| 聊天软件文字回复 | 语音 + 动作 + 文字多模态输出 |

**铺垫价值**：
1. 验证用户对"被看见"的接受度和隐私边界
2. 建立 vision → 叙事注入的管道
3. 积累结构化场景描述的数据模型经验
4. 测试她在叙事中如何自然地使用环境信息

## 7. 硬件前提

这个愿景依赖的硬件能力：

| 能力 | 当前可用 | 预期成熟 |
|---|---|---|
| AR 头显（足够轻、全天佩戴） | Vision Pro（重）/ Meta Orion（原型） | 2027-2028 消费级 |
| 实时空间感知（SLAM + 场景理解） | Vision Pro 已有 | 持续改进 |
| 实时语音合成（低延迟 + 情感表达） | ElevenLabs / 火山引擎 | 已可用，需优化延迟 |
| 全天电池 | 挑战 | 2028+ 可能 |
| 蜂窝网络 / 边缘计算 | 5G 已有 | 边缘 LLM 推理仍在发展 |

**关键瓶颈**：不是 HDSI 软件，而是硬件舒适度 + 实时 LLM 推理延迟 + 电池续航。

## 8. 技术演进路线（高层、非排期）

这条路线更适合被理解为几个可以逐步组合的能力方向，而不是带有固定日期的瀑布式计划：

| 能力方向 | 愿景中的作用 | 可行的渐进方式 |
|---|---|---|
| 环境观察 | 让角色获得关于用户现实环境的时间窗口经验 | 从快照、关键帧和合成视频开始，再增加连续视频或音频 |
| 叙事连续性 | 让观察不会只是一次性描述，而能影响场景、关系和角色弧线 | 先由 HDSI Narrative Core 处理，再考虑把候选经验回流到 HNSU |
| HNSU Agency Core | 在 HNSU 中提供低延迟的持续感知、微决策和在场事件 | 从事件节拍、潜流、有限动作与本地重放开始，再探索更连续的生成 |
| 多模态输出 | 把同一在场意图表达为文字、声音、动作、表情和 Presence | 先复用现有消息和桥接能力，再增加语音、动作和空间事件通道 |
| 空间显形 | 让角色的叙事状态在固定机位、桌面或 AR 视野中可见 | 从二维合成、校准和有限姿态开始，再迁移到 billboard 或设备原生渲染 |
| 多设备与面切换 | 让用户切换设备时仍然面对同一个叙事主体 | 共享账本和事件语义，按设备能力重建派生状态 |

这些方向可以相互解耦。真实实施时，可以根据叙事质量、隐私边界、模型延迟、设备舒适度和成本，选择先验证其中任何一个方向；不需要现在确定最终的模型、硬件、帧率或协议版本。

## 8.1 不冻结实现的可行路径

Agency Core 的实现可以沿着几个互相独立、逐步增强的方向自然演进，而不必现在就决定最终的模型、硬件或协议：

1. **从事件节拍而不是连续文本开始**：先让 HNSU 以“观察到变化—更新潜流—产生可选事件—本地呈现”的节拍运行，连续感由状态保持和渲染重放提供；
2. **从可回放的事件开始**：任何在场行为都尽量能说明来源、持续时间和失效条件，使设备断线、切面或重启后能够恢复、重建或安全丢弃；
3. **从共享叙事状态消费开始**：HNSU 先读取 HDSI Narrative Core 已经建立的角色、关系、场景和近期意图，再逐步增加 HNSU 自己的观察与微事件；
4. **从单向表达逐渐增加回流**：最初 Presence、语音和动作只是主叙事的派生表现，之后再让 HNSU 的观察和在场经验以候选材料回到 HDSI，由主叙事决定是否理解为新的剧情；
5. **从单一表面逐步扩展到多设备**：桌面固定机位、摄像头预览、手机端、AR 设备可以共享同一个在场事件语义，具体渲染器只是不同的表达实现。

这些是可行的设计方向，而不是硬性阶段表。真正的落点可以根据叙事质量、设备能力、成本和用户体验逐步调整。

## 9. 开放问题（记录在案，不急于回答）

- **连续流的叙事质量控制**：回合制有明确的"这轮写完了"边界，流式生成如何确保叙事质量而不是退化成碎片化反应？
- **上下文窗口管理**：连续流场景下，上下文更新频率远高于回合制——现有 Scene/Arc 压缩机制是否能跟上？
- **Agency/Urge 的实时化**：当前 Agency 是分钟级决策，实时场景下需要秒级行为仲裁——架构怎么调整？
- **IM 协议标准化**：是私有协议还是参考现有标准（如 WebRTC DataChannel / MQTT）？
- **离线行为**：AR 设备断网时，Agency Core 是停止还是降级为本地轻量模式？
- **多用户同时在场**：如果多个用户同时佩戴 AR，她如何分配注意力和存在感？（现有 Agency 的参与者容量管理可参考，但需要空间化）

## 10. 结语

这个愿景的根源是 HDSI 的核心哲学：**角色有自己的生活，与用户的生活平行展开，两者在叙事中交汇**。

当前的文字异步模式是这种交汇的最简形式。环境窥视让她第一次"看到"用户的生活。Agency Core 让她持续地看到、持续地存在。AR 具身让这种存在获得视觉形态。

但从头到尾，不变的是：**她是一个叙事存在，不是一个聊天机器人。她的每一次反应都来自她自己的生活逻辑，而不是对用户输入的直接映射。**

这也是为什么 HDSI 的叙事核心（ScriptCommit / Agency / Urge / 长期事实 / 关系演化）在这个愿景中不仅是可复用的，而且是不可替代的——它就是"她是谁"的引擎。

## 11. 最新技术实现澄清：Agency Core 的剧本化动作帧模型（2026-10-05）

本节是在不删除前述愿景、历史讨论和开放问题的前提下，对 Agency Core 的技术实现路径作进一步澄清。前文中出现的“持续流”“行为编排”“微决策”“IM 协议控制”等表述，均应在本节定义的剧本化动作帧模型下理解；它们描述的是能力方向，不表示 Agency Core 必须退化为一个脱离叙事的行为控制器。

### 11.1 单模式运行：一个共享叙事世界，两个运行面

HDSI 与 HNSU 共享同一个叙事世界、ScriptCommit 和角色连续性，但在当前设计中是**两个分开的运行模式**：同一时刻只启用一个主动叙事核心，不把 HDSI Narrative Core 与 HNSU Agency Core 作为两个并发写作者处理。

```text
一个共享叙事世界
        │
        ├─ HDSI 模式：Narrative Core → 对话回合、消息、主叙事提交
        │
        └─ HNSU 模式：Agency Core → 在场动作回合、Presence、Voice、World Action
```

因此，当前技术路径不存在两个模型同时争夺账本写入权的问题。面切换的实现重点是：在切换时读取同一叙事真相、重建对应的派生状态，并让新的运行面从当前剧情位置继续；而不是设计一个复杂的跨模式并发仲裁器。文档前文关于未来“双面并发”的讨论仍然保留，作为远期开放问题，不构成当前 HNSU 基线的前置条件。

### 11.2 Agency Core 是 HNSU 专属的快速 Narrative Core 变体

Agency Core 只在 HNSU 在场模式启用。它不是独立的长期剧本，也不是传统意义上的 `Intent → ActionPlan → Executor` 行为控制链。它更接近一个针对实时在场场景改造过的 HDSI Narrative Core：使用更短上下文、更低延迟的模型调用，以**叙事者视角**写出极短的剧本片段，并将同一片段投影为一次世界动作。

其核心关系应理解为：

```text
Narrative Context + 用户视角观察
        ↓
快速叙事模型（narrator perspective）
        ↓
极短剧本片段
        ↓
一个 Agency Action Frame（在场动作帧）
        ↓
Presence / Voice / World Action 呈现
```

这里的结构化字段不是第二次行为决策，而是叙事片段的可执行表达。叙事文本是动作的来源，结构化世界动作是叙事的投影，呈现层只负责把它显现出来。

### 11.3 最小叙事单位：一次调用对应一帧动作

HNSU 的最小运行单位是 **Agency Action Frame（在场动作帧 / 叙事动作节拍）**。一次 Agency Core 调用直接生成一帧动作，不再预设“一个 Scenelet 先拆成若干低级动作，再由另一个执行器逐个仲裁”的中间层。

```json
{
  "frameId": "agency-frame-204",
  "previousFrameId": "agency-frame-203",
  "narrative": {
    "perspective": "narrator",
    "text": "她听见你的声音，手指停了一下，随后抬头看向你。",
    "continuity": "interrupt_current_activity"
  },
  "worldAction": {
    "activity": "pause_paperwork",
    "gaze": "toward_user",
    "posture": "look_up",
    "expression": "attentive",
    "voice": "你还没睡吗？"
  },
  "durationMs": 2200,
  "viewCaptureAfter": true
}
```

上例中的 `worldAction` 不是独立于叙事的意图仲裁结果，而是这一小段剧本在具体设备上的结构化演出标注。Presence、Voice 和渲染器可以做能力降级、时长适配、姿态插值、遮挡处理和音画合成，但不能在 Agency Core 没有生成的情况下自行追加新的角色行为。

连续性来自相邻动作帧之间的叙事上下文，而不是来自低级动作状态机。上下文可以包括：上一帧叙事文本、上一帧的显形状态、当前活动、用户与角色的空间关系、潜流状态、长期剧本、上一帧的持续时间与结果、`previousFrameId`，以及动作之后重新捕获的用户视角。

### 11.4 HNSU 回合：动作驱动的用户视角闭环

HNSU 的理想回合不是持续向模型上传完整视频，而是围绕一次动作帧形成闭环：

```text
捕获当前用户视角
        ↓
获取可用的结构化场景数据
        ↓
Agency Core 生成一个 Agency Action Frame
        ↓
呈现这一帧动作
        ↓
动作后重新捕获一张用户视角图片
        ↓
图片 + 结构化数据 + 动作结果
        ↓
下一次 Agency Core 调用
```

在 AR 场景中，每一次 Agency Core 调用原则上只放出一帧动作；动作完成或达到适合观察的节点后，再拍摄一张用户视角图片，作为下一次叙事调用的材料。这样可以保留“她在用户视角中连续存在”的拟真感，同时避免把 HNSU 的核心机制建立在持续上传完整视频之上。

可行的数据包形式如下。该结构是技术路径示意，不冻结最终接口：

```ts
type AgencyObservationPackage = {
  viewImage: ImageRef
  viewTimestamp: string
  cameraPose?: CameraPose
  fieldOfView?: FieldOfView
  sceneDelta?: SceneDelta
  visibleUserState?: UserState
  lightingState?: LightingState
  spatialRelations?: SpatialRelation[]
  previousFrameId?: string
  previousActionStatus?: ActionStatus
}
```

图片提供用户实际看到的视觉关系、光照、物体细节和 Presence 外观；结构化数据提供位置、变化、遮挡、用户状态、光照与空间关系；动作结果说明上一帧是否成功呈现、是否被中断或是否完成。三者共同构成下一帧剧本的观察材料。

### 11.5 用户视角包含 Presence 不构成反馈污染

HNSU 的用户视角图片可以包含 bot 自身的 Presence。这个事实不是需要规避的反馈污染，而是 HNSU 连贯性的来源。Agency Core 的系统提示应明确：

- 模型是叙事者，而不是以第一人称摄像头观察者；
- 输入图片是用户所看到的视角；
- 图片中的 bot 是叙事主体自身在上一动作中的显形；
- 当前图片代表上一帧动作之后真实可见的世界状态；
- 模型可以根据自身上一帧的显形继续写作，并让下一帧动作与之保持连续。

可以附加以下语义元数据帮助模型理解画面，但不应因此删除 bot 的图像区域，也不要求强制提供 raw/composited 两套图片：

```json
{
  "viewSemantics": {
    "cameraOwner": "user",
    "selfPresenceIncluded": true,
    "selfPresenceFrameId": "agency-frame-203",
    "selfPresenceRegion": {
      "x": 0.42,
      "y": 0.31,
      "width": 0.18,
      "height": 0.52
    }
  }
}
```

这使得“上一动作 → 用户所见的 Presence → 下一次叙事”成为一个正向的视觉—剧本连续性回路，而不是模型误把自己的渲染结果当作外部角色的错误反馈。

### 11.6 与呈现层的职责边界

```text
Agency Core
  = 以叙事者视角生成极短剧本片段与一个 Agency Action Frame

Presence / Voice / Render
  = 将动作帧显现为姿态、表情、声音、光影、合成画面和设备事件

User View Capture / Environment Observation
  = 捕获动作后用户所见，并把图片与结构化观察材料交回下一次叙事调用
```

呈现层可以是确定性的，以保证设备执行稳定；但确定性执行不应意味着上游采用去剧本化的意图控制。确定性只约束“这一帧如何被可靠地演出来”，不负责创造“角色下一步为什么这样做”。后者必须来自 Agency Core 生成的叙事。

### 11.7 不冻结的实现路径补充

上述模型可以先用桌面固定机位、合成图片和有限动作进行验证，再逐步迁移到 AR；也可以先验证快速叙事提示词和动作帧结构，再接入真实用户视角捕获。以下内容都是可行路径，而非版本阶段或接口承诺：

1. 用模拟用户视角图片验证“动作帧生成 → Presence 呈现 → 下一帧续写”的叙事连续性；
2. 使用短上下文、快速模型和严格输出校验，验证单次调用一帧动作的延迟与剧本质量平衡；
3. 让渲染器只执行动作帧，记录 `frameId`、`previousFrameId`、呈现状态与动作结果；
4. 以动作后用户视角图片作为 HNSU 的默认观察闭环，再按设备能力增加可选的短时观察窗口；
5. 在 HDSI / HNSU 模式切换时只重建派生状态，不复制叙事账本，也不强制引入并发仲裁；
6. 待真实体验证明需要更强的自主性后，再扩展动作帧字段与空间能力，而不是预先建立一整套低级动作计划系统。

这些内容用于补足技术实现想法，保留前文全部愿景、历史路线和开放问题。

## 12. 概念一致性补充：Agency Core 应保持“即时剧本化”（技术路径，不删改前文）

> 本节是对前文路线的进一步澄清和补充。它不删除、不替换前文关于连续在场、潜流、事件节拍、设备迁移或实验性实现的任何内容；如果前文存在多个可行分支，本节只说明当前更希望优先验证的技术解释。

### 12.1 Agency Core 不是 Intent / ActionPlan 控制器

Agency Core 的核心价值不是把角色意图转换成一组外部动作指令，而是把 HDSI 的“剧本化生成”压缩到 HNSU 所需的低延迟时间尺度中。它应当被理解为：

```text
用户视角 / 当前观察
        ↓
快速 Agency Narrative Core
        ↓
极短剧本片段
        ↓
一个 Agency Action Frame
        ↓
Presence / Voice / World Action 呈现
```

因此，下列结构不应成为 HNSU 的主导抽象：

```text
Agency Core → Intent → ActionPlan → Deterministic Executor
```

这种结构可以作为设备适配、动作校验或渲染接口的局部实现，但不能成为叙事决策链。它会把“为什么角色现在这样做”从剧本中剥离出来，最终使 Agency Core 退化为普通行为控制器，削弱 HDSI 原本通过剧本塑造拟真和主体性的优势。

更准确的分层是：

```text
Agency Narrative Core
  = 以叙事者视角，在极短上下文中写出这一刻发生的剧本

Narrative Realization / World Action Projection
  = 将剧本片段投影为本次可呈现的动作帧，并完成字段校验、设备适配和降级

Presence / Voice / Device Renderer
  = 把动作帧稳定地显现为姿态、视线、表情、声音、光影和空间事件
```

后两层可以是确定性的，但它们不拥有新的剧情创作权；如果设备不支持某个动作，只能报告降级、失败或中断，不能擅自改写角色动机。

### 12.2 一次调用只产生一帧动作

HNSU 的最小时间单位不是“一个场景片段拆成若干低级动作”，而是一次 Agency Core 调用对应一个 `Agency Action Frame`。该帧可以在叙事上包含一个短促而完整的动作节拍，例如“她停下手上的事，抬头看向用户，并说出一句话”，但其呈现仍作为同一个世界动作帧处理。

```text
一次 Agency Core 调用
        ↓
一个极短剧本片段 + 一个 Agency Action Frame
        ↓
动作帧呈现
        ↓
动作后用户视角捕获
        ↓
下一次 Agency Core 调用
```

动作帧内部的骨骼插值、口型同步、音频播放、渲染降级和设备时序属于演出层细节，不应被重新解释为多个拥有独立叙事意义的低级动作。这样既能保留动画实现的连续性，也能保证每一帧的叙事来源只有一个。

### 12.3 Narrative 是动作来源，结构化动作是叙事投影

建议把输出理解为以下关系，而不是两个并列决策结果：

```json
{
  "narrative": {
    "perspective": "narrator",
    "text": "她原本低头整理纸张，听到你的声音后，手指停了一下，随后抬头看向你。",
    "continuity": "interrupt_current_activity"
  },
  "worldAction": {
    "activity": "pause_paperwork",
    "gaze": "toward_user",
    "posture": "look_up",
    "expression": "attentive",
    "voice": "你还没睡吗？"
  },
  "durationMs": 2200,
  "previousFrameId": "agency-frame-203"
}
```

这里 `worldAction` 是 `narrative` 的结构化演出投影，用于让 Presence 和设备可靠呈现；它不是脱离剧本后独立生成的意图计划。后续回合继续读取动作后的用户视角，使“剧本—显形—再观察—续写”成为完整的拟真闭环。

### 12.4 HDSI 与 HNSU 是两个运行表面，而不是并发的两个核心

共享叙事世界可以有两个运行表面，但在当前设计假设中，HDSI 与 HNSU 不需要并发写入同一回合：

```text
一个共享叙事世界
        ↓
当前选择一个主动运行表面
        ├─ HDSI：Narrative Core → 文本 / 对话 / 消息
        └─ HNSU：Agency Narrative Core → 一个动作帧 / Presence / 语音 / 世界动作
```

同一时刻原则上只运行一个主动叙事核心。这里需要处理的是单次 HNSU 回合的中断、恢复、动作呈现状态和账本记录，而不是为 HDSI 与 HNSU 引入复杂的并发仲裁、双写冲突或互相覆盖机制。HNSU 关闭或切换回 HDSI 时，恢复的是同一个叙事世界；不需要复制另一套独立剧本。

### 12.5 用户视角回传是动作连续性的来源

HNSU 在 AR 路径上不以持续上传完整视频为最小前提。一次 Agency Core 调用生成并呈现一个动作帧后，系统拍摄一张用户视角图片，并将其与结构化观察数据、上一帧引用和真实呈现状态一起交给下一次 Agency Core：

```text
上一轮动作帧
        ↓
用户看到的动作后视角
        ↓
图片 + 结构化场景数据 + 呈现状态
        ↓
下一轮 Agency Narrative Core
```

这不是把环境观察降级为“只看一张图片”，而是把观察采样点放在每个叙事动作帧之后。若场景确实需要时间信息，可以在特定回合按需加入短窗口或关键帧集合；但持续完整视频不应成为 HNSU 最小闭环的必要条件。

### 12.6 Presence 出现在用户视角中不是反馈污染

用户视角图片可以包含 bot 自身的 Presence，而且这是有意保留的连续性材料。Agency Core 的提示词应明确它是叙事者：图片是用户看到的视角，画面中的 bot 是叙事主体上一帧动作后的显形。模型可以据此判断自己的姿态、距离、视线、遮挡、光照与空间连续性，并继续生成下一帧。

```text
上一帧 Agency Action Frame
        ↓
bot 在用户视角中的显形
        ↓
动作后用户视角观察
        ↓
Agency Core 续写下一帧
```

可选的 `cameraOwner`、`selfPresenceIncluded`、`selfPresenceFrameId` 等字段只用于帮助模型理解视角语义，不是为了屏蔽 Presence、强制拆分 raw/composited 输入，或把自己的显形误判为外部角色。

### 12.6.1 度量空间来自追踪计算，不来自图像估计

单目图像的尺度本质不可知：没有已知尺寸的参照物，从一张图片只能得到序数级的距离感（"她比桌子远"），VLM 也不例外。因此距离、方位、遮挡的**度量值**一律以结构化通道为准；图片承担"质"（场景外观、氛围、她的显形效果、无法枚举的细节），不承担"量"。12.6 中"模型可以据此判断自己的距离"应按此理解：判断的依据是结构化空间数据，图片提供视觉印证。

MR 客户端本地同时持有用户头部位姿（SLAM 每帧更新）、Presence 的锚点与当前渲染 transform（她自己渲染的，位置精确已知）、以及可选的深度图/平面——"用户离她多远"是两个已知向量的范数，是计算而非感知。每个动作帧随视角图附带一个空间摘要（示意，不冻结字段）：

```text
spatialFrame: {
  distanceMeters, bearingDegrees,      // 头 ↔ Presence 锚点的实测向量
  inFieldOfView, lookingAtHer,         // FOV 判定 +（有眼动时）注视锥判定
  herFacing,                           // 从她的渲染朝向导出
  occlusion, betweenFurniture,         // 头→她的射线对深度/平面 raycast
  userMovement,                        // 近几秒头姿增量（接近/远离/静止）
}
```

反向同理：`worldAction` 的移动语义（如 `move-to: 窗边`）由客户端用场景图（锚点/平面/raycast）解析为米制 transform 执行；下一帧的 `previousActionStatus` 与新的空间摘要把执行结果变成实测事实回传。叙事侧始终生活在语义空间，米制始终是设备侧的职责——观察包里的 `cameraPose`、`fieldOfView`、`spatialRelations` 正是这两个空间之间的桥梁。

这条机制也划清了设备能力的优先级：只要客户端持有位姿与锚点（四台设备的结构化观察栈都能做到），度量通道就是完整的；相机像素缺失只损失图片通道的丰度，不会让空间关系退化为猜测。反之，只有像素而没有位姿的输入（如纯手机拍摄）才是真正的盲估。

### 12.6.2 放置解析与立牌坐标系（防滑移规则）

叙事模型**永远不凭空输出米制坐标**。她的位置（立牌）解析有三条安全通道，全部在设备侧完成坐标计算（"后渲染坐标输出"）：

1. **语义放置（默认）**：`worldAction` 输出语义目标（`move-to: 窗边` / `approach-user` / `step-back`），客户端用场景图（持久锚点、平面、raycast）解析为米制 transform。`approach-user` 一类的相对语义在**执行时刻**用执行时刻的头部位姿计算，不用拍照时刻的。
2. **照片像素引用**：模型在所提供的视角照片内指一个点或框。客户端用**拍照时刻**的深度图与相机位姿做反投影：`pixel + depth(T) + pose(T) → world`，再挂持久锚点。因为拍照时刻的位姿是已知且固定的，这一变换无歧义——这是"拍照相对坐标"唯一安全的用法。
   - **指向的永远是"落点表面"，不是她的身体**：放置目标是地板/家具面等可站立表面，raycast 命中平面后做重力下落（gravity drop）到地板，得到站姿锚点。不要求她的脚或落点以外的东西可见。
   - **落点本身被遮挡时（如"站到沙发后面"），像素通道自动让位**：此时可见像素给不出沙发背后的地板，改走通道 1（语义：沙发锚点 + 朝墙偏移）或通道 3。通道选择由客户端按可见性判定，模型不需要知道这个切换。
   - **她自己的当前位置永远不需要像素指向**：她本来就是客户端渲染的，transform 是已知事实。像素通道只服务于"新的目标落点"。
   - **视野事实**：透视即相机画面——真实世界凡是用户看得见的部分必然来自相机像素，不存在"眼见但相机没拍到"的真实场景。真正的缝隙是**送给模型的照片 FOV 可能小于用户实际视场**（采集裁剪/镜像裁切）：用相机内参 + 位姿保证照片内像素的反投影一致性，照片外的目标回落到通道 1/3；采集时尽量用全传感器画幅而非合成镜像画面。
3. **候选选择**：客户端随观察包发送预计算的放置候选（`availablePlacements: [{id, 语义描述, 实测坐标(模型不可见)}]`），模型只返回 id。适合房间已校准、常见落点有限的场景。

**立牌坐标系不变式**：她的 Presence 只存在于世界坐标系（SLAM world frame）的持久锚点上，**绝不**以渲染时刻的相机相对坐标表达。用户在动作帧期间或渲染期间移动，位姿变化只影响用户看到她的视角，不影响她的位置——滑移 bug 的根因正是把照片相对坐标错误地应用到渲染时刻位姿上（或把立牌挂成 head-relative）。跨会话由持久锚点（visionOS WorldAnchor / Android XR `device_anchor_persistence` / HorizonOS Spatial Entities）保证"她总在窗边"。

照片的职责因此保持纯粹：为叙事提供"她存在于其中的环境"的场景外观材料（含她自己的显形效果）；度量信息一概由结构化通道承担。模型需要"放置"能力时，只在上述三条通道的受控词汇内表达。

### 12.6.3 场景知识与全景采集：她要去的地方，模型必须看得见

并排走问题实际包含两个不同的缺口，上一版只答了第一个：

1. **"她在画面里"**——她出了相机视野后叙事材料缺她 → `presenceSnapshot`（自渲染快照）解决：她的显形是客户端资产，任何机位都能渲染。
2. **"她要去的地方模型看得见"**——若模型对用户背后的环境一无所知就把她放到背后某处，叙事等于盲写（背后有没有椅子？有没有人？光照如何？）。**这不是渲染问题，是场景知识问题**——在模型没有视觉材料的地方放置她，无论渲染机制多正确，叙事上都不可接受。

**修正一个前提**：场景知识不等于"拍照时刻的瞬时视角"。头显本来就在持续积累**全向**场景模型——SLAM 位姿 + 平面检测 + 深度累积 + 持久锚点覆盖整个房间 360°，包括用户此刻没在看的地方。"场景校准"（回家戴上 AR 的既定步骤）正是知识积累完成时刻。

**采纳全景方案，放在校准时刻**：

```text
场景校准（用户环视房间一遍）：
  ① 环视全景——多帧相机画面按已知 SLAM 位姿拼接成 360° 全景
     （位姿已知，拼接是确定性的投影贴图，比盲拼容易一个量级）
  ② 场景图——平面/深度/锚点，持久化
  ③ 放置候选——从全景+几何预提取：窗边、沙发左、书架前…各带世界坐标
  三者持久保存（锚点跨会话），成为该房间的常驻上下文

动作帧循环（每帧）：
  前方照片（动态：光影变化、新出现的物体、她若在视野内）
  + spatialFrame + presenceSnapshot
  + 房间常驻上下文（全景/场景图/候选，不逐帧重发）
```

模型的放置指认因此推广为**在全景里指**（原通道 2 的 360° 版）：全景图有已知的等距柱状投影和世界朝向，像素 → 射线 → 与校准几何求交 → 世界坐标 → 锚点。校准全景过期问题由 `sceneDelta`（观察包既有字段）与定期重校准兜底。

**场景知识的新鲜度分层（家具移动问题的解）**——不做周期性全量重构（1 次/s 的 SLAM 重解既贵又无必要：大部分知识不失效，且设备的场景理解本来就是增量更新的）。知识分三层，各走各的更新机制：

| 层 | 内容 | 更新机制 |
|---|---|---|
| 结构层 | 墙、地板、窗、门口 | 几乎不变；持久锚点跨会话 |
| 家具层 | 沙发、桌子、床、椅子 | **视野驱动增量更新**：该区域进入视野时，实时深度/平面与存量比对，冲突则更新场景图并经 `sceneDelta` 报告 |
| 动态层 | 被拖动的椅子、杯子、人、宠物 | 不进放置候选；只活在每帧深度图与前方照片里 |

**可移动物体的规则：候选不挂持久锚点，改挂"使用时校验"。** "她坐到椅子上"的执行流程：落点候选在使用瞬间用当前深度/平面探测目标位置——几何与预期不符（椅子被搬走/挪位）则不执行，回执 `previousActionStatus: blocked（目标不在原位）`，模型据此重新决策（她站在原处 / 把椅子搬回来 / 坐到别处）。这复用的正是观察包既有的动作回执机制：**校验失败不是错误，是叙事材料**——"她走到椅子旁发现你把椅子搬走了"本身就是一帧好剧本。

**重校准由事件触发，不由时钟触发**：用户主动（知道挪了家具，扫一眼）或叙事触发（模型从 `sceneDelta` 冲突中察觉"房间和记忆不一样"，主动环视重扫，或直接在剧本里问）。她的锚点若挂在被移动的家具上，随家具层的更新重新附着到新位置或回退到最近的结构层落点。

**走路/户外换机制**：动态环境里全景立刻过期，但并走场景的放置本就是相对槽位（身侧/身后/前方），且行进方向恰好被前方照片覆盖——静态房间用全景+候选，动态环境用相对槽位+前方照片，两套机制各管一类场景。

外挂 360 相机仍列为"体验证明需要后"的增强（免环视的全自动全景、户外连续重建），不进最小闭环。

### 12.6.5 图像通道分工总表（收敛结论）

经过 §12.6.1–12.6.3 的演化，图像类材料收敛为**观察类（输入）**与**表达类（输出）**两类，职责不再重叠：

| 类 | 通道 | 更新 | 唯一职责 |
|---|---|---|---|
| 观察（模型看世界） | **前方照片**（相机原始帧，拍照时刻位姿+内参） | 每动作帧 | **她的眼睛**：当前视线方向的实时世界——用户在看什么/做什么、新出现的事物（sceneDelta 的语义理解来源）、光影氛围。作用对象是世界，不是她；她在不在视野内与此无关 |
| 观察 | 校准全景（环视拼接） | 校准/事件触发 | 房间的视觉记忆：全貌外观 + 放置指认的静态画布 |
| 观察 | presenceSnapshot（自渲染） | 需要时 | 她自己此刻的样子（视野外补位） |
| 表达（模型放置她） | 语义 / 候选 / 像素指认 | 按需 | 像素指认的画布 = 全景（已知房间内的新落点）或当前照片（"你正在看的那个东西旁边"这类指向新出现物体的空间引用）；反投影逻辑同一套（pixel + depth + 拍照时刻 pose → world） |

与 R3 实时渲染路径（PRESENCE_RENDER §6.2c）合起来，相机与渲染的分工彻底干净：**相机 → 叙事感知（输入，她看世界）；渲染 → 她的显形（输出，客户端资产）**。照片里"有没有她"从此不再是任何机制的前提——SV34 §12.6 最初的"POV 照片包含 Presence"假设就此完成历史使命：她始终在观察包里（照片或自渲染快照），只是来源随方位切换。

### 12.6.6 房间的语义场景图：物体识别与命名（"椅子还是箱子"）

**几何分不清的，外观分得清**：形状相似的椅子与纸箱，深度图上几乎同构——语义区分靠 RGB 外观（材质、纹理、部件模式、上下文）过开放词汇模型，这正是近两年"开放词汇 3D 场景理解"研究线的核心成果。**HNSU 不需要实时识别**：场景图在校准时刻离线构建（秒到分钟级预算），逐帧只需轻量变化检测——因此重量级方案（两阶段 Grounded-SAM）也可用。

**校准管线**（复用 §12.6.3 环视采集的同一批帧，不新增采集成本）：

```text
环视帧（RGB + 深度 + 位姿，全景拼接共用）
  ↓ ① 2D 开放词汇分割（Grounded-SAM 高精度档 / YOLO-World 实时档）
  ↓ ② 逐分割块反投影为点云，多视角关联融合为 3D 物体实例（ConceptGraphs 的关联模块）
  ↓ ③ 每实例的多视角裁剪图 → VLM 命名（"办公椅""纸箱"，含颜色/材质/状态等开放属性）
  ↓ ④ 房间场景图：命名物体（位置/包围盒/属性）+ 平面 + 空间关系
输出 → 叙事的房间常驻上下文 + 放置候选自动派生（"窗台""沙发左侧"从命名物体导出，不再手枚举）
```

**逐帧**：轻量 sceneDelta（YOLO-World/MobileSAM 对当前帧 vs 场景图——新增/消失/移动的物体，语义级报告）。

**平台捷径**：Vision Pro = RoomPlan 原生（约 16 类家具级语义，**不消耗相机授权**——系统级扫描；开放词汇命名可作为增强叠加）；Quest = Scene API 用户辅助标注；Galaxy XR/Android XR = 无内建物体语义，走上述自建管线（前置依赖仍是相机帧可用性的实机验证）。

### 12.7 仍然保持开放的技术验证路径

本节描述的是实现思路，不是版本冻结或接口承诺。可以沿以下路径逐步验证：

1. 用合成用户视角和结构化数据，验证快速叙事模型能否稳定生成一帧动作；
2. 在桌面固定机位中验证“单帧剧本—单帧呈现—动作后捕获—下一帧续写”；
3. 用多个渲染器呈现同一个动作帧，验证叙事语义与显形技术解耦；
4. 注入中断、失败、设备不可用和视角捕获失败，确认下一次叙事读取真实状态；
5. 体验证明需要更强空间能力后，再迁移至 AR，并按需加入短时观察窗口；
6. 继续保留前文的事件节拍、连续流、本地重放和候选事件等路线，作为可组合的实验方案，而不是现在就固定成单一工程阶段。

## 13. Agency Core 的低延迟结构与实现路径

> 本节是 Agency Core 的新增技术路径讨论，不删除或替换前文关于连续在场、事件节拍、潜流、单帧动作、共享叙事世界及各种模型/设备演进路线的内容。以下路径用于比较和实验，不构成接口冻结、阶段承诺或最终选型。

### 13.1 结构判断：叙事决策单线，系统准备分层

Agency Core 既不必被限制为“单一模型承担所有准备工作”，也不宜变成“多个模型逐层审批每一帧”。更适合当前 HNSU 目标的抽象是：**每个动作回合只有一个主动的 Agency Narrative Core 作出叙事决定；其周围可以有不同时间尺度的上下文准备、推理优化和呈现支持。**

```text
低频 / 空闲时的叙事准备
  └─ 整理长线潜流、人物弧线、近期关系与候选创作方向
       ↓ 形成简短、可选的剧作注记

单帧 Agency 回合
  当前用户视角 + 结构化观察 + 最近动作与真实呈现状态
  + 精简的角色 / 场景状态 + 可用的剧作注记
       ↓
  一次快速 Agency Narrative Core 调用
       ↓
  极短剧本片段 + 一个 Agency Action Frame
       ↓
  Narrative Realization / Presence / Voice 呈现
       ↓
  动作后用户视角，作为下一回合材料
```

这里的“分层”主要指**时间尺度和职责分层**，而不是把一个动作帧串成多个模型之间的传递审批链。动作的叙事原因仍由当次 Agency Narrative Core 写出；下游校验、投影和渲染负责可靠呈现，不接管角色动机。

### 13.2 300 tok/s 不等于端到端动作延迟

模型公布或测得的 token/s 通常描述生成阶段的速度，不足以单独代表用户等待一次动作的总时间。Agency 回合的体验延迟还可能包括：

```text
用户视角捕获 / 图像编码
+ 结构化环境数据整理
+ 请求排队、网络与模型加载
+ Prompt prefill / 首 token 延迟
+ 输出解码
+ 结构化结果解析与校验
+ Presence / Voice / 设备呈现准备
```

因此不应只以 token/s 作为优化目标。至少应分别记录“观察材料就绪 → 首个可呈现动作帧”的端到端延迟、TTFT、prefill、decode、校验和呈现准备耗时，并关注 P50 / P95 等分位数。具体目标值应由目标设备、模型、图像输入和用户体验测试共同确定，而不是预先假定一个跨设备通用数字。

### 13.3 可比较的实现路径

#### 路径 A：较强模型单次调用，优先缩短链路

```text
当前观察 + 精简叙事状态 → 单个较强模型 → 短叙事 + 单帧动作
```

这是最直接的质量基线，叙事因果由一个模型完整负责。优化方向包括：稳定系统指令与动态回合材料分离、避免重复塞入整本剧本、控制输出长度、减少重复模型往返，并以结构化输出降低解析成本。适合原型期或质量优先的对照实验。

#### 路径 B：快速模型直接成为单帧叙事核心

```text
Agency 状态包 → 快速 Agency Narrative Core → 极短叙事 + 一个动作帧
```

把模型任务限制为“写好此刻的一个剧本动作”，而不是要求它在每回合重述全部设定、长篇分析或规划多步动作。任务变窄不等于去剧本化：输出仍要表达行为发生的即时因果，只是时间跨度和输出范围更小。

当积累了经过筛选的高质量 Agency 回合后，可以探索蒸馏、微调或偏好优化，使快速模型学习角色一致性、细微主动性、动作连续性和短剧本写作。训练目标不应只包含 schema 合法率或动作标签正确率，否则有把模型训练成快速状态机控制器的风险。

路径 B 与路径 C 不是竞争关系而是组合关系：C 的"快速单帧核心"就应当是 B 描述的这个窄任务核心——C 在其外层加低频剧作准备，B 定义核心本身的任务边界与训练路径。试验矩阵将两者分开对照是为了隔离变量，落地时天然合体。

#### 路径 C：快速单帧核心 + 低频长线剧作准备层（建议优先验证）

长线准备层不负责批准每一次动作，而是在合适的空闲时机整理潜流、人物弧线和可能的戏剧方向，形成短小的可选剧作注记。当前 Agency Narrative Core 再根据即时观察判断是否让这种潜流在这一帧显现：

```text
低频准备：近期叙事 → 潜流 / 人物弧线 / 可选剧作注记
                                      ↓
高频单帧：当前视角 + 即时状态 + 剧作注记 → 一帧剧本动作
```

例如，注记可以提出“角色开始隐约区分陪伴职责与个人愿望，但不必每次都戏剧化；允许这种变化偶尔从停顿、挽留或主动发起话题中显露”。它提供创作势能，不预定某个动作必须发生，也不把候选方向自动变成叙事事实。

在动作帧模型下，潜流由此获得双层形态：**已播出的动作帧序列是它的演出层表达**（向后看的连续轨迹——观众可见的存在流），**剧作注记是它的势能层沉淀**（向前看的创作方向——空闲时整理的潜在意图）。一表一里，同属"事件之间的持续存在"。

**与 HDSI Narrative Attractor 的架构同构（评审补充，2026-10-05）**：路径 C 与 HDSI 已实现并实机灰度过的长线叙事指导（longHorizon / Narrative Attractor，rc30–32）是同一个架构模式——"低频整理长线方向 → 以 subtle 语义注入高频写作 → 不预定具体动作"。对应关系：低频准备层 ≈ attractor 的指导生成（dormant/prime/activate 催化）；剧作注记的"提供创作势能，不预定动作必须发生" ≈ prime 的"最小可撤回表达"约束；单帧核心消费注记 ≈ 主叙事消费长线指导注入。这带来两个直接收益：① 架构先例已经过实机验证，C 不是从零探索；② HDSI/HNSU 两模式可复用同一套"指导生成与注入"基建，与"一个账本两个面"的结构呼应。注记的数据格式可参考 attractor 的 stages/firstExpression 结构。

为保持实时性和单一写作主权，剧作注记可以作为只读上下文快照提供给当前回合；不需要让第二个模型逐帧检查或改写正在生成的 Agency Action Frame。若更新准备材料会与当前叙事写作形成资源竞争，可等回合空闲后再更新。HDSI 与 HNSU 仍按前文的运行模式切换假设工作，不因此引入双核心并发写账本机制。

#### 路径 D：快模型起草，强模型逐帧复核

```text
快速模型起草 → 较强模型检查 / 重写 / 批准 → 呈现
```

此路径可以作为离线质量评估、调试工具或少数需要额外审查的场景，但不建议默认用于每一帧。若等待第二个模型，整体延迟会包含两次推理；同时，逐帧复核可能将有意义但不寻常的角色变化收敛成安全、平均的行为。它不应成为 Agency Narrative Core 的常规叙事审批链。

结构性判据补充：D 是五条路径中唯一把第二个模型放进每帧链路的方案，直接违反 §13.1 的"叙事决策单线"判断——即使延迟可接受，这一结构缺陷也足以将其排除在默认动作链之外。

#### 路径 E：投机解码和多头解码

Speculative decoding、Medusa、EAGLE 等方法通过候选 token / 序列及目标模型验证等机制，尝试减少自回归解码的串行步数。它们属于**推理加速**方向，不会自动提升模型的戏剧判断、角色理解或叙事质量；收益还取决于目标模型、推理后端、硬件、输出长度及候选接受情况。

因此，只有在确认单帧任务的主要瓶颈确实位于 decode，并且目标部署栈支持相应方法后，才值得进行对照测试。若主要耗时来自图像编码、长上下文 prefill、网络、排队或设备准备，投机解码未必能解决实际体验瓶颈。

### 13.4 低延迟的系统性优化方向

在不改变“叙事生成动作”这一原则的前提下，可依次尝试：

1. **上下文最小充分化**：保留当前视角、最近动作、必要角色状态与相关长线注记；历史剧本用摘要或检索结果提供，不默认整本注入。
2. **稳定前缀与动态材料分离**：将不变指令、格式约束与每回合变化的观察分区组织，便于支持前缀 / KV 缓存的推理引擎复用重复计算。
3. **缩短输出而非只追求更高 token/s**：只要求完成一个即时剧本节拍和一帧动作所需的叙述与字段，避免冗长解释和重复状态复述。
4. **图像与结构化观察协同准备**：对相机姿态、已有空间数据、上一帧状态等可本地获取的信息，尽可能与图像捕获并行准备；避免无必要地增加一个串行“先视觉模型总结、再叙事模型动作”的调用。
5. **采用有限且稳定的输出结构**：让 `narrative` 保持叙事来源，让 `worldAction` 成为其结构化投影；校验器检查格式、范围和设备能力，不额外发起逐帧模型修复链。
6. **按真实瓶颈选择推理优化**：分别测量 prefill、decode、图片处理、网络和呈现准备；再决定是否尝试量化、前缀缓存、批处理策略或投机解码。
7. **呈现层保持准备就绪**：设备适配、资源加载与渲染资源准备尽量提前；收到动作帧后进行必要校验并呈现，失败则回报真实状态。

以上是可测量的优化方向，不意味着所有项目都应同时启用。缓存需要考虑上下文完全匹配与隔离，结构化约束和推理优化也应在目标模型与后端上验证正确性。

### 13.5 建议的最小试验矩阵

先用相同场景、角色状态、观察材料与动作目标比较不同路径，避免把输入差异误认为模型质量差异：

| 对照 | 推理结构 | 主要回答的问题 |
|---|---|---|
| A | 较强模型单次生成 | 可达到的单帧叙事质量基线与延迟是什么？ |
| B | 快速模型单次生成 | 当前快速模型直接写 Agency Frame 的质量与延迟如何？ |
| C | 快速核心 + 预制剧作注记 | 长线创作引导能否提升自主性，同时不显著增加单帧延迟？ |
| D | 快速草稿 + 强模型逐帧复核 | 质量收益是否值得额外等待，是否导致叙事趋同？ |
| E | 同一目标模型 + 投机解码 / 后端优化 | 瓶颈是否位于 decode，实际端到端收益有多少？ |

评测至少覆盖：

- 观察材料就绪到首个可呈现帧的端到端耗时，以及 TTFT、prefill、decode、校验与呈现准备的分项耗时；
- P50 / P95 延迟、超时与格式失败比例；
- **每帧 token 成本**（评审补充：A 与 B 的每帧成本可能差一个量级，成本是路径排序的第二根轴；C 的价值主张隐含"质量接近 A、成本接近 B"，需要该维度直接验证）；
- 与当前用户视角、空间关系和上一帧动作的连续性；
- 角色行为是否具有清晰的即时叙事因果，而不是只符合静态角色职责；
- 长线潜流是否能偶尔生成有意义的主动行为，又不会让每一回合都被强行戏剧化（此项验证可复用 HDSI 长线指导的灰度经验——subtle 注入下"偶尔显露 vs 每次戏剧化"正是催化器阈值调优时踩过的同一类问题）；
- 对生成质量进行盲评，不以 JSON 合法率或 token/s 替代叙事质量。

### 13.6 推荐的探索顺序

当前较稳妥的方向是：先建立**单模型单帧的强模型 / 快模型基线**；再用上下文压缩、短输出和前缀缓存等方法优化完整链路；随后评估“快速单帧核心 + 低频长线剧作准备层”；最后仅在实测确认 decode 为瓶颈时测试投机解码或相关推理技术。高质量模型的逐帧复核可以保留为对照实验，不建议作为默认动作链。

这只是适合当前构想的优先验证路径。快速模型能力、硬件、推理服务、AR 视觉输入和实际延迟预算都可能改变路径排序，因此不在此冻结模型、推理框架、阈值、输出 schema 或工程阶段。

评审结论记录（2026-10-05）：路径排序经讨论达成一致——**C+B 组合为推荐架构**（C 的剧作注记喂 B 的窄任务单帧核心，且有 Narrative Attractor 先例支撑）；A 永久保留为质量对照组；E 按瓶颈实测条件启用；D 因 §13.1 结构违反与趋同风险留在调试/离线评估场景。

### 13.7 可参考的研究与推理系统资料

以下资料用于理解推理加速机制，不代表 Agency Core 已选定对应模型或框架：

- Leviathan、Kalman、Matias，[*Fast Inference from Transformers via Speculative Decoding*](https://arxiv.org/abs/2211.17192)：投机解码的基础工作之一，讨论在保持目标分布的条件下并行验证候选 token。
- Cai 等，[*Medusa: Simple LLM Inference Acceleration Framework with Multiple Decoding Heads*](https://arxiv.org/abs/2401.10774)：通过额外解码头与候选树减少自回归解码步数。
- Li 等，[*EAGLE: Speculative Sampling Requires Rethinking Feature Uncertainty*](https://arxiv.org/abs/2401.15077)：在特征层面进行候选预测的投机采样方法。
- [vLLM Automatic Prefix Caching 设计说明](https://docs.vllm.ai/en/stable/design/prefix_caching/)：说明复用相同 prompt 前缀 KV cache 以避免重复 prefill 计算的实现思路。
- [vLLM 生产指标文档](https://docs.vllm.ai/en/stable/design/metrics/)：可参考其对请求延迟与推理阶段指标的拆分方式；实际部署仍应以所用版本和后端文档为准。
