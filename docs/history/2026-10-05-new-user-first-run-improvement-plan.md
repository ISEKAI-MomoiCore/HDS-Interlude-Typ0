# HDSI Desktop 新手首次使用改进方案

- **文档日期**：2026-10-05
- **适用范围**：Electron Desktop 首次完成新建剧本/引导之后，到收到并成功投递第一条回复之前
- **当前版本背景**：以 `desktop/src` 当前实现和 `RELEASE-NOTES.md` 为依据
- **文档状态**：方案草案，待产品、交互、运行时实现共同评审

---

## 1. 执行摘要

当前产品第一次成功运行的关键路径是：

```text
创建剧本
→ 加载 Worker
→ 配置模型
→ 启动 SnowLuma
→ 登录 QQ
→ 绑定账号
→ 配置白名单
→ 让剧本进入运行状态
→ 发送第一条消息
→ 等待模型生成
→ 验证回复已投递
```

这条路径的问题不在于单个功能缺失，而在于多个内部概念和外部依赖连续叠加：

- 创建剧本不等于 Worker 已经运行；
- 模型配置可以跳过，但默认配置可能让 Worker 加载失败；
- Worker、bridge、Story、账号、Self ID、OneBot 不是新手熟悉的概念；
- SnowLuma 需要用户在另一个程序中下载、启动和登录；
- 测试连接只验证上游，不等于完整消息链路可用；
- 配置保存后还需要重载 Worker；
- 消息可能进入暂停收件箱、未分配收件箱或投递队列，新手不一定知道去哪看。

本方案的目标是把首次使用改造成一条**可解释、可恢复、可验证的成功闭环**：

```text
每一步都显示当前状态
→ 明确阻塞原因
→ 给出下一步动作
→ 完成后自动验证下一层
→ 出错时保留上下文并支持安全重试
```

---

## 2. 范围与非目标

### 2.1 本次范围

重点处理以下场景：

1. 新建剧本完成后的首次运行；
2. Worker 加载和 bridge 就绪；
3. 模型提供商和密钥配置；
4. SnowLuma / OneBot 外部连接；
5. 账号绑定与 Self ID 校验；
6. 用户、群聊、机器人白名单；
7. 保存配置后的生效机制；
8. 第一条入站消息、模型处理和出站投递；
9. Studio / Connect / Diagnostics 之间的状态一致性。

### 2.2 本次不处理

以下内容不作为第一阶段重点：

- 引导界面的视觉重做；
- Studio 时间线、编排、分析能力的深度改造；
- HDSI 叙事引擎内部算法；
- SnowLuma 本身的安装包、登录协议或 QQ 账号体系；
- 微信通道的完整能力补齐；
- Linux keyring 兼容性的专项改造；
- 新增模型供应商。

## 3. 现状证据与问题分级

### 3.1 P0：会直接阻断首次成功

| 编号 | 问题 | 代码/文档证据 | 用户后果 |
|---|---|---|---|
| P0-1 | 创建剧本后默认为 `paused`，不会自动加载 Worker | `C:\dev\HDSI-desktop-typ-0\desktop\src\main\main.ts:735-739` | 用户以为创建完成即可使用，但实际仍离线 |
| P0-2 | 模型引导允许留空，模板却写入 `primary-*` secret 引用 | `main.ts:1378-1383`；`index.html:约279` | 后续加载 Worker 可能因缺少密钥直接失败 |
| P0-3 | 就绪检查的“模型可用”主要检查 YAML 是否存在 `providers:` | `main.ts:694-699` | 页面显示可用，但实际 endpoint/key/model 可能不可用 |
| P0-4 | SnowLuma 不由桌面端启动，用户必须手动下载、启动、登录和回应用检测 | `RELEASE-NOTES.md:16` | 外部依赖链断裂后，用户不知道应该修哪一层 |
| P0-5 | 测试连接只探测 OneBot 上游登录信息，不验证完整消息闭环 | `app.js:861-870`；`main.ts:635-637` | “测试成功”后仍可能无法收消息或发回复 |

### 3.2 P1：不会必然阻断，但很容易造成错误判断

- Worker、bridge、Story 等内部术语没有持续转换为用户语言；
- 模型配置中的服务类型、endpoint、model ID、API Key、secret alias 需要用户自行推断；
- 保存配置后必须重载 Worker，当前容易被理解为已立即生效；
- QQ 账号、机器人账号、Self ID、聊天对象和 Story 绑定账号容易混淆；
- 用户白名单、群聊白名单、机器人账号白名单是三套规则；
- `running / muted / paused` 的行为与普通在线/离线状态不同；
- 未分配收件箱与暂停收件箱需要额外“回放”概念；
- Logs、Diagnostics、Console、Deliveries 分散，排错路径不连续；
- 微信入口看起来与 QQ 同等完整，但发行说明已声明能力边界。

### 3.3 P2：会增加探索成本

- 默认进入专业化 Studio 工作台，而不是“当前剧本/当前运行状态”页面；
- 中英文术语和内部架构术语混合；
- 状态信息存在，但没有集中形成“首次成功进度”；
- 错误信息多为结果描述，缺少检查顺序和下一步动作。

## 4. 产品目标与可验收指标

### 4.1 核心目标

新手完成引导后，应该可以在一个连续流程中回答以下问题：

1. 当前是否已经创建了 Story？
2. Worker 是否真的运行？
3. 模型是否配置并可调用？
4. 外部渠道是否在线？
5. 哪个账号正在接收消息？
6. 哪些用户或群被允许？
7. 第一条消息现在处于哪个阶段？
8. 如果失败，下一步应该做什么？

### 4.2 建议验收指标

以下指标用于验收，不要求首版全部做成埋点：

- 创建剧本后，用户不需要猜测“下一步是什么”；
- 未配置模型时，不允许出现“看起来已就绪但加载失败”的矛盾状态；
- 用户能在 10 秒内看出 Worker、模型、渠道、账号、白名单五项状态；
- “测试连接成功”后，界面明确说明它验证了什么、没有验证什么；
- 保存配置后，界面明确显示“尚未对当前 Worker 生效”或已自动重载；
- 第一条消息从接收至投递失败，始终有可追踪的状态记录；
- 出现失败时，至少提供一个直接动作：配置、重载、重试、查看详情或回放收件箱；
- P0 失败不能只依赖用户主动打开 Logs 才能发现。

## 5. 总体方案：建立“首次运行控制台”

不建议继续把首次使用完全分散在 Studio、Connect、Diagnostics、Console 和配置弹窗中。建议增加一个轻量级的**首次运行控制台**，它不是新的复杂页面，而是连接页上方的统一状态条和步骤卡。

### 5.1 统一五项核心状态

```text
运行环境     Worker / bridge
模型         provider / secret / API 探测
平台渠道     SnowLuma / OneBot
账号端点     Self ID / Story 绑定
消息权限     用户、群聊、机器人规则
```

每项状态必须有以下结构：

```text
状态：未完成 / 检查中 / 已就绪 / 被阻塞 / 运行中 / 需要重载
原因：一句用户能理解的话
动作：一个主要按钮
详情：可展开的技术信息
```

例如：

```text
模型：被阻塞
原因：配置引用了 primary-key，但本机尚未录入该密钥
动作：录入 API Key
详情：打开模型配置 / 打开密钥库 / 查看配置来源
```

### 5.2 使用“任务状态”而不是只显示“检查结果”

建议状态枚举：

```text
not-started
checking
ready
blocked
running
needs-reload
degraded
failed
```

其中：

- `ready`：该步骤具备运行条件；
- `running`：该步骤正在工作；
- `needs-reload`：配置已经保存，但当前 Worker 尚未使用新配置；
- `degraded`：可以继续运行，但能力不完整，例如模型未配置或白名单为空；
- `blocked`：必须完成某项操作才能继续；
- `failed`：已执行但失败，需要重试或修复。

不要把所有问题都折叠成红色的“失败”。

## 6. 分阶段改进方案

## 6.1 阶段一：创建完成后的运行闭环（P0）

### 目标

解决“创建成功但还不能用”的断层。

### 建议行为

创建剧本成功后，不要只切换到 Connect 页面，而应执行以下流程：

```text
创建成功
→ 自动选中当前 Story
→ 打开首次运行控制台
→ 立即执行一次状态检查
→ 根据结果决定是否自动加载 Worker
```

推荐策略：

1. 如果模型密钥和必要配置完整，自动加载 Worker；
2. 如果模型配置缺失，不要让 Worker 加载报一个底层 secret 错误；
3. 显示“运行环境可启动，但模型尚未配置”或“需要先配置模型”；
4. 给出唯一主动作，不让用户在多个页面之间寻找入口。

### 两种实现路线

#### 路线 A：严格阻塞

创建后先检查模型配置，不完整就不加载 Worker，并显示：

```text
还不能启动
原因：模型提供商未完成
下一步：打开模型配置
```

优点是状态简单，缺点是用户无法先查看 Worker 或其他配置。

#### 路线 B：降级启动（推荐）

允许 Worker 在模型未配置时启动，但状态明确为：

```text
Worker 已运行
模型未配置
当前不能处理需要模型生成的消息
```

优点是运行环境、Console 和连接诊断可以先验证；缺点是运行时必须支持“无模型配置”的降级状态。

**建议首版采用路线 A，后续具备完整降级语义后再考虑路线 B。**

### 验收标准

- 创建完成后，页面明确显示 Story 名称和当前运行状态；
- 用户不需要自行猜“加载 Worker”按钮在哪里；
- 缺少模型时，错误指向模型配置，而不是只显示 Worker 加载失败；
- Worker 加载成功后，bridge 状态在同一张卡片中可见；
- 如果加载失败，提供“查看详情”和“重新加载”动作。

---

## 6.2 阶段二：修正模型配置和密钥语义（P0/P1）

### 目标

让“模型配置是否可用”与“页面上是否存在 providers 字段”一致。

### 方案 A：不完整配置不写入 provider（推荐）

当用户在创建时跳过模型配置时，不生成以下未完成引用：

```yaml
$secret:primary-endpoint
$secret:primary-key
$secret:primary-model
```

或者生成明确的 disabled / pending provider，而不是一个看起来启用但无法解析的 provider。

### 方案 B：保留引用但在创建后立即标记阻塞

如果为了兼容旧配置必须保留 `$secret:` 引用，则创建后立即扫描：

```text
引用的 secret 别名是否存在
endpoint 是否非空
model 是否非空
provider 是否启用
```

缺失项应在 Connect 页面显示为阻塞，不等到 `stories:load` 时才失败。

### 模型表单改进

将模型配置拆成用户能理解的三层：

```text
1. 选择服务商
2. 选择或填写模型
3. 填写 API Key
```

高级选项中再展示：

```text
自定义 endpoint
协议模式
secret alias
原始 YAML
```

默认不要让普通用户先接触 `$secret:别名`。

### 增加“验证模型”动作

“验证模型”至少分两级：

```text
配置检查：字段、别名、endpoint 格式
连通性检查：实际发起最小请求
```

显示清楚：

```text
配置完整，但尚未测试 API
```

和：

```text
API 请求成功，模型返回可用
```

两者不能都叫“模型可用”。

### 验收标准

- 未录入 key 时，模型状态必须是 `blocked` 或 `degraded`，不能是 `ready`；
- provider 存在但 endpoint/model/key 不完整时，ready check 必须标红或明确降级；
- 用户可以从错误卡片直接进入正确的配置分区；
- 测试成功后显示测试时间和测试对象；
- 不要求用户理解 `$secret:` 才能完成正常配置。

## 6.3 阶段三：SnowLuma / OneBot 分层诊断（P0/P1）

### 目标

把“连接失败”拆成可定位的检查链。

### 建议的检查顺序

```text
A. SnowLuma 是否已安装或可找到
B. SnowLuma 进程是否运行
C. 管理页面是否可访问
D. QQ 是否已登录
E. OneBot WebSocket 是否启用
F. endpoint 是否可连接
G. get_login_info 是否成功
H. 返回的 Self ID 是否与绑定账号一致
I. Worker 是否连接桌面 bridge
J. 是否收到入站消息
K. 是否成功完成一次出站投递
```

每一步都应显示：

```text
已通过 / 未执行 / 被阻塞 / 失败
检测时间
检测目标
失败原因
下一步动作
```

### SnowLuma 路径处理

当前只检查少量硬编码路径，建议改为：

1. 首次启动时允许用户指定 SnowLuma 目录；
2. 记录用户选择的路径；
3. 优先使用记录路径检测；
4. 再使用默认路径和进程名作为补充检测；
5. 如果进程运行但路径未知，应显示“已运行，路径未识别”，而不是“未安装”。

### 是否自动启动

短期不要求 HDSI 自动启动 SnowLuma，但应提供：

```text
打开 SnowLuma 文件夹
打开 launcher.bat 所在目录
重新检测
查看外部连接帮助
```

如果未来支持启动，必须在启动前显示外部程序路径和权限说明。

### 验收标准

- SnowLuma 未运行时，用户能看到明确的启动步骤；
- SnowLuma 运行但 QQ 未登录时，不显示为“连接完成”；
- endpoint 可访问但 Self ID 不匹配时，指出具体不匹配的两个值；
- 上游探测成功后，界面明确写出“仅验证 OneBot 登录信息”；
- 第一条入站和出站消息分别有可观察的状态。

## 6.4 阶段四：账号绑定和白名单语义收敛（P1）

### 账号绑定

表单中建议把字段改为面向对象的命名：

| 当前容易混淆的概念 | 建议显示名称 |
|---|---|
| 账号 / UIN | 外部机器人账号 ID |
| Self ID | 上游返回的机器人账号 |
| 绑定账号 | 将哪个机器人账号交给当前 Story 处理 |
| 连接地址 | OneBot WebSocket 地址 |
| 访问令牌 | OneBot access token |

绑定前显示确认摘要：

```text
当前 Story：xxx
外部平台：QQ / OneBot v11
上游账号：123456789
将绑定到 Story：xxx
```

如果上游返回的 Self ID 与输入账号不同，应要求用户确认或直接阻止绑定。

### 测试按钮拆分

将“测试连接”拆为：

```text
测试 endpoint
读取上游登录信息
验证账号绑定
测试 Worker 接收
发送测试消息
```

不要用一个绿色的“上游连接成功”代表全链路成功。

### 白名单

连接页只显示用户最需要的摘要：

```text
私聊权限：允许 2 个用户 / 允许所有人 / 拒绝全部
群聊权限：允许 1 个群 / 未配置
机器人权限：未启用过滤
```

高级配置中再展开三类列表。

空白名单必须显示安全含义：

```text
当前允许所有人私聊此角色
```

而不是只显示：

```text
白名单为空
```

### 验收标准

- 用户能分辨机器人账号和聊天对象；
- 绑定前能看到 Self ID 和 Story 的对应关系；
- 空白名单的风险在状态摘要中持续可见；
- 用户、群聊、机器人三套规则分别有解释和示例；
- 未通过白名单的消息能显示被哪条规则拒绝。

---

## 6.5 阶段五：配置生效与 Worker 生命周期（P1）

### 目标

消除“已保存但未生效”的隐性状态。

### 推荐方案

保存配置后，立即出现持久化状态条：

```text
配置已保存，但当前 Worker 仍使用旧版本。
[立即重载 Worker] [稍后处理]
```

如果配置涉及必须重载的项，应在保存前说明：

```text
本次修改会影响模型/账号/白名单，需要重载 Worker 才能生效。
```

### 重载流程

点击“立即重载 Worker”后：

```text
保存确认
→ 卸载当前 Worker
→ 加载新配置
→ 等待 bridge ready
→ 再次执行就绪检查
```

整个过程中不能只显示一个旋转图标，应显示阶段：

```text
正在停止旧 Worker
正在编译配置
正在启动 Worker
正在等待 bridge
正在验证账号
已完成
```

### 验收标准

- 用户不需要去 Story 列表寻找卸载/加载按钮；
- 重载完成前状态显示 `needs-reload` 或 `checking`；
- 重载失败时保留失败前的配置版本和错误详情；
- 重载成功后，状态卡显示当前配置已生效的时间。

---

## 6.6 阶段六：第一条消息的可观测性（P1）

### 目标

让用户知道消息没有消失，而是在处理链中的哪一步。

### 建议增加消息链路状态

每条首次测试消息至少显示：

```text
已接收
→ 已路由到 Story
→ 已通过权限检查
→ 已进入 Worker
→ 模型处理中
→ 叙事已提交
→ 已加入投递队列
→ 上游已确认 / 投递失败
```

失败时展示：

```text
失败阶段
失败原因
是否可重试
重试动作
查看详情
```

### 增加“一键发送测试消息”

连接页应允许用户发起一次明确的测试：

```text
发送测试消息
```

测试消息必须标记为测试事件，避免污染正常故事记录，或者提供独立测试 Story / 测试会话。

### 收件箱提示

对于 `paused`、`muted`、未绑定账号等情况，状态条必须直接说明：

```text
消息已收到，但当前处于暂停状态，已进入收件箱。
[回放收件箱] [切换为运行]
```

不要让用户先去日志里发现消息被缓冲。

### 验收标准

- 第一条消息有唯一 ID 或可追踪记录；
- 入站、模型、出站三个阶段都能被观察；
- 消息进入收件箱时，主页面有明确提示；
- 投递失败时可以区分上游失败、权限失败、Worker 失败和模型失败；
- 用户不需要先理解 Timeline、Delivery、Inbox 的内部结构。

## 8. 技术实施建议

### 8.1 统一状态来源

不要在 Renderer 中分别推断“模型可用”“渠道在线”“账号绑定”。建议主进程提供一个统一快照：

```ts
interface FirstRunReadiness {
  storyId: string
  overall: 'not-ready' | 'ready' | 'degraded' | 'running'
  worker: ReadinessItem
  model: ReadinessItem
  channel: ReadinessItem
  account: ReadinessItem
  permissions: ReadinessItem
  lastMessage?: MessageTrace
}

interface ReadinessItem {
  status: 'not-started' | 'checking' | 'ready' | 'blocked' | 'failed' | 'needs-reload' | 'degraded'
  summary: string
  detail?: string
  actions: Array<'configure' | 'load' | 'reload' | 'retry' | 'replay' | 'open-logs'>
  checkedAt?: string
}
```

Renderer 只负责呈现，不要再通过简单正则自行判断真实运行条件。

### 8.2 错误使用稳定错误码

建议为首次运行错误提供稳定 code，例如：

```text
MODEL_SECRET_MISSING
MODEL_ENDPOINT_INVALID
MODEL_PROBE_FAILED
WORKER_NOT_LOADED
BRIDGE_TIMEOUT
SNOWLUMA_NOT_FOUND
SNOWLUMA_NOT_RUNNING
ONEBOT_ENDPOINT_UNREACHABLE
SELF_ID_MISMATCH
ACCOUNT_NOT_BOUND
PRIVATE_USER_NOT_ALLOWED
STORY_PAUSED
DELIVERY_FAILED
```

界面根据错误码给用户文案，日志保留详细技术信息。

### 8.3 保留技术详情，但默认折叠

新手默认看到：

```text
模型密钥未配置
[去配置]
```

展开后才看到：

```text
引用别名：primary-key
配置文件：...
编译阶段：StoryConfigCompiler
```

这样既不损失排错能力，也不会让普通用户一开始面对内部实现。

## 10. 风险与取舍

### 风险一：自动加载 Worker 可能消耗资源

因此不建议无条件自动加载所有 Story。可以只对刚创建的当前 Story 自动尝试，失败后保持未运行。

### 风险二：实际模型探测会消耗费用

“验证模型”应提供：

- 仅配置检查；
- 用户主动确认后的最小 API 请求；
- 明确提示可能产生费用。

### 风险三：自动重载可能中断正在进行的叙事

如果 Story 已经运行，保存配置后应采用：

```text
提示需要重载
→ 用户确认
→ 保存当前状态
→ 受控重载
```

不要默认在有未完成消息时强制重启。

### 风险四：支持过多通道会增加首屏复杂度

首次使用默认只突出推荐路径：

```text
QQ + OneBot v11 + SnowLuma
```

其他通道放入“其他平台”或高级选项，并明确能力状态。

## 11. 最小可交付版本（MVP）

如果只能做一轮修复，建议只做以下六项：

1. **创建完成后自动进入当前 Story 的连接状态，并立即执行就绪检查。**
2. **模型 secret 预检查，禁止出现“模型显示可用但 Worker 加载失败”。**
3. **连接页提供一键重载 Worker，保存配置后显示 `needs-reload`。**
4. **SnowLuma 检查拆成安装、运行、上游登录、Self ID 四层。**
5. **第一条消息提供入站、模型、出站三段状态。**
6. **paused、muted、未绑定账号消息提供主界面可见的下一步动作。**

这六项不需要重做整个 Studio，但能显著减少新手第一次使用时的卡死感和误判。

## 12. 交付验收结论

只有同时满足以下条件，才建议认为“新手首次使用闭环”达到可发布标准：

```text
创建的 Story 能被明确选中
Worker 能被加载或明确解释为什么不能加载
模型状态与真实可运行条件一致
SnowLuma / OneBot 的失败层级可定位
账号绑定能校验 Self ID
白名单风险和作用清晰
保存后的配置生效状态明确
第一条消息全链路可追踪
失败时至少有一个直接修复动作
```

最终产品目标不是让新手理解所有 HDSI 内部机制，而是让他在不阅读源码和内部文档的情况下，能够完成：

```text
创建一个角色
连接一个账号
发送一条消息
看到角色成功回复
```

## 13. 初稿审查记录

### 13.1 审查结论

**审查结论：通过作为产品/技术讨论稿，不建议直接作为开发排期单。**

当前方案已经覆盖首次使用的主要断点，且 P0/P1/P2 分级和验收标准基本完整。它适合作为下一步拆分需求、确定交互方案和安排实现顺序的基线。

### 13.2 已确认的优点

1. **范围明确**：没有把 Studio 深层能力和首次运行问题混在一起；
2. **问题来自实际源码**：重点问题均能对应到当前 Renderer、Main、Config Compiler 或发行说明；
3. **优先级合理**：先处理 Worker、模型、SnowLuma、消息闭环，再处理术语和入口；
4. **方案不是单纯换文案**：同时涉及状态模型、错误码、IPC 数据结构、检测链和重载生命周期；
5. **有验收标准**：可以继续转成测试用例和人工可用性测试；
6. **保留高级能力**：没有为了新手体验而删除 Console、YAML、日志等专业排错能力。

### 13.3 需要产品先拍板的事项

#### 决策 D1：模型未配置时，Worker 是否允许启动？

文档暂时推荐“严格阻塞”路线，即先完成模型配置再加载 Worker。这个决定会影响：

- Worker 生命周期；
- ready check 的状态定义；
- 首次运行控制台的主按钮；
- 未来是否支持无模型情况下查看 Console 或进行渠道测试。

**建议首版采用严格阻塞**，因为当前配置编译器已经会因缺少 secret 而失败；先统一行为比立即引入降级运行更安全。

#### 决策 D2：模型连通性测试是否默认发起真实 API 请求？

真实测试可能产生费用，也可能触发供应商限流。建议默认先做本地配置检查，真实 API 测试由用户主动点击并明确确认。

#### 决策 D3：是否允许保存配置后自动重载 Worker？

对于未运行的 Story 可以自动加载；对于正在运行且有未完成消息的 Story，建议只提示并由用户确认，避免隐式中断叙事。

#### 决策 D4：首次使用是否只突出 QQ + SnowLuma？

如果当前发布版本最可靠的是 QQ 路径，应将其作为推荐路径，其他通道显示为“其他平台/部分支持”，避免界面承诺超过实际能力。

### 13.4 方案中仍需补充的工程细节

这些问题不影响方案成立，但在进入开发前必须补齐：

1. **配置版本**：需要定义配置保存版本、Worker 实际使用版本和重载完成版本，避免只用时间戳推断；
2. **旧剧本迁移**：已有 Story 可能存在旧的 `$secret:`、账号注入或 OneBot 配置，需先定义兼容策略；
3. **错误码归属**：错误码应由 Main/Runtime 产生，Renderer 不应根据错误文本二次猜测；
4. **消息追踪 ID**：入站、模型调用、叙事提交和出站投递需要共用一个 trace ID；
5. **重试语义**：明确模型重试、投递重试、收件箱回放是否会造成重复消息；
6. **测试消息隔离**：一键测试消息必须避免污染正式时间线，或提供明确的测试标记和清理策略；
7. **SnowLuma 检测权限**：Windows 进程检测、路径访问、外部 launcher 调用需要验证打包版权限；
8. **多 Story 资源限制**：自动加载不能绕过现有 `maxWorkers` 限制，需要给出资源不足时的用户动作；
9. **安全边界**：endpoint、token、API Key、日志和测试消息不能进入普通 UI 文案、导出文件或错误堆栈；
10. **国际化准备**：如果未来保留中英文 UI，错误码和状态枚举应与显示文案分离。

### 13.5 对当前方案的修改建议

进入开发前，建议把本文再拆为三份执行文档：

```text
A. 产品状态与交互规格
B. Main / Runtime / IPC 技术改造任务
C. 首次使用测试与发布验收清单
```

当前文档已经适合作为 A、B、C 三份文档的共同上游，但还不应直接当作工程 issue 列表。下一步每个 P0 项应补充：

```text
负责人
涉及文件
IPC/API 变更
数据迁移要求
测试用例
完成定义
```

### 13.6 审查后的 MVP 顺序

经审查，建议把最小实现进一步收敛成以下顺序：

1. **先修正 ready check 和 secret 预检查**，解决“假就绪”；
2. **创建后自动选中当前 Story，并提供明确的加载/重载主动作**；
3. **实现统一的首次运行状态快照和稳定错误码**；
4. **把 SnowLuma / OneBot 探测拆成分层状态**；
5. **加入第一条消息的 trace ID 和入站/模型/出站状态**；
6. **最后再做术语、默认入口和配置表单的降噪改造**。

这样可以先解决真实阻断和错误判断，再改善认知成本，避免先做大面积 UI 重构但底层状态仍然不一致。
