> 文档状态：实施中的主设计文档  
> 最后整理：2026-09-02  
> 项目代号：**typ-0**  
> 对应桌面工程：`desktop/`  
> 对应叙事运行时：`C:\dev\HDS-Interlude\plugins\hds-interlude`

## 0. 一句话定义

**typ-0 是 HDSI 的本地桌面宿主。**

它不替代 HDSI 的叙事、记忆、日程、模型调用或数据库逻辑；它负责把这些能力组织成一个可管理、可多开、可暂停、可观察、可接入 QQ/微信等渠道的桌面应用。

最终用户看到的不是“一堆 Koishi 配置和日志”，而是一个可以管理多个独立角色故事的桌面工作台：每个故事有自己的运行状态、收件箱、时间线、日程、模型配置与渠道绑定；角色仍由 HDSI 驱动生活与对话。

---

## 1. 最终要实现什么

typ-0 的终态不是再造一个聊天窗口，而是一个以“故事”为单位的本地 AI 角色运行环境。

用户应当能够：

1. 创建多个独立故事，例如“水濑（QQ 账号 A）”“另一位角色（QQ 账号 B）”。
2. 为每个故事独立保存其 HDSI 数据、配置、模型选择、角色资料与运行状态。
3. 将一个外部账号或渠道绑定到一个故事；同一账号不会被两个故事同时处理。
4. 用 `运行 / 静音 / 暂停` 管理角色生活节奏，而不是通过重载插件或修改数据库硬切换。
5. 在静音或暂停期间安全积累用户消息；恢复后按原始顺序重新交给 HDSI，避免消息丢失或重复写作。
6. 以时间线方式观察剧本、场景、事实、日程预案、投递结果与模型用量。
7. 在不暴露密钥的前提下配置模型、渠道与插件。
8. 将一个故事目录备份、复制、迁移到另一台电脑；密钥仍保留在本机安全存储中。
9. 最终通过 SnowLuma / OneBot 等适配层接收真实 QQ、微信或其他渠道事件，并将 HDSI 的输出可靠投递回渠道。
10. 在 Studio、传统 Logs 与 Koishi 兼容控制台之间切换，同时保持当前故事、定位对象和运行状态一致。

最终体验可以概括为：

```text
外部渠道消息
      │
      ▼
typ-0 账号路由、状态机与可靠收件箱
      │
      ▼
每个故事独立运行的 HDSI Worker
      │
      ├── 剧本、记忆、Schedule Preplan、Alter、模型调用
      │
      ▼
typ-0 时间线 / 用量 / 状态观察
      │
      ▼
外部渠道投递（QQ / 微信 / 其他）
```

## 2. 核心边界：谁负责什么

这是 typ-0 后续不会轻易改变的原则。许多桌面端复杂度，来自把同一份业务规则同时写在 GUI、宿主和 HDSI 中；typ-0 必须避免这种双重权威。

| 层级 | 唯一职责 | 不负责 |
| --- | --- | --- |
| **HDSI Worker** | 角色叙事、主提示词、模型调用、记忆、事实、场景、Alter、日程预案、剧本数据库、是否回复 | 多故事管理、桌面 GUI、密钥 UI、账号绑定策略 |
| **typ-0 主进程** | Worker 生命周期、故事元数据、账号绑定、运行状态、收件箱、密钥引用、配置编译、只读投影、渠道路由 | 直接推演角色剧情、直接改写 HDSI SQLite 业务表 |
| **typ-0 渲染层** | 展示、配置编辑、操作入口、可视化与反馈 | 保存密钥明文、直接访问数据库、直接控制子进程 |
| **渠道适配器** | 将 QQ/微信等原始事件转换为统一输入；执行真实投递 | 角色记忆、剧情判断、故事状态机 |

### 2.1 不可违反的约束

- **HDSI 是叙事事实唯一来源。** 角色“做过什么、知道什么、下一步怎样发展”只能以 HDSI 的数据与逻辑为准。
- **桌面端不直接写 HDSI 的 SQLite 业务表。** 所有叙事写入都走 Worker 的受控入口；桌面端只读投影。
- **浏览器/Renderer 不保存密钥。** 密钥仅放在 Electron 主进程调用的系统安全存储中。
- **同一外部账号最多绑定一个故事。** 冲突必须显式提示，不允许暗中抢占。
- **静音不是暂停。** 静音仍让角色生活与自动推进运行，只把外部消息放入收件箱；暂停停止新的 HDSI 自动工作与剧本推进。
- **队列只在 HDSI 确认接收后确认消费。** 不能因为“尝试转发过”就删除用户消息。
- **桥接仅在桌面 Worker 环境启用。** 普通 Koishi/HDSI 插件安装不应感知 typ-0 的存在。

### 3.3 当前可运行程度

目前已经具备“桌面宿主 + 单故事 HDSI Worker + IPC bridge + 受控回放 + HDSI 只读时间线投影”的垂直切片。

仍未形成完整终端产品的部分主要是：

- 真实 SnowLuma/QQ/微信输入尚未接入到桌面路由器；
- HDSI 的 `delivery` 事件当前会回到桌面端 GUI/日志，尚未由桌面端投递给真实渠道；
- 密钥、模型、Koishi 插件、渠道绑定等后端能力尚未完整做成 GUI；
- 当前时间线是可读取的列表/详情面板，不是最终的多轨缩放画布；
- 打包、迁移、崩溃恢复、适配器安装与升级流程尚未产品化。

### 3.4 产品交互定位：HDSI Studio，而不是聊天窗口

typ-0 的界面应采用 Ableton Live、FL Studio 等宿主软件的核心思想：**让多个异步系统在同一工作台中保持可见、可定位、可控制**。这里借鉴的是宿主软件的信息组织方式，不是复制音乐软件的视觉外观。

HDSI 与这种结构天然匹配：

- 故事是一个工程（Project）；
- HDSI Worker 是故事运行引擎；
- QQ、微信、SnowLuma、OneBot 是输入/输出设备；
- 模型提供商是计算资源；
- 剧本、场景、事实、Overlay、Alter 与 Schedule Preplan 是不同时间轨道；
- 用户消息与角色投递是时间轴上的可见事件；
- Inspector 用来解释某个事件为什么发生、由什么数据支持；
- 底部 Detail Panel 用来观察调用、日志、投递和原始结构。

最终界面应给人一种“角色正在这里持续生活”的感觉：用户既能快速确认系统是否正常，也能在需要时深入到某一次模型调用、一个事实变化或一段日程预案。

高度集成不等于把所有实现写进一个模块。typ-0 需要保持：

- **体验上集成**：用户在一个工作台内完成观察、选择、配置、路由和诊断；
- **架构上分层**：Renderer、桌面主进程、HDSI Worker、渠道适配器各自只有一个权威职责；
- **数据上关联**：不同面板围绕同一个故事、时间范围和选中对象联动；
- **性能上按需**：只读取和绘制当前窗口真正需要的数据。

### 3.5 三个可切换的顶层主界面

typ-0 提供三个互相独立、可随时切换的主界面（Surface）：

| 主界面 | 主要用途 | 面向对象 |
| --- | --- | --- |
| **Studio** | 故事多轨时间线、状态分析、用户/模型/渠道关系、图形化配置与诊断 | 日常使用、角色观察、深度分析 |
| **Logs** | 传统连续滚动日志、搜索、过滤、暂停跟随、导出与错误定位 | 部署、调试、兼容传统 Koishi 使用习惯 |
| **Koishi** | 打开当前故事 Worker 对应的 Koishi Console，配置和连接其他兼容插件 | 高级配置、第三方插件、适配器与生态兼容 |

三个 Surface 是顶层信息架构，不是 Studio 里的三个普通标签页。顶栏始终保留故事、三态、Worker、渠道、收件箱与错误状态；其下的主体区域根据 Surface 完整切换。

推荐切换方式：

- 顶栏左侧提供清晰的 `Studio / Logs / Koishi` 切换器；
- 提供快捷键，例如 `Ctrl+1 / Ctrl+2 / Ctrl+3`；
- 当前故事切换后，三个 Surface 都自动切到该故事的上下文；
- 每个 Surface 独立记住滚动位置、过滤器、选中对象和面板布局；
- 从 Studio 的错误、调用或插件对象可一键跳转到 Logs/Koishi，并带入故事与定位条件；
- 返回 Studio 时恢复原来的时间范围和 SelectionContext。

#### Surface 之间的职责边界

- Studio 的 Diagnostics 展示结构化、可关联的诊断结果；Logs 展示忠实的传统日志流。
- Studio 的 Configure 提供 HDSI/typ-0 经过整理的配置体验；Koishi Surface 提供第三方插件的完整兼容入口。
- Logs 不解释或修改剧情；它只显示来源、级别、时间和原始内容。
- Koishi Surface 不成为 typ-0 的主导航，也不直接获得桌面主进程权限；它只连接当前故事隔离运行的 Koishi Worker。
- Blind/失明模式对三个 Surface 同时生效。启用后 Logs 和 Koishi Surface 根据 Blind 规则锁定或隐藏，不能通过切换界面绕过内容屏蔽。

#### 顶层状态与深链接

Surface 跳转使用受控深链接对象：

```ts
interface SurfaceLocation {
  surface: 'studio' | 'logs' | 'koishi'
  storyId: string
  workspace?: string
  entity?: { type: string; id: string }
  timeRange?: { from: number; to: number }
  logQuery?: string
  pluginName?: string
  koishiPath?: string
}
```

例：Studio 中选中一次失败投递并选择“查看原始日志”，typ-0 切换到 Logs Surface，自动过滤当前故事、对应时间窗口和 delivery/request ID。选择“打开适配器配置”则切换 Koishi Surface，并导航至对应插件页面。

### 3.6 Studio Shell：五个稳定界面区域

typ-0 采用五区宿主布局。第一阶段不追求任意悬浮、任意嵌套的窗口系统，以稳定、可恢复、可理解的布局为主。

```text
┌────────────────────────────────────────────────────────────────────┐
│ 顶栏：故事 / 三态 / 故事时间 / 渠道 / 收件箱 / 模型状态 / 全局操作 │
├────────────┬────────────────────────────────────┬──────────────────┤
│            │                                    │                  │
│ Browser    │ Arrangement / 当前主工作区         │ Inspector        │
│ 对象浏览器 │ 多轨时间线、路由或配置画布         │ 选中对象检查器   │
│            │                                    │                  │
├────────────┴────────────────────────────────────┴──────────────────┤
│ Detail Panel：详情 / 调用 / 投递 / 日志 / 数据观察 / 错误          │
└────────────────────────────────────────────────────────────────────┘
```

#### 顶栏：Transport & Global Status

顶栏持续显示当前故事最关键的控制与健康信息：

- 当前故事名称、头像和故事切换；
- `运行 / 静音 / 暂停` 三态控制；
- HDSI Worker：启动中、就绪、忙碌、故障、已卸载；
- 当前故事时间、时区与“现在”指针；
- 渠道在线状态及当前绑定账号；
- 收件箱积压数量；
- 当前模型调用状态与最近延迟；
- 当日 Token/费用摘要；
- Blind/失明模式状态；
- 全局搜索、命令面板和紧急停止入口。

三态控制可以借鉴宿主软件的 Transport 区域，但图标与文案必须表达 HDSI 自己的语义，不能让用户误以为“暂停”只是停止界面动画。

Blind/失明模式应成为明确的故事级运行状态。启用后界面收起剧本、日志、指令与内容详情，只保留经过允许的健康心跳、连接状态和退出 Blind 模式的入口。普通设置页仍可配置这一功能，但运行中必须在顶栏持续可见。

#### 左侧 Browser：故事对象与资源浏览器

Browser 展示经过整理的逻辑对象，而不是默认暴露磁盘目录：

```text
故事
├─ 角色资料
│  ├─ Canon
│  ├─ Perspective
│  ├─ 发言与行为规则
│  └─ 当前 Overlay
├─ 用户与关系
├─ 渠道与账号
├─ 模型与提供商
├─ Prompt 与模板
├─ 本地贴纸及媒体
├─ 备份与版本
└─ 高级文件视图
```

高级文件视图可以显示这些对象对应的真实文件，但只能作为高级管理入口。普通用户操作 Canon、Perspective、模型或渠道时，应面对明确的业务对象，而不是猜测 YAML 与目录结构。

Browser 支持搜索、类型过滤、收藏和最近使用。拖放能力应逐项开放，例如将渠道账号拖到故事上可以进入绑定确认，将本地素材拖入贴纸库可以进入导入流程。所有拖放动作都必须先显示将要发生的业务操作，不能直接产生不可见的文件覆盖。

#### 中央 Workspace：主工作区

中央区域承载当前任务，而不是永远固定为一个页面。核心工作区包括：

- `Arrangement`：故事多轨时间线，默认主视图；
- `Overview`：多故事健康状态与资源概览；
- `Routing`：渠道、账号、故事与参与者的绑定关系；
- `Models`：提供商、模型用途、回退链路和调用表现；
- `Configure`：角色、HDSI 功能和运行设置；
- `Diagnostics`：投递、调用、缓存、错误与性能分析。

工作区切换不应销毁用户的时间范围、轨道开关、选中对象和面板尺寸。每个故事保存自己的工作区布局；应用也提供一个可恢复的默认布局。

#### 右侧 Inspector：解释当前选择

Inspector 始终围绕当前选中对象工作。它不重复中央画布，而是解释对象的属性、来源、状态和关联。

例：选中一条主角回复时，Inspector 可以显示：

- 发生时间、处理时间、投递时间；
- 私聊/群聊、渠道、账号、参与者；
- reply mode、引用对象、媒体动作；
- 所属场景、当时有效的日程与 Alter；
- 对应模型调用、用量与恢复重写情况；
- 投递是否成功、渠道返回的消息 ID；
- 可执行的安全操作，例如复制、定位来源、重试允许重试的投递。

选中一个事实时，Inspector 则显示事实类型、内容、来源条目、首次出现、最后确认、是否仍活跃，以及它被哪些场景或计划引用。

#### 底部 Detail Panel：深度观察区

底部面板提供可切换的技术细节：

- 内容详情；
- 模型调用与 Token；
- 渠道投递与回执；
- 运行日志；
- Prompt/响应诊断；
- 只读数据观察器；
- 错误栈与恢复建议。

面板可以折叠、调整高度或移动到右侧，但第一阶段不实现任意浮动窗口。关闭 Detail Panel 不会停止后台数据采集，只停止不必要的渲染与高频订阅。

### 3.7 Arrangement：故事多轨时间线

Arrangement 是 typ-0 最有辨识度的界面，也是用户理解角色连续生活的主要方式。

#### 三种时间域

时间线上明确区分：

| 时间域 | 意义 | 推荐视觉 |
| --- | --- | --- |
| 过去 | 已发生并保存在 HDSI 中的剧本、消息、事实与投递 | 实色块、清晰边界 |
| 现在 | 当前消息缓冲、模型调用、写作、打字等待和投递 | 醒目的 Now 指针、轻微活动状态 |
| 未来 | Schedule Preplan、Intent、承诺、候选后续与自动推进计划 | 半透明、虚线或较低饱和度 |

未来轨道表达“已知的预安排或倾向”，不能渲染成已经发生的事实。Schedule Preplan 到达可见时间范围后才逐步对角色公开的语义，也应通过透明度或可见边界表达。

#### 轨道分组

完整轨道集合：

| 轨道组 | 主要内容 | 默认状态 |
| --- | --- | --- |
| 对话与投递 | 用户消息、主角回复、群回复、引用、贴表情、图片、投递结果 | 开启 |
| 剧本 | 用户触发剧本、自动推进、对话后续、短期补写、被截断消息 | 开启 |
| 场景 | 场景区间、地点、在场人物、场景摘要、关闭/切换 | 开启 |
| 日程与计划 | Schedule Preplan、当天安排、临时变更、Intent、承诺节点 | 开启 |
| 事实与关系 | 新事实、更新、承诺、兑现、关系变化、重要时间点 | 按需 |
| 人格状态 | Alter、Overlay、Perspective 变化及刷新来源 | 按需 |
| 系统诊断 | 模型调用、压缩、视觉处理、缓存、Token、错误与重试 | 按需 |

默认只打开最能解释角色生活的四组轨道，避免第一次进入就看到完整的工程诊断信息。高级用户可以保存自定义轨道组合，例如“叙事视图”“记忆诊断”“渠道投递”“模型性能”。

#### 时间线对象的最小显示

轨道块只显示足够识别的信息：

- 类型或图标；
- 时间/持续时间；
- 一行摘要；
- 状态颜色或角标；
- 必要的关系连线或来源标记。

完整剧本、JSON、Prompt、Token、消息元素和数据库字段放入 Inspector/Detail Panel。高信息密度来自关系与层级，而不是在小色块中塞入全文。

#### 时间缩放与 LOD

不同缩放范围需要返回和绘制不同粒度：

| 可视跨度 | 主要显示 |
| --- | --- |
| 数分钟 | 每条消息、打字阶段、模型调用、投递、重试 |
| 数小时 | 对话段、剧本块、场景、自动推进、Alter 节点 |
| 一天 | 日程区块、关键场景、重要事实、关系变化 |
| 数天/数周 | Schedule Preplan、长期节奏、场景弧线、趋势与关键事件 |

缩远时由 HDSI/主进程投影层聚合信息，不是将数万条 DOM 元素简单缩小。原始记录仍可通过下钻查看。

#### 交互规则

- 单击：选择并同步 Inspector；
- 双击：缩放/定位到对象的详细范围；
- 框选：选中一个时间范围，显示该范围摘要与统计；
- 滚轮/触控板：水平时间缩放或滚动，具体手势保持平台一致；
- `Now`：一键回到故事当前时间；
- 过滤：按轨道、来源、用户、渠道、事件类型过滤；
- 搜索结果：不离开时间线，显示定位标记并支持逐条跳转。

第一阶段的时间线保持只读。涉及事实修正、日程刷新、重试投递等动作，应进入明确命令流程，不能通过任意拖动时间线直接改写 HDSI 业务事实。

### 3.8 跨面板选择与联动模型

整个 Studio 共享一个 `SelectionContext`：

```ts
interface SelectionContext {
  storyId: string
  workspace: 'overview' | 'arrangement' | 'routing' | 'models' | 'configure' | 'diagnostics'
  timeRange?: { from: number; to: number }
  trackIds?: string[]
  entity?: { type: string; id: string }
  participantId?: string
  channelAccountId?: string
}
```

联动原则：

- 选择时间线事件后，Browser 高亮相关对象，Inspector 解释事件，Detail Panel 显示深层数据；
- 选择用户档案后，时间线可过滤/标记与该用户有关的消息、事实和场景；
- 选择渠道账号后，Routing 显示故事绑定，Detail Panel 显示最近收发与错误；
- 选择模型用途后，Diagnostics 显示该用途的调用、延迟、错误与回退；
- 面板间只传递稳定 ID 与选择上下文，不复制整份数据库对象。

选择状态需要可序列化并保存在本地布局中。删除或迁移对象后，如果选择失效，界面退回其父级对象并显示一次轻量说明，不能留下空白或崩溃面板。

### 3.9 Overview、Routing、Models 与 Configure 工作区

#### Overview：多故事总览

Overview 用卡片和紧凑列表展示：

- 故事名称、角色头像与阶段；
- Worker、渠道与模型健康；
- 最近活动；
- 收件箱积压；
- 当日 Token/费用；
- 最近错误；
- 快速进入 Arrangement、静音或暂停。

总览只展示摘要，不持续订阅每个故事的完整时间线。多故事同时运行时，它是资源与异常的第一观察面。

#### Routing：渠道、账号、用户与故事关系

Routing 不是三个孤立列表，而是可理解的绑定关系：

```text
渠道适配器
└─ Bot/账号
   └─ 绑定故事
      ├─ 主角
      ├─ 私聊参与者
      ├─ 群聊与群成员
      └─ 可用渠道能力
```

点击账号显示在线状态、selfId、能力、绑定故事、最近收发和最后错误。点击用户显示渠道身份、参与故事、关系摘要、关键事实和近期互动。账号冲突必须通过明确确认替换。

概念图中“管理员金色、普通用户灰色”可以作为身份标签的一部分，但权限不能只靠颜色表达；同时显示文字、图标或徽标。颜色不应用来暗示角色对用户的情感价值。

#### Models：按用途组织模型

模型工作区优先展示用途分配：

```text
主叙事       → Zhipu / glm-...
压缩         → DeepSeek / ...
Alter        → ...
视觉         → ...
贴纸描述     → ...
Embedding    → ...
```

选中某个用途后再显示 Provider、model mode、模型 ID、温度、思考、流式、格式和回退链。界面同时展示最近延迟、成功率、无效结构恢复、Token 与最后错误，使“配置”与“运行表现”能够互相解释。

#### Configure：分层配置而不是复制 Console

配置按用户决策顺序划分为故事、模型、渠道、能力、运行与隐私。基础模式只显示正常部署必须填写的字段；高级模式显示缓存、结构化输出、实验性流式、压缩细节等参数。

理想情况下由 HDSI 输出配置 Schema、用途选项、条件显示和校验规则，typ-0 根据 Schema 构建界面。这样 HDSI 新增配置时不会产生另一套手工维护且逐渐过时的表单。

所有配置变化先形成 `ConfigPatch`：

1. Renderer 编辑本地草稿；
2. 主进程请求 HDSI/配置服务校验；
3. UI 显示影响范围：立即生效、需要重载、需要重启 Worker；
4. 用户确认后原子保存；
5. 密钥字段只保存 `$secret:` 引用；
6. 失败时保留旧配置并显示具体字段错误。

### 3.10 只读数据库观察器

概念图中的 Database Viewer 保留，但定义为高级诊断能力，而不是普通业务编辑器。

普通详情层提供经过解释的数据：剧本、事实、场景、日程、投递、模型调用及其关联。高级观察器才提供：

- 原始投影字段；
- 稳定记录 ID；
- 来源表/来源类型；
- 关联记录；
- 创建、更新时间；
- JSON 展开；
- 当前结果导出。

观察器默认只读，不直接连接 SQLite。需要修改事实、重做 Preplan、刷新某种记忆或重新投递时，由 typ-0 调用 HDSI 提供的明确命令，并在 UI 中展示影响范围与结果。

### 3.11 视觉语言与信息密度

颜色必须承载稳定语义，并同时使用图标、形状或文字，避免颜色成为唯一信息来源。

| 语义 | 推荐色相 | 用途 |
| --- | --- | --- |
| 未来/预安排 | 蓝色 | Schedule Preplan、未来计划、候选事件 |
| 已确认/成功 | 绿色 | 已发生事实、投递成功、健康状态 |
| 重要/高优先级 | 金色 | 重要事实、管理员身份、需关注节点 |
| 人格/情绪状态 | 紫色 | Alter、Overlay、Perspective |
| 处理中 | 青色 | 模型调用、写作、发送中 |
| 错误/冲突 | 红色 | 失败、绑定冲突、不可恢复异常 |
| 中性/未激活 | 灰色 | 普通用户、后台信息、关闭轨道 |

亮色与暗色主题保持相同色相语义，通过明度、描边、底色和对比度适配。重点文本、选中状态和错误状态需要满足可读对比度；密集小块避免使用大面积高饱和颜色。

信息层级分为三级：

1. **持续可见**：故事阶段、Now、渠道、Worker、收件箱和错误；
2. **工作区可见**：当前轨道块、列表摘要、状态指标；
3. **选择后可见**：全文、JSON、Prompt、Token、关联记录与诊断细节。

这让专业用户可以在一屏内获得大量信息，同时让普通用户只需理解顶栏、Browser 和默认四条轨道。

### 3.12 界面性能架构与预算

Studio 的高信息密度必须建立在可视范围渲染上。

#### 渲染策略

- 时间尺、密集轨道块、关系标记：Canvas/WebGL；
- 工具栏、Browser、Inspector、表单：DOM；
- 剧本、日志、事实列表：虚拟滚动；
- 图表：按复杂度选择 Canvas/SVG；
- 折叠或不可见面板停止高频绘制与非必要订阅；
- Renderer 不解析整库、不进行大型全文索引、不执行备份压缩。

第一版不实现完整自由浮窗系统。支持面板折叠、尺寸调整、底栏/右栏位置选择、布局保存与恢复即可。过早实现无限 Docking 会显著增加焦点管理、窗口恢复和测试复杂度。

#### 数据策略

- 打开故事时获取有限初始快照；
- 后续通过增量事件更新；
- 时间线按可视范围、轨道和 LOD 查询；
- 全文搜索、统计聚合、导入导出在主进程 Worker Thread 或 Utility Process 执行；
- Renderer Store 以稳定 ID 归一化对象，避免复制巨型嵌套树；
- 多故事 Overview 只订阅健康摘要，不加载各故事完整时间线。

#### 初步性能目标

| 项目 | 目标 |
| --- | --- |
| Studio Shell 初次可交互 | 常规电脑冷启动后尽快进入外壳，不等待所有故事 Worker 全部就绪 |
| 面板操作 | 普通折叠、选择和滚动保持接近 60 FPS |
| 时间线平移/缩放 | 只在当前窗口重算，连续操作无明显停顿 |
| 事件推送 | 合并同一渲染帧内的高频更新，保持语义事件不丢失 |
| 大型故事 | 历史量增长不导致启动时全量加载 |
| Worker 故障 | 单故事故障不冻结 Renderer 或其他故事 |

这些目标后续应转成可重复基准：例如 5 万时间线对象的范围查询、1 万条日志的虚拟滚动、多故事并行心跳，以及大量增量事件下的帧率与内存观察。

### 3.13 Logs Surface：传统滚动日志界面

Logs Surface 为熟悉 Koishi、终端和传统调试流程的用户提供完整日志视图。它保留“日志从上到下持续滚动”的直观形式，同时增加桌面宿主需要的故事隔离与结构化定位能力。

#### 界面组成

```text
┌──────────────────────────────────────────────────────────────┐
│ 故事 | 来源 | 等级 | 时间范围 | 搜索 | 跟随 | 暂停 | 清屏视图 │
├──────────────────────────────────────────────────────────────┤
│ 12:43:21 [I] hds-interlude ...                               │
│ 12:43:22 [D] typ0.router ...                                 │
│ 12:43:24 [W] channel.snowluma ...                            │
│ ...                                                          │
├──────────────────────────────────────────────────────────────┤
│ 匹配数 / 当前速率 / 缓冲量 / 文件位置 / 导出                 │
└──────────────────────────────────────────────────────────────┘
```

必须支持：

- 传统自动跟随最新日志；
- 用户向上滚动时自动停止跟随，并显示“回到最新”；
- 暂停画面更新，但后台仍持续接收和持久化日志；
- 按故事、Worker、渠道适配器、桌面主进程、插件 logger 和等级过滤；
- 纯文本搜索、正则搜索、时间范围和 request/event/message ID 定位；
- 多行日志作为一个逻辑记录折叠/展开，避免堆栈被拆散；
- 复制当前行、复制事件、导出过滤结果、打开所在日志文件；
- 从日志行跳转 Studio 对应事件，或跳转 Koishi 对应插件；
- 显示当前日志速率、内存缓冲量、落盘状态与丢弃计数。

“清屏”只清除当前视图，不删除磁盘日志。真正删除或轮转日志属于明确的数据管理操作，需要显示范围和可恢复性。

#### 统一日志记录

桌面主进程把不同来源规范为：

```ts
interface DesktopLogRecord {
  id: string
  storyId?: string
  occurredAt: number
  receivedAt: number
  level: 'debug' | 'info' | 'warn' | 'error' | 'success'
  source: 'desktop' | 'worker' | 'channel' | 'plugin'
  logger: string
  message: string
  details?: unknown
  correlation?: {
    eventId?: string
    requestId?: string
    messageId?: string
    deliveryId?: string
    entityType?: string
    entityId?: string
  }
}
```

原始文字必须保留，结构化字段用于过滤和跳转。无法解析的第三方日志仍作为完整文本记录，不因缺少字段而丢弃。

#### 采集与持久化

日志来源包括：

- Electron 主进程与 Renderer 的受控错误；
- 每个 HDSI/Koishi Worker 的 stdout、stderr 与结构化 bridge 日志；
- SnowLuma/OneBot 等渠道适配器；
- typ-0 路由、收件箱、配置编译、投递和迁移服务；
- Koishi 插件 logger。

主进程维护有限内存环形缓冲，同时按故事和日期写入日志文件。UI 打开时先读取最近窗口，向上滚动再分页读取旧日志。日志写盘不经过 Renderer，也不能阻塞消息路由与 HDSI Worker IPC。

日志需要轮转策略：

- 单文件大小上限；
- 按日或按大小轮转；
- 可配置保留天数；
- 错误/崩溃摘要可比普通 debug 日志保留更久；
- 清理任务在低优先级后台执行；
- Blind 模式遵从 HDSI 的日志屏蔽语义，不落盘被禁止的内容。

#### 渲染性能

- 使用虚拟化列表，只渲染视口附近的记录；
- 高频日志先在主进程批量合并通知，例如每 16–50ms 推送一批；
- 批量推送只优化 UI 通知，不合并或去重不同日志记录；
- 搜索大型文件由 Worker Thread/Utility Process 建立索引或流式扫描；
- 暂停时停止 Renderer 插入新行，但显示积压条数；
- 对超长单行和大型 details 设置折叠与按需加载。

### 3.14 Koishi Surface：第三方插件配置与连接兼容界面

Koishi Surface 的目标是让 typ-0 兼容 Koishi 生态，而不在 typ-0 中重新实现每一个第三方插件的配置页面。

它应连接**当前故事 Worker 自己的 Koishi Console**。因此每个故事看到的是自己的插件、服务、配置和连接状态，不会误操作另一个故事。

#### 推荐集成方式

采用隔离的嵌入式 Web Contents 容器承载 Koishi Console。实施时根据项目锁定的 Electron 版本选择官方支持的隔离视图能力；容器必须满足：

- `nodeIntegration: false`；
- `contextIsolation: true`；
- 启用 sandbox；
- 使用每故事或每应用受控 Session Partition；
- 只允许访问 typ-0 分配的本地 Koishi Console 地址；
- 拦截新窗口、下载、外部导航和权限申请；
- 外部链接必须经主进程白名单确认后交给系统浏览器；
- Koishi 页面无法调用 typ-0 preload 的管理接口；
- Surface 隐藏时降低或暂停非必要绘制，但不破坏正在保存的配置操作。

不建议用普通 iframe：Koishi Console 的 WebSocket、路由、认证与安全边界更适合独立 webContents。也不应启用不受控的 `<webview>` 权限来换取快速接入。

#### 每故事 Console Endpoint

StoryManager 启动 Worker 时：

1. 从受控端口分配器取得空闲 loopback 端口，或使用等价的安全本地传输；
2. 为该 Worker 启用 Koishi Console/配置服务；
3. 只监听 `127.0.0.1`/loopback，不对局域网开放；
4. 生成短期会话 nonce 或本地认证信息；
5. Worker 在 `bridge-ready` 或独立事件中返回可用的 `consoleEndpoint`、协议版本与能力；
6. 主进程验证 endpoint 属于本 Worker 的分配记录；
7. Koishi Surface 创建或复用该故事的隔离视图。

```ts
interface KoishiConsoleDescriptor {
  storyId: string
  workerId: string
  endpoint: string
  sessionToken?: string
  capabilities: Array<'market' | 'plugins' | 'config' | 'connections' | 'database'>
  ready: boolean
  revision: number
}
```

Worker 未启动、Console 插件缺失或页面加载失败时，Surface 显示明确状态和修复入口，而不是浏览器空白页。

#### 原生配置与兼容配置的分工

- HDSI、模型、渠道、故事运行等高频配置优先使用 Studio Configure 的原生界面；
- 其他 Koishi 插件使用 Koishi Surface 的官方/插件自带配置页；
- 同一字段不能由两套界面同时持有未保存草稿；切换前提示保存或放弃；
- Koishi Surface 完成插件重载后，typ-0 刷新 Worker/插件健康状态；
- 插件安装、卸载、启用和禁用必须归属于当前故事，并显示影响范围。

#### 临时编译配置与密钥安全

当前 Worker 使用由 `$secret:alias` 编译出的临时运行配置。直接让 Koishi Console 保存这份临时文件会产生两个严重问题：

1. 修改可能只写入临时目录，重启后消失；
2. 展开后的 API Key 可能被写回磁盘或显示在页面中。

因此 Koishi Surface 在开放“可写配置”前必须实现 `KoishiConfigMediator`：

```text
故事 canonical koishi.yml（只含 $secret 引用）
        │
        ├─ 编译 → Worker 临时运行配置
        │
Koishi Console 产生结构化配置变更
        │
        ▼
ConfigMediator 校验、去除运行时展开密钥、恢复 secret 引用
        │
        ▼
原子写回 canonical koishi.yml
        │
        ▼
受控重载 Worker / 插件
```

Mediator 必须：

- 知道 canonical 配置与 runtime 配置的对应关系；
- 将已存在的密钥值还原成原 `$secret:alias`，禁止明文写回；
- 对未知新密钥字段要求用户在 typ-0 Secret Store 中创建引用；
- 保存前生成 patch、校验 YAML 和插件 Schema；
- 保存失败时保留旧配置与用户草稿；
- 使用原子替换并保留有限版本备份；
- 记录“哪个 Surface、哪个插件、何时修改了哪些非敏感字段”；
- 不把密钥值写入日志、事件 payload、崩溃报告或 Renderer Store。

在 Mediator 完成前，Koishi Surface 可以先开放状态、连接和只读页面；涉及保存配置的入口应明确标记为开发中或受限，不能让用户产生“已经保存”的错觉。

#### 插件兼容等级

typ-0 可以对插件标记兼容状态：

| 等级 | 含义 |
| --- | --- |
| Native | 有 typ-0 原生界面，并通过 Koishi Worker 正常运行 |
| Console-compatible | 使用原 Koishi Console 配置，主要功能可用 |
| Runtime-only | 可在 Worker 中运行，但没有安全的桌面配置路径 |
| Unsupported | 依赖不允许的进程、端口、GUI 或权限，当前无法使用 |

兼容等级用于解释能力，不用于阻止用户安装普通插件。发现插件需要文件系统、浏览器、数据库或外部端口权限时，Surface 应显示来源明确的权限提示。

#### 连接管理

Koishi Surface 需要保留 adapter、service 和连接类插件的原生配置体验，并将关键健康信息同步回 typ-0：

- 插件是否启用；
- 连接中、在线、重连、离线、错误；
- 已发现账号与 selfId；
- 监听地址与端口冲突；

#### 已完成的三态行为

| 状态 | HDSI Worker | 外部新消息 | 恢复时行为 |
| --- | --- | --- | --- |

## 6. 关键数据模型与生命周期

### 6.1 故事目录

每一个故事应作为一个独立目录保存。开发模式位于 `desktop/stories/<story-id>/`；打包后应迁移至应用用户数据目录。

目标结构：

```text
stories/<story-id>/
├── story.json                 # 故事元数据、展示信息、运行偏好
├── koishi.yml                 # 不含密钥明文的 HDSI/Koishi 配置
├── data/
│   └── koishi.db              # HDSI 的叙事数据与数据库
├── inbox.json                 # typ-0 的可靠收件箱
├── usage/
│   └── YYYY-MM-DD.json        # 本故事按日用量聚合
├── logs/                      # Worker/渠道/桌面端相关日志（后续）
└── assets/                    # 角色资料、导入素材、可选本地资源（后续）
```

`story.json` 当前可保存故事 ID、名称、阶段、创建/更新时间等基础元数据。正式稳定格式前，需要补充显式 `schemaVersion`，为将来的目录迁移提供判断依据。

### 6.2 密钥引用

配置中只允许将完整标量写成：

```yaml
apiKey: $secret:glm-main
```

启动 Worker 时由主进程临时展开为真实密钥。原始 `koishi.yml` 保留引用，不会写回明文。

原因：

- 故事目录可以备份或分享而不包含 API Key；
- Renderer 和普通文本日志不需要触碰密钥；
- 同一密钥可被多个故事引用；
- 导入故事后只需在本机重新绑定相同别名或新增本机密钥。

### 6.3 账号绑定

绑定表由桌面端统一维护：

```text
渠道账号 / bot 身份 / 会话归属  →  一个 storyId
```

同一账号如尝试绑定到另一个故事，必须要求用户明确选择替换；不能让后创建的故事静默夺走输入。

### 6.4 入站消息与收件箱

统一输入需要至少包含：

```ts
{
  rawMessageId?: string,      // 渠道侧稳定事件 ID；存在时才用于精确去重
  platform: string,
  selfId: string,
  channelId: string,
  senderId: string,
  occurredAt: string,         // 原始事件发生时间（ISO）
  content: string,
  quote?: unknown,
  elements?: unknown[],
  attachments?: unknown[],
}
```

正常路径：

```text
渠道事件
  → 适配器标准化
  → typ-0 根据 binding 找故事
  → running：发送 HDSI Worker
  → HDSI 接收并回执
  → 如有可见输出，发出 delivery
  → 渠道发送器投递（T4）
```

缓冲路径：

```text
渠道事件
  → 无绑定 / muted / paused / Worker 未就绪
  → inbox.json 原子持久化
  → 用户恢复运行或 Worker 就绪
  → 顺序 replay
  → HDSI 明确确认本条已接受
  → 才从 inbox 移除
```

### 6.5 为什么事件时间必须随输入传递

HDSI 在 desktop bridge 已接受 `receivedAt`。桌面端接入真实适配器时必须传递渠道事件的真实发生时间，而不是“桌面端刚刚处理到它的时间”。

这关系到：

- 剧本时间轴正确性；
- 静音/暂停期间积压消息的真实先后顺序；
- HDSI 日程与自动推进的冲突判断；
- 延迟、补发和重放时的可解释性。

### 6.6 Studio Projection API

当前 `timeline-snapshot` 足以支撑原型详情，但宿主式界面需要一个受控的投影层。它位于 HDSI 业务数据与 Renderer 之间，负责把内部数据转换为稳定、可分页、可聚合、可增量更新的界面对象。

目标接口可以逐步发展为：

```ts
getStoryOverview(storyId)
getTimelineRange({ storyId, from, to, tracks, detailLevel, cursor })
subscribeTimeline({ storyId, afterRevision })
getEntityInspector({ storyId, type, id })
getRuntimeMetrics({ storyId, range })
getDeliveryHistory({ storyId, from, to, cursor })
getUsageSeries({ storyId, from, to, granularity })
getChannelAccounts({ adapterId })
getUserProfiles({ storyId, cursor })
getConfigSchema({ storyId })
validateConfigPatch({ storyId, patch })
applyConfigPatch({ storyId, patch })
```

这些名称描述能力，不要求一次全部实现。新增接口时遵守：

- HDSI 仍负责解释业务数据；
- 主进程负责权限、路由、缓存与 IPC；
- Renderer 只请求所需投影；
- 所有列表支持范围或游标，不返回无界全量；
- 所有结果带故事 ID、协议版本和数据 revision；
- 时间字段明确区分事件发生、桌面接收、HDSI 处理和渠道投递；
- 投影字段变更尽量向后兼容。

### 6.7 初始快照与增量事件

Studio 打开一个故事时先请求一次有限初始快照。随后通过增量事件维护画面：

```text
story-overview-updated
runtime-updated
timeline-entry-added
timeline-entry-updated
scene-updated
fact-updated
schedule-updated
delivery-updated
usage-updated
error-raised
```

每个事件至少携带：

```ts
{
  storyId: string
  revision: number
  occurredAt: number
  type: string
  entityId?: string
  payload: unknown
}
```

Renderer 发现 revision 不连续时，不猜测缺失数据，重新请求对应范围或快照。主进程可以合并同一渲染帧内的 UI 通知，但不能将两个不同的用户消息或业务事件按文本相同而去重。

### 6.8 命令与查询分离

Studio 接口分为两类：

- **Query**：读取故事概览、时间线、Inspector、日志、投递、用量和配置 Schema；
- **Command**：切换三态、回放收件箱、应用配置、刷新 Preplan、重试投递、绑定账号等。

Command 必须返回明确的接受/拒绝、操作 ID、影响范围和最终结果。对于可能耗时的操作，先返回 accepted，再以事件更新进度。Renderer 不通过修改本地投影来假装命令已经成功。

### 6.9 Logs 与 Koishi Surface 接口

Logs Surface 需要的主进程接口：

```ts
subscribeLogs({ storyId?, sources?, levels?, afterId? })
queryLogs({ storyId?, from?, to?, query?, cursor?, limit? })
getLogContext({ logId, before, after })
exportLogs({ filters, format, destination })
getLogStorageStatus({ storyId? })
```

Koishi Surface 需要的受控接口：

```ts
getKoishiConsoleDescriptor({ storyId })
startKoishiConsole({ storyId })
stopKoishiConsole({ storyId })
navigateKoishiConsole({ storyId, pluginName?, path? })
getKoishiPluginHealth({ storyId })
validateKoishiConfigPatch({ storyId, patch })
applyKoishiConfigPatch({ storyId, patch })
```

Renderer 不直接接收本机端口分配权、临时配置路径或密钥。嵌入视图的创建、导航校验、Session Partition 与销毁均由主进程负责。

## T3.7：构建 Koishi Compatibility Surface

Koishi Surface 分阶段开放。先解决隔离、只读状态和连接观察，再开放安全可写配置。

### T3.7.1 Worker Console 生命周期

1. 为 StoryManager 增加 loopback 端口分配与占用释放。
2. 为故事 Worker 启用最低必要的 Koishi Console 服务。
3. bridge-ready 增加 console descriptor 或通过独立握手返回。
4. Worker 退出、崩溃或故事卸载时立即使 descriptor 失效并关闭嵌入视图。
5. 重启 Worker 后 endpoint/revision 改变，旧页面不得继续控制新 Worker。
6. 测试两个故事同时运行时端口、会话和页面完全隔离。

### T3.7.2 安全嵌入

1. 主进程创建隔离 webContents 容器，不向页面暴露 typ-0 preload。
2. 禁用 Node 集成，启用 context isolation 与 sandbox。
3. 限制导航到已登记的 loopback endpoint。
4. 拦截新窗口、外链、下载、媒体权限和剪贴板等敏感能力。
5. 为每故事或每应用配置受控 Session Partition，并在故事删除/退出登录时清理。
6. Surface 切换时正确调整视图尺寸、可见性、焦点与快捷键归属。

### T3.7.3 只读状态与连接闭环

1. 首先开放插件列表、服务状态、连接状态与适配器页面。

3. 从 Koishi 插件页提供“查看相关日志”和“查看故事绑定”。
4. Worker 未就绪或插件页面不可用时显示 typ-0 原生错误页。
5. 验证 Market、配置页与第三方页面不会越过故事边界。

### T3.7.4 ConfigMediator 与安全写回

1. 明确 canonical `koishi.yml`、临时 runtime 配置及其 revision。
2. 捕获 Koishi Console 的结构化配置变更，不允许页面直接永久保存临时明文配置。
3. 对变更做 Schema/YAML 校验和 secret 引用恢复。
4. 新密钥字段转入 typ-0 Secret Store 流程。
5. 显示 patch、插件重载范围和可能中断的连接。
6. 原子写回 canonical 配置，并保留有限版本备份。
7. 受控重载插件或 Worker；失败时自动保留上一有效配置。
8. 写入非敏感审计记录，并通知 Studio/Logs 刷新。

### T3.7.5 插件兼容与权限说明

1. 标记 Native、Console-compatible、Runtime-only、Unsupported。
2. 检测插件需要的本地文件、外部端口、浏览器或数据库能力。
3. 对潜在冲突显示具体对象，例如端口、服务名或账号。
4. 不因为插件“未知”就禁止运行；未知能力进入高级提示与日志观察。
5. 为常用适配器、数据库、Market 和 Puppeteer 建立最小兼容测试清单。

### T3.7 验收标准

- 每个故事只打开自己的 Koishi Console；
- 页面无法访问 typ-0 主进程能力、其他故事 endpoint 或外部任意网址；
- 插件与适配器连接状态能同步回 Overview/Routing；
- 保存配置后修改进入 canonical 配置，重启 Worker 后仍存在；
- 原有 `$secret:` 引用不会被替换成明文；
- 保存失败时旧配置、Worker 与连接尽可能保持可用；
- Blind 模式无法通过 Koishi Surface 绕过内容或指令屏蔽。

## T4：真实渠道接入与可靠投递

T4 是 typ-0 从“本地运行时原型”进入“真实可聊天产品”的关键阶段。

### T4.1 选择并封装第一个渠道适配器

建议先接入已经具备研究基础的 SnowLuma / OneBot 路径，而不是立即把所有渠道一次性塞进主进程。

需要定义一个小型 `ChannelAdapter` 接口：

```ts
interface ChannelAdapter {
  id: string
  start(): Promise<void>
  stop(): Promise<void>
  onInbound(listener: (event: DesktopInboundEvent) => Promise<void>): void
  send(delivery: DesktopDelivery): Promise<DeliveryReceipt>
  listAccounts?(): Promise<ChannelAccount[]>
}
```

适配器内部负责协议细节；typ-0 只接收统一事件和回执。

### T4.2 真实输入转换

对每一条渠道消息完成：

1. 生成稳定事件 ID；优先使用渠道消息 ID，必要时组合渠道、账号、会话、消息 ID。
2. 读取真实时间戳并转换为毫秒值。
3. 保留发送者 ID、昵称、群 ID、私聊 ID、引用消息、原生表情、图片、语音等必要元素。
4. 将渠道格式转为 `DesktopInboundEvent`，但不在适配器里做 HDSI 的剧情判断。
5. 交给现有 `MessageRouter`，由绑定与三态规则决定立刻发送或入箱。
6. 为渠道可能的重复推送设置**只针对同一稳定事件 ID**的去重；不能把短时间内两条相同文本误当成重复消息。

### T4.3 真实输出投递

HDSI 的 bridge `delivery` 当前已经能够带回桌面端。下一步在主进程中：

1. 根据该故事关联的渠道绑定选择发送器；
2. 将文本、引用、贴表情、指定回复、图片/本地贴纸等 HDSI 已有动作转换为渠道支持的操作；
3. 保存投递尝试记录；
4. 收到渠道成功回执后标记成功；
5. 仅对可确认的网络暂态失败进行有限次数、带退避的重试；
6. 对权限不足、账号掉线、动作不受支持等永久失败，显示为可操作错误，不盲目重试；
7. 避免“投递失败却把剧情当已送达”的错位。HDSI 与桌面端之间需要明确 delivery acknowledgement 的语义；若必须补充协议，应优先增加轻量确认事件，而不是让 GUI 直接干预剧本数据库。

### T4.4 账号发现与绑定 UI

在适配器能够列出账号后，桌面端应提供：

- 可用账号列表与在线状态；
- 账号绑定到故事的操作；
- 冲突提示与明确替换；
- 解绑、掉线提示与恢复入口；
- 将“故事接收哪个渠道/账号”显示在故事概览中。

### T4 验收标准

- QQ/目标渠道的一条真实私聊消息可进入已绑定故事；
- `running` 下 HDSI 正常处理并能真实发送回复；
- `muted` 下消息不丢失、角色自动生活继续、恢复后按顺序处理；
- `paused` 下新自动工作不再启动，恢复后安全继续；
- 渠道掉线或投递失败在 UI 中有明确状态；
- 一个账号无法被两故事同时消费；
- 重启桌面端后，收件箱与绑定仍可恢复。

## T5：配置体验、故事管理与发布准备

当 T4 能稳定收发后，再将底层能力组织成普通用户可用的产品流程。

### T5.0：当前已落地的初步垂直切片

本阶段已先实现一个谨慎的配置/备份底座，而不是提前承诺完整导入导出或第三方插件可视化配置：

| 能力 | 当前实现 | 明确边界 |
| --- | --- | --- |
| Canonical 配置读取与保存 | `StoryConfigMediator` 是 typ-0 自己的唯一 YAML 写入入口；限制 1 MB、拒绝 NUL 与敏感字段的明文，并检查所有 `$secret:` 别名已经存在。 | HDSI/Koishi 仍是 YAML schema 的最终解释者；本阶段不重写、格式化或猜测插件字段。 |
| 密钥别名 | Renderer 只能查看别名并通过专用 IPC 保存新值；值落入 Electron `safeStorage`，不会回传给页面或写进故事目录。 | 尚未提供删除确认、迁移、系统安全存储不可用时的替代方案。 |
| 保存后重载 | 运行中的 Worker 在保存后受控退出并重新加载；若新文件无法重新启动，宿主恢复保存前文本并尝试恢复旧 Worker。 | 当前只验证了主进程级回滚路径；未来应增加真实 Worker/配置夹具的端到端演练。 |
| 配置历史 | 每次保存前创建最多保留 20 份的 `story/.typ-0-backups/config/` 文本副本。 | 尚未做 GUI 历史浏览、差异比较或一键回退。 |
| 故事备份 | 故事卡片可创建 `dataRoot/backups/<story>/<time>/` 的文件夹快照；会保留数据库和角色资料，排除 `.typ-0-runtime` 中可能含解析后密钥的 Worker 临时文件。 | 这是本机可恢复快照，不是跨电脑 `.zip` 导出包。 |

### T5.0.1：故事生命周期补全

在初步配置底座之上，现已补齐下面的故事级操作：

1. **复制/分叉**：以现有文件夹创建独立副本，强制填写新的本地 ID，重写 manifest 的创建时间，清空 `accounts`，将 phase 设为 `paused`。复制不会带走 `.typ-0-runtime` 或历史配置备份。
2. **目录导出**：选择目标文件夹后，导出一个可移交的故事目录；故事本身没有密钥，因此导出不会带走 `safeStorage` 内容或宿主级 bindings。
3. **目录导入**：选择一个含有效 `story.json` 的故事目录，在导入时指定新的本地 ID 与可选显示名。源目录不被修改；导入故事默认暂停且无渠道绑定，避免接管已有账号。
4. **可恢复删除**：删除动作先创建普通备份，再受控卸载 Worker，解除该故事的所有账号绑定，最后把完整目录移动至 `dataRoot/trash/<story>/<time>/`；它不是不可逆 `rm -rf`。
5. **资源边界**：`StoryManager` 默认最大 3 个同时运行的 Worker；达到上限时拒绝新的加载请求，绝不为了省资源暗中暂停或改变其他故事的 HDSI 语义。

这些操作全部在 Main Process 执行，Renderer 只获得窄 IPC 操作和结果路径。运行时覆盖项持续增长；当前实际结果以 `desktop/src/main/runtime/runtime.test.ts` 和 `npm run test:runtime` 为准，已覆盖账号解绑、复制时的身份重写、运行期密钥文件排除、废纸篓移动和配置回滚副本。

当前原型 Renderer 已有“配置”和“备份”入口。配置窗口明确显示别名、将 `koishi.yml` 作为高级文本配置处理，并提示保存运行中故事会触发安全重载。普通用户层的模型、渠道、能力分区表单将在 schema/插件兼容能力到位后构建在同一个 Mediator 上。

配置别名校验、保存前备份以及故事快照排除运行期解析配置均已纳入运行时回归测试；不要在设计文档中固定测试数量。

### T5.1 配置中心

按用户的实际决策顺序组织，而不是按 HDSI 内部字段堆叠：

1. **角色与故事**：名称、头像、角色资料、剧本基础资料。
2. **模型**：提供商、预设、模型选择、密钥引用、主叙事/压缩/视觉等用途分配。
3. **渠道**：适配器、账号、绑定故事、连接状态。
4. **能力**：图片识别、贴纸、群聊互动、Schedule Preplan、Alter 等已有 HDSI 功能。
5. **运行与隐私**：三态、日志等级、Blind/失明模式、备份策略。

配置编辑应写回故事的非密钥配置，并调用现有受控重载/Worker 生命周期机制。不要让每一个字段变化都通过直接改数据库实现。

### T5.2 故事生命周期

需要提供：

- 新建故事向导；
- 从模板或已有 HDSI 数据创建；
- 复制/分叉故事；
- 导出故事目录；
- 导入与冲突检查；
- 删除前备份或移动到可恢复位置；
- 版本升级与目录 `schemaVersion` 迁移。

导出包默认不含密钥。导入后由用户选择复用已有密钥别名或重新填写。

### T5.3 多故事资源控制

多个故事并行运行时，应当有明确预算：

- 限制同时启动的 Worker 数；
- 将非前台故事的低优先级整理工作排队；
- 绝不为了节省资源而破坏 HDSI 对实时输入、Alter、必要压缩与日程判断的既有语义；
- 每个故事独立失败、独立重启；一个 Worker 崩溃不能带倒所有故事；
- 在 UI 中显示故事当前是否活跃、静音、暂停、掉线或故障。

### T5.4 发布与运维

发布前必须完成：

- 生产路径从开发 `desktop/stories/` 切换到用户数据目录的迁移验证；
- 确认 HDSI 运行源码/依赖的唯一来源，消除 `hdsi-sourcecode/` 与外部开发目录的版本漂移风险；
- 安装器/便携包策略；
- 适配器与 HDSI 的版本兼容检查；
- Worker 崩溃日志、自动恢复策略和用户可读的报错；
- 数据备份、恢复与升级演练；
- 首次运行向导与最小可用样例故事。

## T6：三 Surface 工作台与统一观察模型

T6 不再增加故事文件写入能力，也不改变 HDSI 叙事逻辑。它的任务是把 T0–T5 已有的故事、Worker、收件箱、Outbox、配置和备份能力组织为真正可持续使用的桌面工作台，并为后续真实渠道接入提供可观察的证据链。

### T6.0：已完成的初步实现

已完成第一版 **Studio Shell**，视觉语言取自 Ableton Live 的信息组织方式：低饱和深灰平面面板、细密边界、固定分区、压缩的 Transport 控制与按轨道排列的数据，而不是大卡片和大段说明文字。

当前窗口由以下区域组成：

```text
Transport：Surface / 当前故事 / 三态 / Worker 容量 / 时钟
Status Ruler：故事 phase / 时区 / 过去—现在—未来标尺 / Worker 健康
Browser：故事列表、对象导航、备份/导出等故事操作
Workspace：Studio / Logs / Koishi 三个主 Surface
Inspector：所选故事或条目的来源、时间与属性
Detail：Events / Deliveries / Model Usage / Data
```

### T6.0.1：Arrangement 的轨道语义与时段 Script

Arrangement 不再把所有条目均分成一排同样大小的卡片。它采用一条共享的、以“现在”为锚点的横向时间域；过去、现在、近未来在同一个标尺上可比较，但不会让长周期 Preplan 把今天发生的剧本压缩到不可读。

初始轨道由高到低分为：

| 轨道 | 高度与显示密度 | 数据含义 | 点击后行为 |
| --- | --- | --- | --- |
| **Script** | 主轨，高度约为普通轨道的三倍 | 将相邻的叙事/自动推进条目聚合为一个覆盖时段的 Script Segment。块内显示剧本片段、条目数和起始时间。 | Detail 切到 **Script**，展示该时段所有原始剧本条目及完整文本。 |
| **Timeline** | 极窄事件轨 | 所有可见条目的时间点，作为时间结构的“钢琴卷帘式”定位标记。 | Inspector 显示原始事件。 |
| **Receive / Send** | 窄轨 | 用户进入、主角可见消息、群聊投递等传输事件。 | Inspector 显示参与者、发生时间、内容。 |
| **Facts & Scenes** | 中等密度轨 | 场景的开始/结束区间、活跃事实最近确认时间。 | Inspector 显示对应的结构化对象。 |
| **Preplan** | 中等高度、半透明斜纹块 | 当前 HDSI Schedule Preplan 的近未来有效区间。 | Inspector 显示 revision、时区与有效范围。 |

Script Segment 的开始、结束时间优先来自 HDSI 的 `timelineWindow {from,to}`：它由自动推进、对话余波或到期承诺在持久化时一并写入，代表时间导演已确认的自动窗口。早于此功能的历史条目、以及没有自动时间账本的普通对话，保留为单一时间点；界面通过最小可点宽度呈现它们，**不再按文字长度或相邻段落猜测生活时长**。所有范围只读，不会回写 HDSI，也不会成为角色世界的新增事实。

共享时间域默认落在“近期过去 → 当前 now → 近未来”的 14 小时工作窗。这是因为 HDSI 当前主提示词本就只使用近半日的日程信息；多日 Preplan 仍保存于 HDSI 中，但在 Arrangement 里通过摘要/导航查看，而不是摊平在同一缩放层级。用户可在不改变故事或 HDSI 时间轴的前提下缩放到 15 分钟～14 天、平移到过去/未来，或一键返回跟随 Now 的默认窗。

这使界面在同一屏内同时保留三件重要信息：角色刚刚经历了什么、当前消息在哪里、近期生活结构大致会如何展开。

已连接的真实数据与操作：

- Browser 读取真实故事列表、运行阶段、Worker bridge 就绪状态，并将选择持久化到本地 `WorkspaceState`；Inspector 同时读取宿主侧持久 Inbox、Outbox、按日用量与最近错误摘要；
- Transport 可直接切换当前故事的 `running / muted / paused`；
- Studio 在 Worker ready 后优先请求带 revision、范围、轨道和分页 cursor 的 `timeline-range` Projection；预 M3 bridge 才回退到现有有限 `snapshot`。对话/投递、剧本、系统事件、场景、Schedule Preplan 映射到五条紧凑轨道；
- 轨道块和 Detail 中的事件可选择，Inspector 显示其 actor、参与者、发生时间和原文；
- Detail 的 Events 使用 HDSI snapshot；Deliveries 读取持久 Outbox 历史，Model Usage 读取宿主按日聚合历史，当前会话 bridge 事件仅用于即时刷新；
- Logs Surface 已通过主进程 LogBroker 查询当前故事当天的持久化日志，并订阅新记录；完整历史分页、虚拟化与过滤面板仍待后续完成；
- Koishi Surface 明确展示为未接入状态，不创建假 Console 或绕过安全边界；
- T5 的 Load、Configure、Backup、Import、Export、打开备份目录等入口都保留在新 Shell 中。

初步实现仍有意保持以下边界：

- Arrangement 当前是有限快照的密集可视化，不是无限时间缩放器；
- `Deliveries` 与 `Model Usage` 的历史查询 API 尚未接入，当前显示本次桌面会话收到的增量事件；
- Logs 已有持久化 LogBroker 和基础关键词/等级/来源查询接口；界面过滤、跨日分页、全文检索线程与轮转仍待后续完成；
- Koishi 未嵌入 Web Console，因 endpoint 隔离和导航限制必须先完成；
- Browser 中 Facts/Scenes/Schedule 的选择目前改变工作区语义和后续扩展方向，完整独立的实体视图将在范围 Projection API 到位后接入。

### T6.0.2：M4 Arrangement 操作层与紧凑分级信息架构

M4 将 Arrangement 从“每次打开固定的一段近期快照”推进为稳定的桌面工作区。其原则是：**视图是可恢复的本机偏好，故事事实仍只存在于 HDSI 的投影和数据库中。** Renderer 只保存下列安全 UI 状态：

```ts
type StoryWorkspaceLayout = {
  followNow: boolean
  centerAt: string | null
  spanMinutes: number // 15 min … 14 days
  tracks: { script: boolean; timeline: boolean; messages: boolean; state: boolean; preplan: boolean }
  panels: { browser: boolean; inspector: boolean; detail: boolean }
}

type SelectionContext = {
  storyId: string
  type: 'script' | 'entry' | 'fact' | 'scene' | 'preplan'
  entityId: string
}
```

`StoryWorkspaceLayout` 以故事 ID 为键保存到本机 LocalStorage。它不会携带 token、提示词、原始 HDSI 配置或数据库内容；导出/备份故事时也不会被带走。切换故事后，工作台恢复各自的缩放和轨道偏好；没有历史布局时使用 Follow Now 的 14 小时工作窗。

Arrangement 顶栏提供 `− / ＋ / ‹ / NOW / ›`：缩放按比例改变 `spanMinutes`，平移以当前可见窗口的一部分移动中心，`NOW` 清除固定中心并再次跟随当前时间。Ctrl/⌘ + 滚轮执行缩放，Shift + 滚轮执行横向平移。为避免触控板滚轮将大量相邻范围请求压向 Worker，连续操作在 Renderer 合并后才发起一次只读 `timeline-range` 查询。当前范围请求也有 revision guard：故事切换或后一请求已经开始时，先返回的旧请求不能覆盖新视图。

Browser 改为三层紧凑信息结构：

1. **故事选择层**：筛选、故事列表、运行阶段和 Bridge 就绪状态；
2. **当前故事层**：Overview、Timeline、Facts & Scenes、Schedule Preplan、Configure；
3. **Arrangement / Operations 层**：轨道显隐及对象计数、备份、导出、打开备份位置。

轨道显隐只影响 Overview Arrangement，不会阻断范围 Projection，也不会让 Facts/Scenes 或 Schedule 专用视图空白。Script 主轨比窄事件轨更高，块内展示摘要、条目数量、真实 `RANGE / POINT` 状态；紧凑粘性轨道头、刻度网格和独立 Inspector 使阅读重点保持在内容而不是界面装饰上。Browser、Inspector 与 Detail 可收起，任何已收起面板都可从顶栏 `Layout` 菜单恢复，避免用户把自己锁在不可逆布局中。

SelectionContext 只保存 `storyId + type + entityId`，绝不缓存上一轮的条目对象。范围刷新后，Renderer 在新 Projection 中重新解析该 ID：存在则恢复 Inspector/Script Detail；不存在则清空选择并回到故事摘要。因此旧范围、分页变化或 Worker 重载不会留下“看起来仍可点、实际引用旧数据”的悬挂对象。

M4 暂不实现自由拖拽分栏、无限画布、Canvas 双渲染器或按十万对象的 LOD。原因不是忽视性能：range Projection 已有 14 天和 500 条的上限，DOM 工作量仍受控。虚拟化/Canvas 只能在完成 1k、10k、100k 基准后按数据决定；Dock Layout 与可拖拽尺寸则需要统一高 DPI、最小宽度、Pointer Capture 与恢复策略，不能由各个面板各自保存像素值。

### T6.1 前置条件（已由 T5 提供）

- 每个故事有稳定的本地 ID、schema v1 manifest、可恢复删除与导入隔离规则；
- GUI 不能直接读写 HDSI SQLite，也不能读取密钥；
- Worker 数量有明确上限，单个故事可独立加载、卸载和重载；
- 入站、收件箱、投递与渠道回执都有稳定 ID 与持久化记录；
- 配置写入、运行时重载和失败回滚已有唯一主进程边界。

因此 T6 可以专注于读模型、选择状态和界面性能，不必再在 Renderer 中发明业务事实或文件写入捷径。

### T6.2 第一目标：统一工作台状态

建立 Renderer 侧可序列化的 `WorkspaceState`，但其数据只来自预加载的只读 IPC：

```ts
interface WorkspaceState {
  surface: 'studio' | 'logs' | 'koishi'
  storyId?: string
  selected?: { type: string, id: string }
  timeRange?: { from: number, to: number }
  detailTab?: 'content' | 'calls' | 'deliveries' | 'logs' | 'data'
  filters?: Record<string, string | boolean | number>
}
```

- Studio、Logs、Koishi 三个 Surface 共用当前 storyId，但独立保存滚动位置、过滤器和面板尺寸；
- Surface 切换只改变视图，不加载第二份故事数据或第二个 Worker；
- 选中对象通过稳定 ID 深链接，不把整条剧本/数据库对象放在 URL 或全局 state；
- 故事被导入、移入废纸篓或 Worker 退出后，SelectionContext 必须自动退回安全父级状态。

### T6.3 第二目标：版本化的只读 Projection API

现有 `snapshot` 继续服务原型，但 T6 新接口必须支持范围、游标和 revision：

```ts
getStoryOverview({ storyId })
getTimelineRange({ storyId, from, to, tracks, cursor, detailLevel })
getDeliveryHistory({ storyId, cursor })
getUsageSeries({ storyId, from, to, granularity })
subscribeStoryEvents({ storyId, afterRevision })
```

约束：

1. HDSI 只负责叙事相关的投影；Outbox、收件箱、Worker 资源和宿主备份由 Main Process 投影；
2. 结果携带 `storyId`、`revision`、数据来源与时间语义；
3. 首屏只请求可见时间范围，缩放或滚动后再加载相邻页；
4. Renderer 不缓存无限历史，不直接执行 SQL，不以接收时间伪造故事发生时间；
5. 旧 `snapshot` 在 T6 期间仍保留，直到 Studio 多轨视图稳定后再废弃。

### T6.4 三个 Surface 的具体构建顺序

1. **Studio Shell**：先完成顶栏、Browser、中央 Workspace、Inspector、Detail Panel 的固定五区布局，接入 T5 的 Worker 容量、配置状态、收件箱、Outbox 和备份状态。
2. **Arrangement v1**：使用有限、虚拟化的时间线显示对话/投递、剧本、场景、日程四组轨道；未来 Schedule Preplan 使用半透明语义，不冒充已发生事件。
3. **Logs Surface**：主进程 `LogBroker` 已按故事/日期落盘并提供基础查询；下一步补齐轮转、范围分页、虚拟列表与 Renderer 批量通知，不能以无限 DOM 列表承载日志。
4. **Koishi Surface**：最后接入每故事隔离的 loopback Console endpoint 和受限 webContents；先只读观察和兼容配置，再开放经 ConfigMediator 写回的操作。

### T6.5 T6 不做什么

- 不接入真实 QQ/微信协议；真实适配器仍在 T4 后续的渠道子阶段完成；
- 不把 Koishi Console iframe 当作有主进程权限的页面；
- 不直接编辑 HDSI 数据库、事实、场景或剧本文字；
- 不在第一版实现无限缩放、任意浮动窗口或所有轨道同时实时渲染；
- 不为了更漂亮的界面改变 HDSI 的 Alter、压缩、Schedule Preplan 或消息队列语义。

### T6 验收标准

- 三个 Surface 可切换且保持同一故事上下文；
- Studio 首屏仅加载有限投影，切换故事不阻塞 Worker 路由；
- 从一条投递记录能定位其 Outbox 状态、HDSI 时间线对象和相关日志；
- 大量日志或历史条目不无限增加 Renderer DOM；
- Worker 上限、离线、故障和收件箱积压在顶栏/Overview 中可见；
- Blind/失明模式在 Studio、Logs、Koishi 三个 Surface 中保持一致的屏蔽规则。

## 8. 推荐的具体开发顺序

为了避免同时修改 GUI、HDSI、渠道与数据层造成难以定位的回归，建议严格按以下操作顺序推进。

### 第一步：固定当前桥接基线

1. 为现有 bridge 协议写最小协议测试：ready、phase、inbound、replay、snapshot、delivery、token、error。
2. 固定并记录当前 bridge 协议版本 `2` 的字段；新增字段保持向后兼容或明确升级策略。
3. 明确 HDSI `delivery` 的成功语义和未来渠道确认的衔接方案。
4. 将当前外部 HDSI 开发依赖记录为开发期选择，制定后续内置/打包策略。

完成标志：升级桌面端或 HDSI 时，IPC 字段变化会被测试发现。

### 第二步：完成 T3.5 Studio Shell 与 Arrangement

1. 搭建顶栏、Browser、Workspace、Inspector、Detail Panel 五区外壳；
2. 建立 SelectionContext 与布局持久化；
3. 接入对话、剧本、场景、日程四条真实数据轨道；
4. 让 Worker 事件驱动 Overview、时间线和投递状态节流更新；
5. 将数据按“发生时间 / 接收时间 / 处理时间 / 投递时间”分层显示；
6. 建立范围查询与增量 revision 的兼容接口；
7. 保持所有业务数据来自 bridge 只读投影；
8. 用常规故事和大数据夹具验证滚动、缩放、切换故事与面板折叠性能。

完成标志：不连接真实 QQ，也能在宿主工作台中完整演示一个故事的运行、静音、暂停、入箱、回放、HDSI 输出、时间线联动与诊断详情。

### 第三步：完成 Logs Surface

1. ✅ 已建立统一日志记录、主进程 LogBroker 与有限环形缓冲；后续集中完成轮转、查询 UI 和隐私规则；
2. 接入 desktop、Worker、bridge、Koishi plugin 和渠道来源；
3. 建立按故事/日期落盘、轮转、查询和导出；
4. 实现虚拟滚动、Follow/Pause、搜索过滤和多行折叠；
5. 实现日志与 Studio entity、Koishi plugin 的深链接；
6. 验证高频日志、隐藏 Surface、Blind 模式和大型文件搜索。

完成标志：用户既能保持传统 Koishi 滚动日志的使用习惯，也能从日志准确回到 typ-0 中的故事事件，且高频输出不阻塞 Renderer 或消息路由。

### 第四步：完成 Koishi Compatibility Surface

1. 为每个故事 Worker 分配隔离的 loopback Console endpoint；
2. 在安全 webContents 容器中嵌入对应 Koishi Console；
3. 先开放插件、连接和状态观察；
4. 将账号发现和插件健康同步到 Overview/Routing；
5. 实现 ConfigMediator，解决临时运行配置、canonical YAML 与 `$secret:` 引用安全；
6. 开放受控的第三方插件配置、启停和重载；
7. 验证跨故事隔离、外部导航、权限、Worker 重启和 Blind 模式。

完成标志：用户可以配置和连接 HDSI 原生界面尚未覆盖的 Koishi 插件，修改能安全持久化，且页面无法越过故事与主进程安全边界。

### 第五步：实现一个最小渠道适配器

1. 仅选择一个渠道和一个消息类型起步：私聊纯文本；
2. 接入真实输入 → 统一事件 → 绑定路由 → HDSI；
3. 接入 HDSI delivery → 真实文本发送；
4. 保存渠道发送回执与失败信息；
5. 测试 running/muted/paused 三态与重启恢复。

完成标志：真实 QQ 私聊可从头到尾闭环，且异常不会丢消息。

### 第六步：扩展渠道能力，但一次只扩展一类

建议顺序：

1. 群聊上下文与群账号绑定；
2. 引用消息；
3. 原生表情与贴表情；
4. 图片与本地贴纸；
5. 语音输入/输出；
6. 微信或第二种外部渠道。

每增加一种元素，必须分别验证“入站保存”“HDSI 可理解”“出站投递”“失败回显”四个阶段；不要只验证“模型输出看起来有字段”。

### 第七步：完成配置中心和故事导入导出

1. 先实现密钥别名管理与模型配置；
2. 再实现渠道账号发现与绑定；
3. 再做角色/功能配置与受控重载；
4. 最后实现故事迁移、备份、版本升级和首次运行向导。

完成标志：新用户无需手动进入数据库或大量编辑 YAML，也能创建、配置、运行和备份一个故事。

## 9. 测试与验收矩阵

### 9.1 必须自动化的回归项

| 范畴 | 最少覆盖 |
| --- | --- |
| 账号绑定 | 绑定、冲突拒绝、显式替换、解绑、重启恢复。 |
| 收件箱 | 原子写入、顺序回放、只在确认后删除、失败保留、旧格式迁移。 |
| 三态 | running 立即输入；muted 入箱但自动生活继续；paused 阻止新的自动工作。 |
| bridge | 协议握手、错误处理、超时、Worker 退出、重启。 |
| 时间 | 使用渠道原始事件时间；回放不把处理时间冒充发生时间。 |
| 配置 | `$secret:` 解析不修改原文件、不向日志泄漏明文。 |
| 投递 | 成功、网络暂态失败、永久失败、重复回执、渠道掉线。 |
| Logs Surface | 多来源采集、故事隔离、暂停不丢失、虚拟滚动、轮转、搜索、Blind 屏蔽。 |
| Koishi Surface | endpoint 隔离、导航限制、Worker 重启、配置写回、secret 恢复、插件重载。 |
| Surface 路由 | Studio/Logs/Koishi 切换、故事上下文一致、深链接与状态恢复。 |
| HDSI | 继续执行 HDSI 全量类型检查、构建与既有测试。 |

### 9.2 手工验收场景

1. 创建一个故事，配置一个密钥引用，启动 Worker；确认原始 YAML 中没有 API Key。
2. 绑定一个测试账号，向该账号发送私聊；确认 HDSI 收到的时间与渠道时间一致。
3. 切为静音，连续发送多条消息；确认角色仍可自动推进，消息按顺序留在收件箱。
4. 恢复运行；确认每条消息只交给 HDSI 一次，且只有收到确认后才从收件箱消失。
5. 切为暂停；确认新的自动推进、压缩与定时工作没有启动。
6. 让渠道断线后触发一次投递；确认 UI 显示失败原因，不伪造“已送达”。
7. 关闭并重开桌面端；确认绑定、故事状态、收件箱、日用量和可恢复 Worker 状态符合预期。
8. 导出故事、在另一台干净环境导入；确认数据可读但密钥需要重新绑定。
9. 在 Studio 选中一条错误并跳转 Logs；确认自动带入故事、时间与 correlation ID，返回后原选择仍存在。
10. 暂停 Logs 画面并产生大量日志；确认日志继续落盘，恢复后可查看积压且界面没有卡死。
11. 打开两个故事的 Koishi Surface；确认插件、端口、会话和配置互不串线。
12. 在 Koishi Surface 修改一个第三方插件配置并重启 Worker；确认修改仍存在，原有密钥仍为 `$secret:` 引用。
13. 启用 Blind/失明模式；确认 Studio 内容、Logs 和 Koishi 管理入口都遵从屏蔽规则。

## 10. 主要风险与处理原则

### 10.1 HDSI 源码双份导致漂移

风险：当前 `hdsi-sourcecode/` 是项目内参考副本，但 Worker 实际依赖 `C:\dev\HDS-Interlude`。两个副本如果各自修改，桌面端测试的代码可能不是最终发布代码。

处理：在 T5 发布准备前选择一种策略并执行到底：

- 将 HDSI 作为固定版本 npm 依赖；或
- 将 HDSI 作为此仓库的受控 git submodule/subtree；或
- 发布时由明确脚本同步单一来源，并对版本/hash 做校验。

不建议长期保留“一个能看、另一个在跑”的无约束关系。

### 10.2 GUI 直接碰数据库

风险：SQLite schema 变化、并发写入、故事迁移与 HDSI 内部约束都会让 GUI 直接读写变得脆弱。

处理：坚持 bridge 的只读投影；若桌面需要执行业务动作，新增明确的 HDSI 指令而不是 SQL。

### 10.3 一次性接入过多渠道能力

风险：群聊、引用、贴纸、图片、语音、好友管理的协议差异很大，混合接入会使 bug 来源不可辨认。

处理：先完成“一个渠道 + 私聊文本 + 完整收发与失败可见”，再纵向扩展能力。

### 10.4 Worker 与渠道投递的一致性

风险：角色剧本认为已回复，但渠道实际失败，或渠道重复投递。

处理：保存独立投递记录、建立明确的 delivery acknowledgement 语义、对暂态失败有限重试、所有失败可见。不要靠静默吞错掩盖问题。

### 10.5 多故事资源争抢

风险：多个角色同时自动推进、压缩、视觉处理时，可能造成 CPU、内存、网络与模型额度竞争。

处理：Worker 级隔离、启动/低优先级任务预算、故事级健康状态。资源优化不能篡改 HDSI 对实时输入和重要后台任务的既有优先级语义。

## 11. typ-0 完成后的产品形态

完成 T4 与 T5 后，typ-0 应当呈现为下面这样的工作方式：

```text
启动 typ-0
  │
  ├─ 顶层主界面
  │    ├─ Studio：多轨故事时间线、路由、模型、配置与诊断
  │    ├─ Logs：传统滚动日志、搜索、过滤与导出
  │    └─ Koishi：当前故事的插件配置、服务与连接管理
  │
  ├─ 看到多个故事卡片
  │    ├─ 水濑：运行中，QQ 已连接，收件箱 0，今日用量正常
  │    ├─ 另一角色：静音中，积压 3 条消息，日程仍在推进
  │    └─ 测试角色：暂停，等待配置模型
  │
  ├─ 打开一个故事
  │    ├─ 查看角色近期剧本、场景、事实和半透明的日程预案
  │    ├─ 观察实时输入、投递结果、错误和模型用量
  │    ├─ 调整模型、角色能力、渠道与运行状态
  │    └─ 备份、复制或导出这个故事
  │
  └─ 外部 QQ/微信消息自动按账号绑定进入正确故事
       ├─ 运行：立即与角色对话
       ├─ 静音：不打断角色，安全收进收件箱
       └─ 暂停：停止新的故事自动工作，消息等待恢复
```

三个主界面共享当前故事与顶栏状态，但各自保持自己的上下文。用户可以从 Studio 的一次失败投递跳到 Logs 查看原始错误，再跳到 Koishi 修改对应适配器配置，完成后返回 Studio 验证新的投递状态。整个过程不需要退出故事、寻找另一个本地端口或手动翻查不同日志目录。

它会把 HDSI 已有的高密度叙事能力变成一个更稳定、可见、可维护的个人角色系统：角色依然拥有连续生活和主体性，用户则拥有清晰的控制面、观察面和数据边界。

### 11.1 完整 Studio 工作方式

一个成熟的 typ-0 工作区应形成以下稳定关系：

```text
Browser 负责“找到对象”
        │
        ▼
Arrangement / Workspace 负责“理解关系与时间”
        │
        ▼
Inspector 负责“解释当前选择”
        │
        ▼
Detail Panel 负责“查看原始依据与诊断”
        │
        ▼
Command 负责“执行受控操作并返回真实结果”
```

例如用户发现角色突然复读：

1. 在 Arrangement 中定位重复回复；
2. 同时看到两次回复各自对应的剧本、场景和时间；
3. Inspector 展示它们使用的近期上下文、Schedule Preplan 和投递状态；
4. Detail Panel 展示主模型调用、压缩、缓存、恢复重写与 Token；
5. 用户可以判断是模型生成重复、旧 delivery 被补发、收件箱重放，还是时间线事实本身重复；
6. 如存在安全修复命令，从 Inspector 发起并等待 HDSI 返回真实结果。

这种联动使 typ-0 同时服务两类使用者：普通用户可以通过默认轨道与状态理解角色当前生活；高级用户和开发者可以下钻到运行时证据，而不需要先学习 SQLite 表结构或翻找多个日志文件。

### 11.2 最终能力边界

最终 typ-0 可以做到：

- 像宿主软件一样集中管理多个 HDSI 故事；
- 像时间线编辑器一样观察角色的过去、现在与半透明未来；
- 像路由工作站一样管理 QQ、微信、SnowLuma 和未来渠道；
- 像模型控制台一样配置不同用途并观察延迟、费用和回退；
- 像诊断工具一样追踪消息从渠道输入、HDSI 写作到真实投递的完整链路；
- 像本地创作工程一样备份、复制、导入和迁移故事；
- 同时保留 HDSI 的角色主体性、自动生活和 Blind/失明模式。

它不应演变成一个允许随意拖动剧情、直接编辑数据库、用 GUI 伪造运行结果的“剧本编辑器”。typ-0 的核心价值是让复杂系统变得可理解、可控制和可靠，而不是取代 HDSI 自己对角色世界的维护。
